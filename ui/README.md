# erpcraft admin UI

The first slice of the admin UI. It is generated from what the server says about itself (`GET /api/meta`): the menu, every list, every form and every document screen are built from the registry, so a module that adds an entity or a document type gets its screens without UI code.

The rules this code follows are in [GUIDELINES.md](GUIDELINES.md). Read them before changing anything here.

## Run it

The erpcraft server must be running on `http://127.0.0.1:8600` (set `ERPCRAFT_URL` to use another address). The scripts read `ERPCRAFT_ADMIN_EMAIL` and `ERPCRAFT_ADMIN_PASSWORD` from `../.env`.

| Command               | What it does                                                                                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun install`         | Installs the dependencies.                                                                                                                                                                                                                |
| `bun run dev`         | Dev server on http://127.0.0.1:5173. `/api` and `/mcp` are proxied to the server, so the browser needs no CORS.                                                                                                                           |
| `bun run seed`        | Creates demo data through the API: the company "Ohio Widgets" with accounts, a fiscal period, items, warehouses, a vendor, a customer, settings, a tax code, and documents in several states. Safe to run twice.                          |
| `bun run generate`    | Reads `/api/meta` from the running server and rewrites `src/api/generated.ts`. Run it after the server's commands, entities or document types change.                                                                                     |
| `bun run check`       | TypeScript, Biome (lint and format) and the tests. A change that fails it is not merged.                                                                                                                                                  |
| `bun run format`      | Applies Biome's formatting and safe fixes.                                                                                                                                                                                                |
| `bun run build`       | Type-checks and builds static files into `dist/`.                                                                                                                                                                                         |
| `bun run check:dist`  | Checks that `dist/` runs under the content security policy the server sends with it (no inline script, no `eval`, nothing from another host, no `data:` URL).                                                                             |
| `bun run e2e`         | Drives the UI in headless Chrome against the real server and checks it end to end. Needs `bun run dev` and the seed. Takes the groups to run as arguments (`bun run e2e documents "purchase to pay"`).                                    |
| `bun run screenshots` | Retakes `docs/screenshots/*.png` with headless Chrome. Needs `bun run dev` running and the seed data. If a company with the code `AWC` exists, it also takes the `awc-*` pictures there, which show the tables with thousands of records. |

Use `bun` for everything. Sign in with the administrator from `../.env`, or any user created with `user.create`.

## What exists

Everything below is built from what the server declares in `GET /api/meta`; where the UI still decides something itself, the README says so under "What does not exist yet".

- **Sign-in** with email and password, and one button per single sign-on provider (`GET /api/auth/sso`). A provider's sign-in starts as a plain navigation to `/api/auth/sso/<slug>/start?return_to=...`; when it comes back with `?sso_code=`, the code is exchanged (`POST /api/auth/sso/exchange`, with this origin's cookies) before the app decides whether anyone is signed in, and is removed from the address. `?sso_error=<word>` on the sign-in page is explained in one sentence. The token is kept in memory and in `sessionStorage`; a 401 returns to the sign-in page and, after signing in, to where the user was.
- **Shell.** A menu grouped by module (the module's `label`), listing only what the user may read, each entry by its `plural`. Entities with a `parent` (bill of materials lines) are not in the menu; they are a table on the parent's page. The current company is always shown and is the first part of every URL (`/c/OHIO/...`). Ctrl+K opens a palette that goes to any screen or report, starts any new record, switches company, and finds records and documents with `search.records`.
- **Entity list** for any entity: search, sort, paging and total on the server and in the URL; a column chooser per user (kept in `localStorage`, timestamps hidden by default).
- **Entity record**: inputs chosen by field type; required fields marked; `default` fills a new record; `help` under the input; enum `labels`; references of every kind (below). Errors appear next to the field the server names. A failed save keeps what was typed; leaving with unsaved changes asks first; a stale save (`409`, `reason: "stale"`) says what the other person changed and offers their version or yours. The record's commands (`target`, `resource`) are its actions. Reports that take the record's id (`gl.account_ledger` for an account) are offered from it. Child entities are listed under it.
- **Document list** for any document type: number, date, status, the type's `summary` fields (who it is with, its totals; sortable as `summary.<field>`), memo; search, status filter and a filter by each summary party, all in the URL.
- **Document page**: the header fields (`document_header` gives the labels of date, memo, created by), the type's fields, and each collection as a line grid. Lines go back to the server as it returned them, with their ids and computed fields. An error on a line is shown on that line, by the field it names. Decimals are shown by their `decimal.role` (money and unit prices with their currency's decimals, quantities with their unit of measure). The summary's figures are a totals block. Actions are the commands whose `resource` is the type and whose `from_states` include the status; `destructive` ones look different. An action is previewed first: the preview shows the change of status and number and the entries the posting will make in each ledger (general ledger, stock, open items, tax). Actions that draft a follow-on document (`creates`: Receive, Invoice, Deliver) run at once and open the draft. Postings of a posted document are shown with their entries.
- **References**: `link` (a searchable lookup with recent choices first and "New ..." last, `active_only`), `document_link` (documents of a type in the allowed states), `line_link` (a line of the document another field names), `lookup` (the rows of a query command, with inputs read from the record), `entity_link` (a record of the entity another field names), `posting`.
- **Reports**: every command with `report` is a page at `/c/:company/r/<command>`. Trial balance, balance sheet, income statement, account ledger, open items and stock on hand have pages of their own; any other report (audit log, sign-ins, outbox, tax report, and whatever a module adds) gets a generic page built from the command's input and output schemas.
- **Open items** with Pay: choose items of one vendor or customer and a bank account; `payment.draft` drafts the payment, which opens.
- **Policy rules**: the point is chosen from `meta.policies`, which also explain the point's facts and default beside the form; point and condition are always sent together.
- **Printing**: every document has a Print view (`document.render`). The page is shown in an `iframe` with an empty `sandbox` (no scripts, no origin of its own) loaded with `srcdoc`, with a choice of the print templates for the document's type and company. Print opens the page in a window of its own from a Blob URL, with a Content-Security-Policy `<meta>` that forbids every script (a Blob document also inherits the app's policy), and prints that window. **Print templates** are edited on their record page, with "Start from the built-in template" (`print_template.builtin`) and the template as it is being written rendered against a chosen document beside the form (`print_template.preview`; nothing is saved).
- **Single sign-on providers** have screens of their own on `sso_provider.*`: the form is built from the commands' input schemas, the client secret is write-only (set at creation, replaced with "Set client secret", never shown), the redirect URI to register is shown with a Copy button, and changing the issuer or client id warns first. Users bound to a provider are listed (`sso_identity.list`) and unbound (`.delete`); a user is bound (`.set`) from a sign-in through the provider in `auth.events`.
- **Field-level access** (`access.entities.*.fields`): a field the user may not read is left out of lists and forms; one they may not create or update is read-only for that; a field readable on some records shows "(withheld)" where the value was held back.
- **The palette runs actions**: on a document, its actions are offered first in Ctrl+K and run as their buttons do (follow-on drafts at once, everything else through the preview).
- **Bulk actions**: in a document list, choose documents and run an action that every chosen document's state allows. The confirmation says what will run on how many; each document is its own request with its own idempotency key; the result is listed per document, with the server's reason for each refusal.
- **Users** are an entity: listed and read through the generic pages, edited with `user.update` (the dialog starts from the user's values), activated and deactivated, and their roles granted (`user.assign_role`, for one company or all) and taken away (`user.revoke_role`) on the user's page. Binding a user to a single sign-on identity picks the user from the users.
- **Company setup**: "Set up a new company" (on the companies list, in Ctrl+K, and where there is no company yet) lists the templates of `setup.templates` with their descriptions, asks for what `company.setup` takes, shows the server's preview of what will be created (accounts, fiscal years, tax codes, which account does which job), and then sets the company up and opens it.
- **Ledger entries** under postings are typed from the entry schemas the registry publishes (`ledgers`), titled from them, and an entry in another currency shows its transaction amount beside the accounting amount. A ledger the UI has no layout for is a table of its schema's fields.
- **Lookups** apply the filters a link declares (`{"is_bank": "true"}` for a payment's bank account, also in Pay). Status badges take the state's `tone`. Fields written together are the entity's `written_together`.
- **Banking**: "Import statement" on the statements list (`/run/bank_statement.import`) takes the bank account, the format (camt.053, OFX, or CSV read with the account's saved `bank_csv_mapping`, edited on its record page and reached from here) and a file read in the browser. A draft statement's page is a matching workspace: each line with its proposals from `bank_statement.proposals`, accepted with `bank_statement.match`; a line paid through open items shows the drafted payment, posted from there through its preview; "Reconcile" posts the statement. Keyboard: ↑↓ or j k between lines, Enter takes the best proposal, 1–9 a particular one, a goes to the account, x clears. The `bank.reconciliation` report sets the books against the statements. `bun run seed` adds "1010 Checking (demo)" with a June statement to match.
- **Payment terms and aging**: the `open_item.aging` report shows what is owed or owed to the company in buckets of days past due, what falls due in 7 and 30 days, and the control accounts beside what their items add up to; a party's row opens its items. The open items page shows due dates and early-payment discounts, and Pay says which chosen items may still be paid with a discount; `payment.draft` puts the discount on the payment's line when it is paid in time.
- **New records through commands**: an entity the generic layer does not write (users) gets "New" from the command that creates it, with a form built from that command's schema; secret inputs are masked.
- **Foreign currency**: amounts are shown in the currency their field declares (the company's, a field of the record, or the document's header for its lines); a document in another currency shows its totals in both.
- **Approvals**: an action a policy rule holds for approval says so in its preview ("needs approval by ...", with the rule's message and facts), and after asking shows that it is waiting, with a link to the request. The Inbox (`approval.list`: to approve, asked by me, all; by status) lists requests with the record each is about and its facts; a request's page shows the record by its number and party with its totals, the facts labelled as the policy point declares them (`meta.policies[].facts`), the command's input with ids shown as what they name (the raw JSON behind Details), and the decisions, and lets an approver approve or reject (a reason is needed to reject). The requester is never offered to decide their own request. A policy rule with effect `approve` names the approver role or permission, how many approvals are needed and for how many days. A bulk action that is held is listed with its request.
- **Fixed assets**: the `asset.register` report lists the assets with cost, accumulated depreciation, book value and this year's depreciation, with totals, and sets each account the asset classes name beside the ledger (agree or differ, and whether the whole register ties). An asset's row opens its depreciation schedule (`asset.schedule`, also a button on the asset): month by month, posted (with the run that posted it) or planned, with the book value after each. A depreciation run is a document whose lines the server proposes: they are shown, not typed, and a new run says they are worked out when it is saved. An asset offers its actions with what they ask for (Take over: cost, depreciation to date, dates; Put in service; Capitalise: a picker of the posted lines that debited the class's asset cost account and that no asset was capitalised from, then the in-service date), and "New Asset disposal" starts a disposal with the asset filled in; posting it previews what leaves the books and the gain or loss.
- **Actions that ask for something**: an action whose command needs more than the record is offered when a dialog can ask for it: dates, numbers, yes or no, choices, links the server describes, text. One that needs a document line or an id the schema says nothing more about is not (`asset.capitalise`).
- **Documents started from a record**: a record page offers "New …" for each document type whose header requires a link to it (a disposal from its asset, an order from its vendor), and the new document starts with that link filled in from the address.
- **Line kinds**: where a document type declares that a line is one of several kinds (`alternatives`: a stock item, a charge, an account; or an order line), the grid shows one column with a kind switch and the fields of the chosen kind; switching empties the others. A kind made of a line of a document the header does not name yet (an order line on an invoice without an order) is not the default. Discounts (percent and amount) and the net the server works out are columns of their own.
- **Invoices without an order**: a document type whose source document is optional and whose party it then names itself (vendor and sales invoices) offers "New … without …" on its list and on the party's record; the new document leaves the source out and starts with the party.
- **E-invoicing**: a posted sales invoice or credit note has "Export e-invoice" (syntax and profile from `einvoice.export`'s schema; the XML downloads, and the rules it breaks are listed). "Import e-invoice" on vendor invoices reads an XRechnung or ZUGFeRD file in the browser and shows `einvoice.read`'s proposal (what the invoice says, the vendor its VAT identifier names or the candidates to confirm, the order, where each line goes, the tax code, the rules it breaks) before `einvoice.import` drafts the vendor invoice. A customer, vendor or company shows its e-invoice data (`einvoice_party`, `einvoice_profile`) under it, with "New" when there is none.
- **Money inputs** show their value as read-only money does (grouped, with the currency's decimals) while they are not being edited, and the digits as typed while they are.
- **Saved views**: each document and entity list can save its search, filters, sort and columns under a name and switch between them. Views are kept in this browser's `localStorage`, per user and per list; keeping them on the server, so they follow the user and can be shared, is a later step.

### How it is put together

```
src/api/generated.ts   Generated: the input and output type of every command, and the registry's own types.
src/api/types.ts       Shorter names for the generated types, and the few shapes the server does not describe.
src/api/client.ts      The one API client. Nothing else calls fetch. Everything but sign-in is a command.
src/app/sso.ts         Finishes a single sign-on before the router starts.
src/i18n/              t() and the English dictionary. All of the UI's own text is here.
src/lib/               meta.ts (reading the registry), decimal.ts (decimal strings, never numbers), dates.ts,
                       link-labels.ts and doc-labels.ts (names of referenced records and documents), url-state.ts.
src/components/ui/     shadcn-style primitives, written by hand on Radix and Tailwind.
src/components/        The shared components that carry the rules: DataTable, Lookup, Picker, MoneyInput, DateInput,
                       Dialog (does not close on an outside click), unsaved-changes guard, ActionDialog (preview, then
                       confirm), Postings (ledger entries), DecimalValue, references.
src/pages/             One generic page per kind of screen, and the reports with a page of their own.
src/index.css          Design tokens (light and dark). The only file with raw colors and sizes.
scripts/               generate-api-types.ts, seed.ts, screenshots.ts, e2e.ts, check-dist.ts, browser.ts.
```

How the guidelines are enforced:

- **Types**: `strict`, `noUncheckedIndexedAccess`; Biome forbids `any`, `@ts-ignore` and `!`.
- **Biome**: `fetch` and `parseFloat` are forbidden globals outside `src/api/client.ts`; `@radix-ui/*` may only be imported inside `src/components/`; string literals as JSX text are an error.
- **`src/guidelines.test.ts`**: scans the source for what Biome cannot express: `Number(`, `.toFixed(`, raw colors, Tailwind's fixed palette, arbitrary pixel sizes, type escapes.
- **The generator**: `CommandInputs` and `CommandOutputs` type every `api.run(...)` call; names the UI relies on (`company`, `account`, ...) are typed as `EntityName`, so a rename on the server breaks the build.
- **`bun run e2e`**: the scripted browser run, including purchase to pay through the follow-on drafts and the open items page, the print view, a restricted user's fields, a bulk post with a refused row, an action from the palette and single sign-on providers. It signs in as one test user, `e2e-restricted-test-user@example.test`, whose role it sets; its password is derived from the administrator's at run time and never stored.

### Development sign-in by URL

In development builds only (`import.meta.env.DEV`), a page opened with `#token=<token>` adopts that token and removes it from the address. `scripts/screenshots.ts` and `scripts/e2e.ts` use this. Production builds ignore the fragment.

## What does not exist yet

- **Still decided by the UI, because the server does not say:**
  - The four ledgers the UI knows (`gl`, `stock`, `open_items`, `tax`) have a layout of their own: which fields are columns, and how a settlement reads. Their column titles come from the entry schemas.
  - Money is shown in the currency its field declares. Where a document is in another currency, the server declares some of its amounts in the company's currency although they are in the document's (reported; the UI follows the declaration and will follow its correction).
- Saved views are kept in the browser only.
- `asset.capitalise` takes a document line as plain ids; which lines qualify is worked out in the UI (`src/components/line-pickers.tsx`) from the command's description: debits to the class's `asset_cost` account not yet capitalised. Openings of taken-over assets are offered too, as the server does not link them.
- Records that belong to another record without being its lines (e-invoice data) are found by a required typed link that can name the record's entity, or a display that starts with a required link to it (`src/pages/attached-records.tsx`).
- The labels and colours of approval statuses (`pending`, `executed`, `failed`, `stale`, `rejected`, `expired`) are the UI's: `approval.list` names them only in its description.
- Aging cannot open the items of one bucket: `open_item.list` has no filter by days past due, so a party's row opens all its items.
- Only English. Dates and numbers follow the browser's locale.
