# erpcraft architecture

erpcraft is an open-source ERP written in Rust, meant to be the layer other ERPs are built on. It ships a reference ERP in the same repository, and it is MCP-native: an AI agent can do what a user can do, through the same commands and with the same permissions.

Sibling project: SolidCraft (parametric CAD, same maker, same MCP-native approach). Domain: `erpcraft.io`.

Status: the first slice works end to end. A journal entry can be drafted, posted and reversed over HTTP and over MCP. Sections below say what is **built** and what is **planned**.

## Decisions

| Topic | Decision |
|---|---|
| Language | Rust |
| Database | PostgreSQL only. Its transactions, row locks and triggers carry the invariants. |
| Scope | Kernel plus a full reference ERP, in one repository |
| Target | Small and medium companies, the range of SAP Business One or a minimal Dynamics 365: a manufacturer in Ohio or in Germany. United States, Canada and the European Union first. |
| Localization | Country-specific rules (tax, reporting, formats) are modules, meant to be opened to the community. Nothing country-specific goes into the kernel or the ledgers. |
| Structure | High cohesion, low coupling. A module owns its tables, documents and rules, and reaches others only through their public API. |
| Extension model | Rust crates implementing the `Module` trait, registered at compile time |
| Interfaces | HTTP and MCP, both generated from one registry |
| Tenancy | One database per tenant; many companies inside it |
| License | `MIT OR Apache-2.0` in `Cargo.toml`, as SolidCraft. License files are not added yet; confirm before the first public push. |

**Migrations go forward only.** Each module numbers its own migrations, and `erpcraft_migration` records which have run. A binary applies what is pending when it starts (or with `--migrate-only`), one migration per transaction, under an advisory lock. It refuses to run against a database that records a migration it does not know: such a database was migrated by a newer binary, and the way back is the backup taken before the upgrade (`erpcraft_db::status`; docs/ops/UPGRADING.md). `erpcraft verify` checks every ledger against the others from the tables, read in one read-only snapshot, after a restore or at any time (`apps/server/src/verify.rs`; docs/ops/backup.md).

Planned: SAML and SCIM inside `erpcraft-auth` (single sign-on with OpenID Connect is built), then tax and localization modules per country, and the admin UI in `ui/`.

Dependencies point one way: `core` ← `db`, `rules` ← `kernel` ← `gl`, `stock` ← modules. The kernel knows nothing about accounting, and nothing about passwords or tokens. The two ledgers know nothing about each other: a module that moves stock posts its value to the general ledger itself, in the same posting.

## The model

### Commands

Every business operation, read or write, is a registered **command**: a name such as `journal_entry.post`, a typed input with a JSON Schema, a permission, and a handler. HTTP, MCP and the future UI all call the same executor, so no interface can go around a business rule.

The executor gives every command:

- one database transaction;
- an authorization check before the handler runs;
- an idempotency key (optional): the same key and input return the first result, the same key with different input is refused;
- a preview mode: run, return the outcome, roll back. A preview reserves nothing; the real run validates again;
- an audit record of who ran what with which input, and which records it touched. A command that fails or is refused is recorded too, with the reason. For a command marked sensitive (it handles secrets) neither the input nor anything made from it is recorded: a failure keeps only the error code and a fixed sentence for that code ("the input was refused"), because any error message may quote what was sent, such as a secret pasted into the wrong field. The caller still gets the full message;
  A command may instead redact named input fields too large to keep, such as a file's content (`CommandSpec::redact`; `edi.receive` redacts `content` and `content_base64`): the audit log and the outbox hold `{"sha256", "bytes"}` of each in place of its value, and the rest of the input as given. An approval request keeps the whole input, as it must to run it. The idempotency key still compares the whole input, so a different file under the same key is refused;
- an outbox event, written in the same transaction, for delivery after commit.

Queries are commands marked read-only. A module publishes its reads (`gl.trial_balance`) the same way as its writes, so other modules and reporting tools do not need to know its tables.

Entity metadata describes the data. Commands define what the system may do.

A command describes itself, so that an interface need not derive anything from its name or try it to see whether it applies. Besides its input schema, `meta.describe` gives for each command: a `label` for a button; the `resource` it is about and whether that is an entity or a document type (`resource_kind`); whether it acts on one record named by the input `id` (`target`); for a command on a document, or on an entity that declares a `state_field` (the fiscal period's `status`), the states it applies from (`from_states`), checked against the document type's states or the field's values when the server starts; whether it reverses, cancels or deletes (`destructive`); whether it is a `report` to show as a page, with a title; and an `output_schema`, the JSON Schema of what it returns. Every property of an input, and every property anywhere in a report's output, has a `title` (from the field name unless declared), so a form and a table can label it. Decimals are strings in both schemas. A module states these with the builder methods of `CommandSpec`; all but `from_states`, `destructive` and `report` have a default taken from the name and the input.

### Errors

Every interface sends the same error object: `code` (`validation`, `not_found`, `conflict`, `forbidden`, `unauthorized`, `internal`) and `message`, a complete sentence. Where it is known, the object also says where the error applies, so that an interface can mark the place instead of reading the sentence:

- `field`: the field the error is about;
- `collection` and `line`: the collection of a document body and the line in it, counted from 1; `field` is then a field of that line;
- `reason`, on a `conflict` only: `stale` (the record changed after it was read: read it again), `state` (the record or document is in a state that does not allow this), `duplicate` (a unique value is taken), `in_use` (something still refers to the record). A conflict that is none of these has no reason.

Input that cannot be read is reported the same way, in words: which field, on which line, what was expected and what kind of value came instead. The value itself is never repeated, for any command: the caller knows what they sent, and the sentence goes on into the audit log. Over HTTP the object is the `error` of the response body; over MCP it is the `error` of the tool result's structured content, and the result's text is the same JSON. Modules raise such errors with `Error::field`, `Error::line`, `Error::stale`, `Error::state`, `Error::duplicate` and `Error::in_use`, and read a document body with `erpcraft_kernel::input::parse`.

### The registry describes, the interface renders

Whatever an interface would otherwise guess is declared in the registry and comes with `meta.describe`. A module states each with one builder call, and most have a default.

- **How a state is shown.** Each state of a document type has a `tone` (`neutral`, `info`, `success`, `warning`, `danger`): the meaning of a colour, not a colour. Unless a module says otherwise with `StateMeta::tone`, an editable state is neutral, a locked one success, `open` and `released` info, `cancelled` neutral (it never happened) and `reversed` danger (it happened and was taken back).
- **Copies of linked fields.** A field can declare that it copies a field of the record a link beside it refers to (`FieldMeta::shown_from`, such as a summary's `vendor_name` from `vendor_id`). A reader who may not read that record, or that field of it, gets it blank in every document read and list, and may not filter or sort a list by it unless they read every such record and field.
- **What a ledger's entries hold.** Each ledger declares the schema of the rows it shows under a posting (`Ledger::entry_schema`, with a title on every property), published in `meta.describe` as `ledgers: [{name, label, entry_schema}]` and put into the output schema of every command that returns a document, under `postings[].entries.<ledger>`.
- **Fields written together.** An entity can name fields that are checked against each other (`written_together`: a policy rule's `point` and `condition`, an account rule's `scope_type` and `scope_id`); an update that sends some of a group and not the rest is refused, naming the missing field.
- **What a field refers to.** Besides a link to an entity, a field can refer to a document of one type, optionally only in given states (`FieldType::document_in`); to a line of the document another field holds (`FieldType::line_of`); to a record of the entity another field names (`FieldType::entity_named_by`); to a row that a query command lists, such as an open item (`FieldType::Lookup`, with the inputs that narrow the list, and `by_keys`, the input that lists given rows whatever their state, so that a value already chosen can be shown: `open_item.list` takes `ids`, and a posted payment shows the items it settled through it); or to a posting. The kernel knows nothing about open items: the lookup names the command. A link to an entity can also name fixed `filters` that say which records to offer, in the form `entity.list` takes them: a payment's `bank_account_id` offers accounts with `is_bank`, which setup templates set for bank and cash accounts and an upgrade set for the accounts posted payments used. The registry refuses a reference that leads nowhere, and a test refuses a document body field named `*_id` that is a bare id.
- **What a decimal is.** `.money()`, `.unit_price()`, `.quantity()`, `.rate(n)` or `.percent(n)` give a decimal field its role and its number of decimal places, and say where its currency (the company's, or a field beside it) or its unit (a field of a linked record, such as the item's) is. For an entity the decimal places are read from the table.
- **What a field starts as and offers.** The default of an entity's field is read from the table; a choice has a label for every value (`FieldType::options` makes them from the values, `FieldType::labelled` states them); `.help(...)` adds one line of guidance.
- **How a record is shown and retired.** An entity names the fields that tell a person which record it is (`display`; its search fields unless declared), its plural, the boolean field that says a record is no longer used (`active_field`; a field named `active` unless declared), and the record it belongs to and is edited inside, if any (`child_of`). `entity.list` leaves retired records out when asked with `active_only`, which is what a lookup wants. Document types have a plural too, and modules a label.
- **Which action comes first.** A command may say when it is a record's primary action (`CommandSpec::primary_when`, in `meta.describe` as `primary_when`: `states`, any state when empty, and optionally a collection that must be `empty` or `not_empty`). A payment run's primary action is `payment_run.propose` in `draft` while it has no `lines`, and `payment_run.approve` in `draft` once it has some. An interface takes the first of a record's commands whose `primary_when` matches, else its first command that is not destructive. The states and collections are checked against the document type when the server starts.
- **What every document has.** The header fields (`number`, `status`, `doc_date`, `memo`, who created it and when) are described once, under `document_header`, like the fields of a body.

### Lists

Every list of entity records or documents takes the same parameters and returns one page as `items` plus the size of the whole list as `total`:

- `q`: text to find in the fields the entity declares as its search fields (a code, a name);
- `where`: a condition in the rule language, for example `record.debit > 100 && record.account_type == 'asset'`;
  it can test text (`record.name.containsIgnoreCase('bolt')`; also `contains`, `startsWith`, `endsWith`, the `IgnoreCase` forms of those and `equalsIgnoreCase`, compiled to `LIKE`/`ILIKE` with the wildcards in the value escaped), read dates relative to today (`today()`, `addDays`, `addMonths`, `startOf`/`endOf` `Month`, `Quarter` and `Year`; only in a list's condition, never in a stored rule, which is also decided in memory), and name a document's summary fields as `record.summary.<field>`;
- `params`: values the condition reads as `params.<name>`, bound as parameters, so a list of 500 ids is `record.customer_id in params.customers` and does not lengthen the condition;
- `time_zone`: the reader's zone (an IANA name the database knows): what day `today()` is, and where a day begins when a timestamp is compared with one;
- `sort`: field names, `-` for descending, and ` nulls first` or ` nulls last` after one to say where rows without a value go. A choice sorts in its declared order (a workflow's states in theirs), a link to an entity by what the linked record is shown as when the reader may read that of every such record, and a document summary's link by the name the summary shows for it;
- `limit` and `offset`.

All of it runs in the database, in the same query as the caller's row permissions. So a total never counts a record the caller may not see, and a field withheld from the caller cannot be searched, sorted by, or named in a condition.

**Line figures of a draft.** A draft's view, and so a preview of creating or changing it, shows each line's figures as posting will work them out: the net amount on the lines of orders, invoices and credits, the tax its code puts on an invoice or credit line, and the tax a credit note takes back. A posted document shows what it posted.

**Lookups.** A command a field looks its choices up with (`FieldType::Lookup`, or `x-field-type` lookup in a command's input) accepts `limit` beside the params the lookup names, as the generic lookup sends it; `party.get` also takes `q` (text in an address). A test calls every lookup in `/api/meta` that way.

### The MCP endpoint

`POST /mcp` speaks the Model Context Protocol, revision 2026-07-28, in which nothing is kept between requests: every request says which revision it speaks, and `server/discover` says what the server offers. Clients of the four revisions before it, which open with `initialize`, are answered too, each with what its revision knows. The bearer token is the one of the HTTP API.

- **Tools.** Every command is a tool, described from what the command declares: a title, its input schema, an output schema that its structured result conforms to, and the hints of the specification (read-only for a query, destructive for a command that reverses, cancels or deletes, idempotent for one that moves a record out of a state). A tool that writes also takes `preview` and `idempotency_key`. A tool the caller can never run is not listed. The list is paged.
- **Finding tools.** Two tools come first in the list so that an agent need not read the rest: `erpcraft_modules` says what each module holds, and `erpcraft_tools` returns the tools of one module or for one resource.
- **Resources** are reference material that is the same for every caller: the sections of this document on commands, errors, documents and policies (`erpcraft://guide/...`, served from this file, so there is one text), the policy points with their facts (`erpcraft://policies`), and what each module holds (`erpcraft://modules/{module}`). Records and documents are not resources: what a caller may read of them is decided per call, by the tools.
- **Prompts** are pieces of real work: entering a vendor invoice against an order, closing a period, explaining a refusal. Each names the tools it uses from the registry, and is not offered to a caller who could not run them.
- **Web pages.** A request with an `Origin` header is let in only from the server's own pages and from this machine, or exactly from the origins in `ERPCRAFT_MCP_ALLOWED_ORIGINS`. The first is judged by the `Host` header, which does not stop DNS rebinding; what does is that the endpoint takes a bearer token and no cookie. An installation reachable from browsers should set the list.

### Audit and history

The audit log is written only by the command executor and cannot be changed, even with direct database access. Each entry names the records the command touched, so every record has a history (`audit.history`): who ran which command on it and when, failed attempts included. Whoever may read a record may read its history; the inputs of the commands are shown only with the permission `audit:read`, because an input can contain fields the reader is not allowed to see.

### Outbox

A module can register **subscribers** that react to committed changes: an integration, a notification, a projection. A worker in the server hands each event to every subscriber that wants it.

- Delivery is at least once. A subscriber that succeeded is not called again when another one fails and the event is retried, except if the server stops at the wrong moment; handlers must tolerate a repeat.
- A failed delivery is retried after 10 seconds, then with a doubling delay up to an hour, without limit. `outbox.list` shows failing events and their last error.
- There is no ordering guarantee: a failing event does not hold back the ones behind it.
- Several servers can run the worker at once; each event is taken by one of them.

Delivered events are deleted after 30 days and idempotency keys after 24 hours. The audit log and the ledgers are never cleaned.

**Webhooks** carry events to the outside. The `webhooks` module is one such subscriber: for every event it sends a POST to each active webhook that subscribes to the event's topic (a command name, or a prefix such as `purchase_order.*`; no topics means all). The body is `{id, topic, created_at, payload}`, exactly what the outbox holds, so the event of a command that handles secrets says only which command ran and who ran it. Each request carries `X-Erpcraft-Event`, `X-Erpcraft-Delivery` (the event id, the same on every retry, so a receiver can drop repeats) and `X-Erpcraft-Signature`: `sha256=` and the hex HMAC-SHA256 of the body under the webhook's secret.

- Only a 2xx answer within 10 seconds counts. Anything else fails the event, which the outbox retries as above; redirects are not followed. The module notes per event and webhook what arrived, so a retry goes only to the webhooks that have not had the event. `webhook.deliveries` and the webhook record show the last failure.
- A webhook can be limited to one company. The company of an event is taken from its payload (`output.company_id`, else `input.company_id`); an event that names none goes only to webhooks without that limit.
- A webhook must point to a public address over https. Public is an allow-list: the global unicast space of each family (IPv4 1.0.0.0 to 223.255.255.255, IPv6 `2000::/3`) less the blocks the special-purpose registries mark as not globally reachable. An IPv6 address that carries an IPv4 address (IPv4-mapped, IPv4-compatible, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) is judged by that address; Teredo is refused whole. This is checked when the webhook is saved and again when a request is sent, by the name lookup the HTTP client itself uses. The refusal is one sentence whether the address is private, the name leads to a private address or the name does not exist, and names no address, so that whoever may save a webhook cannot map the names of the internal network; the detail goes to the server's log. `ERPCRAFT_WEBHOOKS_ALLOW_PRIVATE=1` lifts this for development, and with it http to localhost works.
- Webhooks are managed with commands of their own (`webhook.create`, `webhook.update`, `webhook.set_secret`, `webhook.delete`), marked sensitive, not with the generic entity commands, so that neither the secret nor the URL reaches the audit log or the outbox. The secret is returned once, when it is created or generated. It is stored as given, because it must sign: whoever can read the database can read it.

### Documents and postings

A **document** is a business record with a workflow that its module defines: states, which states lock the content, and the allowed transitions. A journal entry goes draft → posted → reversed. A purchase order will have more states and stay open across several receipts.

The body of a document is accepted on write exactly as it is returned on read. Fields the system sets (a line's `line_no`, `qty_received` on an order line, the value of a receipt line) are declared read-only in the type's description and ignored on input, never trusted. A line sent back with its `id` keeps that id when the draft is saved, whatever its position, so that what refers to the line stays valid; a line without an id, or with one the document does not have, is new.

A **posting** is the immutable record that a document changed a ledger. A document can post many times. A posting has no status and is never edited; it is undone by a second posting that reverses it, and it can be reversed at most once.

A document is read with its postings, and each posting with the entries it wrote, by ledger: `postings[*].entries.gl`, `.stock`, `.open_items`, `.tax`. Each ledger supplies its own (`Ledger::entries`) and applies its own permissions: reading a document does not give the right to read a ledger, so a ledger's entries are left out for a reader who may not read them, and fields withheld on its entries are withheld here. Because a preview runs the command and reads the document before rolling back, the preview of a posting shows the entries it would write. A ledger names the tables it writes (`Ledger::entry_tables`); one statement asks which of them hold rows under each posting, and a ledger is asked for its entries only where it wrote some. The tables are what was written, so no module has to remember to mark anything; a ledger that names no tables is asked for every posting.

A command that returns a document returns all of this by default. A caller that only needs the outcome, such as an importer, asks for the header and summary alone: `?view=header` over HTTP, which leaves out `body`, `postings` and `links`, and the argument `view: "header"` over MCP, offered on every tool that returns a document, where `body` is null and `postings` and `links` are empty so that the result still fits the tool's output schema. The queries for the rest are not run. With an idempotency key, the view is part of what a retry must repeat.

The kernel loads a document's body once per change: to work out the summary (`DocumentHandler::summary_of` gets the body just loaded, and reads lines from it), and the view at the end of the command shows that same body when the document has not changed since, as known by its version. A handler that implements only `summary` still works; it reads what it needs itself.

Ledger entries hang off a posting. Each entry records the document line that caused it and the command that created its posting. Three dates are kept apart: when the event happened (`doc_date`), its accounting date (`posting_date`), and when the system recorded it (`created_at`).

A document type can declare a **summary**: the few figures that say what a document is without opening it, such as the vendor and the total of an order, or net, tax and gross of an invoice. The type's handler works them out (`DocumentHandler::summary`) and the kernel stores them with the header whenever a body is saved or the document changes state, so that lists return them, sort by them (`summary.total_net`) and filter by them without reading a body, and the document itself shows the same figures. Amounts are worked out in Rust as the posting works them out, line by line with the same rounding, so that the total shown on a draft is the total that will be posted; a figure that is not known yet, such as the cost of a delivery before the stock ledger has valued it, is null. A document saved before its type had a summary gets one from the server's background work after it starts, a batch at a time, or from `document.refresh_summaries` (granted for all companies; it takes a `doc_type` and a `limit`, at most 1000, and says how many it refreshed and how many remain). A batch skips documents another transaction holds rather than waiting for them.

A document and each of its postings carry the name of the user who created them (`created_by_name`). Whoever may read a document may see those names, as with a record's history; there is no separate right to read users.

`search.records` finds records and documents of every kind in one call, a few per entity and document type. It runs the lists' own queries, so it finds exactly what the lists would show the caller: rows out of reach are not found, and a withheld field is neither searched nor shown. Its cost is bounded: at least two characters, at most ten matches per kind, fifty in all.

### Documents that follow from each other

A document can be linked to the document it follows from: a receipt to its purchase order, an invoice to that order. The link is kept by the kernel and shown on both documents, to readers who may read the other one.

Sales orders work the same way, with deliveries and invoices. A purchase order shows the pattern for a document that stays open while others are posted against it. The order itself posts nothing. Each receipt and each invoice is its own document with its own posting, and locks the order before it does anything. That lock is what stops two receipts from together receiving more than the company accepts (by default, more than was ordered; see Policies). How far each order line has got is kept beside the order, because it changes while the order's content is locked. An order closes by itself when everything on it is received and invoiced, can be closed short by a person, and reopens if a reversal leaves it with goods received and not invoiced.

The next document can be drafted from the one it follows: `purchase_order.receive` and `purchase_order.invoice`, `sales_order.deliver` and `sales_order.invoice` create a draft with a line for everything still to come, linked to its order; `purchase_order.return` and `sales_order.return` a return of everything received or delivered and not yet returned; `vendor_invoice.credit` and `sales_invoice.credit` a credit note for what was returned and not yet credited on the invoice's lines; and `payment.draft` one that settles open items in full.

### Returns and credit notes

Goods that go back are a business event of their own, dated when it happens, not a reversal: a reversal undoes a mistake. A **purchase return** sends goods received on an order back to the vendor, a **vendor credit note** reduces what is owed for a posted invoice; a **sales return** brings goods delivered on an order back, a **sales credit note** reduces what the customer owes. Each is a document with its own posting, linked to the order or the invoice, and reversible while nothing depends on it.

- A purchase return takes the goods out of stock at the moving average, as every issue does, and takes out of goods received not invoiced (GRNI) what they were received for: the average received value of the order line. The two differ only where the item's cost moved since the receipt; the difference goes to purchase price variance, as an invoice's difference from its receipt does. Stating the issue's value was not an option, because the stock ledger values every issue itself.
- A vendor credit note puts back into GRNI what the credited goods were invoiced at (the average cleared value of the line), debits payables by what is credited, sends the difference to purchase price variance, and takes the tax back. So GRNI holds goods received and not invoiced, less goods returned and not credited, and clears when both sides are level. Whichever document makes them level (a return, a credit, an invoice or a replacement receipt) takes the value that is left, so nothing stays behind to the cent; the database checks this per order line.
- A sales return brings the goods back at the cost they left for: the average cost of what was delivered on the order line and has not come back, the last of it taking what is left. Cost of goods sold is taken back by exactly that. Goods that come back onto a level below zero are handled like any receipt: the variance goes to `stock_variance`.
- A sales credit note takes back revenue and the tax charged, and credits receivables.
- Only goods received (or delivered) on the order and not yet returned can go back: an invariant, because more would leave the order owing goods that never arrived and GRNI or cost of sales wrong. A credit note line credits a line of its invoice, never more than the invoice charged on it. The part of a line covered by goods returned and not yet credited counts on the order; any other part is a credit of price only (an allowance, a discount), which goes to purchase price variance or takes back revenue alone, and is a judgement: `vendor_credit_note.without_return` and `sales_credit_note.without_return`, refused by default.
- An order line keeps what was received (delivered) and invoiced in all, and what was returned and credited apart; what the order shows as received and invoiced is net. A return can be made against an open or a closed order. A closed order stays closed after a return unless the company wants it open again for replacements (`purchase_order.reopen_on_return`, `sales_order.reopen_on_return`); replacements received against it are counted like any receipt. A return or credit note on an order that is open does not change its state; one that leaves goods returned and not credited keeps the order from closing.
- A credit note takes tax back at the code, direction and rate the invoice recorded for that line, whatever the code says now, as negative base and amount dated in the credit note's period, so a period already reported does not change. The tax ledger refuses to credit more of an entry than it charged, in base or in tax, and the last of a line's base takes the last of its tax. The policy `tax_code.use` is not asked: a credit must be able to undo what an invoice charged at a code since retired.
- A credit note opens an item below zero (see open items) for the vendor or customer. A payment settles it with that party's invoices, netting them; `payment.apply_credit` applies it to one invoice without money moving.
- An invoice that a posted credit note credits cannot be reversed, nor a return whose goods were credited; reverse the credit note first. A credit note that a payment settled or applied cannot be reversed; reverse the payment first. They post nothing; the draft is checked, changed and posted like one entered by hand. A command that creates a document says so in its description (`creates`), so an interface goes to the new document.

**Credits without an invoice.** A customer credit (`sales_credit`) credits a customer for something no single invoice stands for: a rebate over a year's invoices, goodwill, a price agreed after the fact. Its lines are charges or accounts with a quantity, a price and a tax code (the tax rules propose one). Posting takes back revenue (the line's account, or its charge's revenue, else the sales revenue account), and the tax at each code in the credit's period, and leaves the customer an open item below zero, applied to its invoices like a credit note's. With no invoice entry to credit, the tax ledger records the tax taken back as entries of their own below zero, marked `adjustment` (`erpcraft_tax::as_credit`); a trigger allows negative amounts only for those, reversals and credits of an entry. The reversal of an adjustment is marked `adjustment` too (tax migration 11), so whatever picks adjustments out sees a credit and its reversal net to nothing. The policy `sales_credit.without_invoice` (facts: total, currency, customer code; allowed by default) is asked first, so a company can have such credits approved or limited. A vendor credit (`vendor_credit`, policy `vendor_credit.without_invoice`) is the same from a vendor (a volume rebate): it takes the amount off each line's account (or its charge's `charge_expense` account) and the tax off the account it was reclaimed on, and leaves a credit with the vendor; tax the company accounts for itself is taken back from both tax accounts and is not part of the credit.

### Ledgers own their rules

The kernel coordinates transactions, permissions, audit and reversal. Each ledger enforces its own invariants. The general ledger's are database triggers, so they hold for every module and for raw SQL:

- a posting's entries balance in the company's accounting currency, checked at commit;
- the posting date falls in an open fiscal period;
- a posting cannot be dated in a closed fiscal period, whichever ledgers it writes to. This one is a trigger on the kernel's `posting` table that the general ledger module puts there, because fiscal periods are the general ledger's and a closed period is closed for every ledger. A date in no period at all is let through (such a posting cannot have general ledger entries);
- the dates of a fiscal period cannot change, and the period cannot be deleted, while it is closed or once anything is posted inside it;
- the account belongs to the company, is active, and is not a group account;
- amounts fit the currency's decimals, and the accounting amount equals the transaction amount times the captured rate;
- entries and postings cannot be updated, deleted or truncated.

The general ledger also says which account a company posts to for a purpose. An **account rule** names the account for a purpose such as `inventory`, either as the company's default or for one record of another module: an item, a warehouse. A module that posts a value asks `account_for` with what the posting is about, most specific first, and gets the account of the first rule that applies. So every module that moves stock (receipts, deliveries, adjustments, transfers, production) lands on the same account without knowing the others, and the inventory accounts together are worth what the stock ledger says is on hand. The ledger does not know what an item or a warehouse is; it only matches the scope it is given.

**Dimensions** say what an entry is about besides its account: the site, the cost center, the project (`crates/erpcraft-gl/src/dimensions.rs`, gl migration 10). The chart stays one chart; no account code carries a site.

- A company defines its dimensions (`dimension`: code, name) and their values (`dimension_value`). Codes never change, since sets are labelled with them, and hold no `:` or `,`. An inactive dimension takes no defaults; an inactive value cannot be stated, and a default pointing to one gives nothing.
- Every `gl_entry` points to a **dimension set** (`dimension_set_id`): one value for some of the company's dimensions. A set is immutable and kept once per combination (`dimension_set_of(company, values)` finds or creates it; two transactions creating the same one wait on the unique key and get the same id), with a `label` such as `COSTCENTER:ASSY, SITE:OHIO`. No values is the empty set, `NULL`; entries posted before dimensions existed have none. The set must be the entry's company's (a foreign key).
- **Which values a line gets.** `GlLine` carries `scopes`, what the line is about, most specific first, and `dimensions`: `Defaults`, `Stated(values)` or `Exact(set)`. For each active dimension the posting path takes the stated value, else the default that **dimension rules** give (`dimension_rule`: a value, for a scope or for the company), matched like account rules by `dimension_for(conn, company, scopes)`: the first scope with a rule, then the line's account, then the company's rule without a scope. Modules give the scopes in the order warehouse (and the locations above it, then its site), item, charge, then the party (`customer`, `vendor`) or the asset and its class; `erpcraft_gl::add_scopes` adds those of each document line and the document's own, and `erpcraft_stock::line_scopes` / `locations` give a movement's places. A journal entry line states values (`dimension_value_ids`); the company's other dimensions take their defaults. `Exact` carries on a set already in the books unchanged, as the year-end close does.
- **Which combinations are allowed** is the policy `gl.dimensions`, asked for every line a posting writes with what the line ends up with (facts `doc_type`, `account_code`, `account_type`, and the lists `dimensions`, the codes that have a value, and `values`, as `DIMENSION:VALUE`): a cost center required on expenses is a refuse rule when `facts.account_type == 'expense' && !('COSTCENTER' in facts.dimensions)`, a blocked combination one when `'SITE:TEXAS' in facts.values && 'COSTCENTER:SALES' in facts.values`. By default everything is allowed. A refusal names the line, the account and the values. It is not asked for a reversal or for `Exact` lines, which carry on what the books already hold: the closing entries of a year-end close are exempt on purpose, since they only carry each set's result to equity and a rule added since must not keep a year from closing.
- **A reversal copies the set** of each entry exactly.
- **Reports.** `gl.trial_balance`, `gl.income_statement`, `gl.balance_sheet` and `gl.account_ledger` take `dimension_value_ids` (count only entries that have, for each dimension among the values, one of them: two sites are either, a site and a cost center both) and `group_by_dimension_id` (a row per account and value of that dimension, null for entries without one, with the totals of each value in `groups`). The account ledger shows each entry's values and totals the range per value. Unknown values are refused, since they would narrow nothing. A posting balances, a dimension need not: see Known gaps.
- **The year-end close keeps the sets.** It closes each income and expense account per dimension set and puts each set's result on the retained earnings account under the same set, so a site's balance sheet carries its own result after the close.

The stock ledger's, also triggers:

- stock on hand never goes below zero, per item and warehouse, unless the company's policy allows it (see Policies, `stock.negative`). The ledger then lets an issue through only if its entry names an active policy rule of that point that allows, for that company, and carries the facts the rule was asked with; the ledger checks those facts against the level it has locked (on hand, issuing, short by, item and warehouse) and copies the rule's condition onto the entry. The rule, the facts and the condition stay on the entry, so an auditor can ask the condition again. Goods that are not on hand leave at the last cost known for the item in that warehouse, an estimate, and the level carries that estimate as a negative value. When goods arrive on a level below zero they first cover what is missing; the difference between their real cost and the estimate is a variance, which is not stock value, and the rest comes into stock at its real cost;
- valuation is moving average: a receipt comes in at the cost the caller states, an issue goes out at the average cost of what is on hand. The ledger works out the value of an issue; the caller cannot state it;
- the last of the stock takes the last of the value with it, so rounding never leaves value on an empty shelf;
- a reversal takes back exactly the quantity, value and variance of the original entry, and is refused if the stock has since moved on. Taking back a receipt that arrived on a level below zero may leave the level as far below zero as it stood before that receipt, not further;
- quantity and value of a level always point the same way: never a positive quantity with a negative value or the reverse, and an empty shelf is worth nothing;
- the level on hand changes only through entries.

Open items are the third ledger: the detail behind the payables and receivables accounts. An invoice opens an item under its posting; a payment settles items under its own. Its rules, also triggers:

- an item is never settled for more than its amount;
- an item is a debt, above zero, or a credit, below zero: a credit note, or money paid on account. A settlement runs the way of its item, so what is settled of a credit is below zero too;
- reversing the posting that opened an item calls the item off, which is refused once any of it was paid;
- reversing a payment takes back exactly its settlements;
- items and settlements are never edited.

Because purchasing and sales only open items and payments only settle them, the three modules do not know each other. A payment can settle an item whatever module opened it.

A payment settles the debts and credits of one party together: an allocation to a credit is below zero, and the payment comes to the debts less the credits. A payment that comes to nothing needs no bank account and moves no money; `payment.apply_credit` posts one to apply a credit to a debt. A payment can also carry money beyond its allocations (`on_account`, with the party and the payables or receivables account when nothing is allocated): it opens a credit of the party, applied later like a credit note. A payment that comes to less than zero is money coming back, a refund.

Tax is the fourth: a record of the tax on each posting, which a tax return is built from. A tax code is a rate; a company names the account for tax it collects and the account for tax vendors charge it (an asset where it can be reclaimed, as with VAT; an expense where it cannot, as with US sales tax). An invoice asks what the tax on a line is, posts it to the general ledger, and records it. Tax is worked out and rounded per line. A reversal is recorded in the period it is posted in, so a period already reported does not change. Which code applies where is data: tax rules (below), and by the place the goods go, areas, registrations and exemption certificates (see [Tax by destination](#tax-by-destination)). The form of a return is left to country modules.

**Tax rules.** A sales or vendor invoice line that names no tax code starts with what the company's tax rules (`tax_rule`, per company) propose, when the draft is saved: the rule for the invoice's customer or vendor (an exempt buyer, a buyer under the reverse charge), else the rule for the line's item, else the charge's own code, else the company's default (the rule without a scope). A code the line gives is kept, and a line can be changed to any code before posting. The rules are matched like account rules: the tax module does not know what a customer or an item is.

**Tax the buyer accounts for.** A code marked `self_assessed` is tax the buyer owes rather than the seller: the EU reverse charge, an intra-Community acquisition, US use tax. On a purchase the vendor charges none and is owed the net amount. The company owes the tax and, where it may, reclaims it: `erpcraft_tax::quote` gives two taxes per component, `paid` on the paid account (an asset where it is reclaimed, an expense for use tax that is not) and `collected` on the collected account, of the same amount. Both are posted (`Tax::debit_credit`) and recorded as entries marked `self_assessed`, so the tax report shows the tax due and the tax reclaimed and still equals the tax accounts. `Tax::total`, what is owed with an invoice, leaves them out, and so does `posted_value`. A credit note takes both back from the accounts they were posted to, and an early-payment discount takes neither back. On a sale the seller charges none: the entry records the base with no tax, and the e-invoice writes the line at 0 % in the code's VAT category (below). Being accounted for by the buyer does not say which: a domestic reverse charge (AE), an intra-Community supply (K) and an export (G) all charge nothing, so such a code must name its category before an e-invoice is written.

**The VAT category of a code.** What a sale under a code is, in the terms of EN 16931 (UNTDID 5305 as the standard restricts it), is a property of the code (tax migration 10): `vat_category` (`S` standard rate, `Z` zero rated, `E` exempt, `AE` reverse charge, `K` intra-Community supply, `G` export outside the EU, `O` not subject to VAT, `L` and `M` for the Canary Islands and Ceuta and Melilla), with `exemption_reason_code` (BT-121, from the VATEX list) and `exemption_reason` (BT-120). Only `E`, `AE`, `K`, `G` and `O` may have a reason, as the standard says. A code that does not state its category is standard rated when the seller charges a rate above 0 %; any other must say. The e-invoice writes it, and an incoming invoice's lines are matched to the codes by it. The migration derived it for the codes there were: a code the buyer accounts for became `AE` with VATEX-EU-AE (what the e-invoice wrote for it before), a rate above zero `S`, a rate of zero `E` where its code or name says exempt (with the name as the reason) and `Z` otherwise; a group has none. E-invoicing's own `einvoice_tax_category`, where it had a row, replaced what was derived and was dropped (einvoice migration 4). The category is the code's meaning, not a check of the sale: nothing compares a `K` buyer's country with the seller's, or a `G` buyer's with the EU.

A line can carry more than one tax. A **tax group** is a tax code made of component codes (`tax_code_component`, in order): GST plus British Columbia PST, or a US state plus a county. Each component is a plain code with its own rate and, per company, its own collected and paid accounts, so each authority's tax is owed on its own account. A code without components is a group of one, exactly as before. Tax is worked out and rounded per component per line; the line's tax is their sum, and a draft's summary adds them the same way, so what it shows is what is posted. A component marked `compound` is charged on the net amount plus the taxes of the components before it (as Quebec QST was until 2012, and some US and Canadian taxes still are); otherwise on the net amount alone. Each component is one tax entry, which names the group (`group_code_id`), so `tax.report` shows each authority's code on its own row and still equals the tax accounts. A credit note takes back each component's entry, a compounding one on what is credited plus the taxes taken back before it, and the last of an entry's base takes the last of its tax. A group marked `self_assessed` makes each of its components so (a reverse charge set up as a group of the ordinary rates is charged by no one and assessed by the company), and a component marked so stays so in a group that is not. Groups are one level deep, and a group has no accounts of its own; its rate is the sum of its parts, for people to read, and is not charged. The policy `tax_code.use` is asked for the group and for each component, so an inactive component refuses the line by default.

Whether a tax paid can be claimed back is said by its paid account, not by a flag: an asset where it is reclaimed (VAT, GST, Quebec QST as an input tax refund), an expense where it is not (British Columbia, Saskatchewan and Manitoba PST, US sales tax).

Decisions in the stock ledger that are choices, not necessities, and can be revisited:

- Moving average, not FIFO or standard cost. It needs no cost layers and suits interchangeable goods.
- Stock below zero is an estimate until the goods arrive. An issue of 10 with 4 on hand worth 12.00 and a last cost of 3.00 leaves at 12.00 + 6 × 3.00 = 30.00, and the level stands at -6, worth -18.00. A receipt of 10 at 3.50 then covers the 6 with goods that cost 21.00: 3.00 of variance. The other 4 come in at 14.00, so the level is 4 worth 14.00, and the receipt's 35.00 is 32.00 of stock value plus 3.00 of variance. The module that brought the goods in posts the variance to the account for the purpose `stock_variance`, which is asked for only when there is one. The last cost is the unit cost of the most recent receipt into that warehouse that has not been taken back, in the order the ledger recorded them: taking back that receipt puts back the cost of the receipt before it. Where nothing was ever received, the missing goods leave at nothing and their whole cost becomes variance when they arrive.
- `stock.on_hand` lists a level below zero with its negative quantity and value, so its total equals the inventory accounts at every moment.
- Entries are valued when they are recorded. A back-dated entry does not revalue what was recorded after it.
- Items are shared by all companies; warehouses belong to one.

**Sites and the location tree** (stock migration 8). A **site** (`site`: company, code, name) is a place where a company keeps goods: a plant, a distribution center. A warehouse names its site (`site_id`) and, optionally, the warehouse it is part of (`parent_id`): a site holds warehouses, a warehouse holds locations or bins, and each is a warehouse row with stock of its own. The tree lives in the stock ledger's crate because warehouses do; the kernel and the general ledger know nothing of it.

- A location is at the site of the warehouse it is part of: it takes it when it names none, a different one is refused, and moving a warehouse to another site moves its locations with it (triggers). A location is never part of itself, however far up, and never of another company's warehouse; changes to a company's tree take an advisory lock per company, so two changes cannot together make a loop.
- **What a warehouse is does not change under its stock** (stock migration 9, an invariant): while a warehouse, or a location inside it, holds stock, its `transit` flag, its site and its parent are refused, since the value posted for that stock would stay on the account and with the dimension values of its old place. Moving the goods out (a transfer) comes first. This was chosen over posting a reclass between dimension sets when a warehouse moves. A dimension rule, by contrast, can change at any time and applies to what is posted after it: value already on hand keeps the values it was posted with (see Known gaps).
- **Where money is follows where goods are.** `erpcraft_stock::locations` gives a movement's places for the general ledger's defaults, most specific first: the warehouse, each warehouse it is part of upwards, its site (scope `site`), then the item. A site's default value of the SITE dimension is the dimension rule for the site (`scope_type` `site`); a rule for a warehouse reaches the locations inside it and comes before the site's. Every module that moves stock passes these places, so the inventory accounts of one site, filtered by its value, equal the stock value at that site (`stock.on_hand` takes `site_id`, and `warehouse_id` with the locations inside it). A one-step transfer between warehouses whose inventory takes other dimension values moves the value between them in the general ledger even on one account.
- **Access by site.** A stock entry keeps the site of its warehouse when it is recorded (`stock_entry.site_id`, set by a trigger), so permission rules read `record.site_id in user.sites` on warehouses and stock entries as they read `user.warehouses`.
- A warehouse flagged `transit` holds goods between the two steps of a transfer between sites (see Transfers in two steps).

**Transfers in two steps** (module `inventory`, migration 4, `modules/inventory/src/transit.rs`). Goods between sites travel.

- A `stock_transfer` that names a transit warehouse (`transit_warehouse_id`, a warehouse flagged `transit`) is **shipped** when posted: the goods leave the source at their average cost and come into the transit warehouse with exactly that value, and the transfer is `in_transit`. Goods in transit are stock like any other, carried on the account for the purpose `inventory_in_transit` (an account rule, by item or warehouse, else the company's; required), so the general ledger equals the stock ledger on every account while the truck is on the road. A transit warehouse belongs to a site like any warehouse; at the destination site its goods count there in the general ledger's site dimension. One per destination site is the simple setup; a company may keep one per pair of sites.
- A **transfer receipt** (`stock_transfer_receipt`, `TR`) takes what arrived from the transit warehouse into the destination, at the transit warehouse's average cost, and the general ledger moves it from the in-transit account to the destination's inventory account. `stock_transfer.receive` drafts one for everything still on its way; receipts may be partial, and no line receives more than is on its way (an invariant, kept per line in `stock_transfer_progress` beside the locked transfer, under the transfer's row lock). The transfer is `received` once everything arrived. A transfer line shows `qty_received`.
- **Reversals.** A receipt is reversed while its goods are still at the destination; they are on their way again and a received transfer is in transit again. A shipped transfer is reversed only while nothing of it has been received: receipts first.
- **Closing short** (inventory migration 5). Goods that will not arrive are written off with `stock_transfer.close_short`: what is still on its way leaves the transit warehouse at its average cost there and goes to the account rule `transit_loss` (by item or warehouse, else the company's); the transfer is `closed`, counts as coming in no more, takes no receipts and is not reversed. The policy `stock_transfer.close_short` is asked first (facts `qty_left`, `value_left`, `lines`; allowed by default), so a company can ask for approval of large losses. A line shows `qty_written_off`.
- **Rules by site.** A transfer's summary, and a transfer receipt's, carry the sites it moves between (`from_site_id`, `to_site_id`), and permission rules on a document may name its summary's fields (`record.summary.<field>`), so `{ "allow": "stock_transfer:post", "where": "record.summary.from_site_id in user.sites && record.summary.to_site_id in user.sites" }` keeps a user to their sites.
- **What is on its way.** `stock_transfer.in_transit` (report "Goods in transit") lists every shipped line not received in full, with shipped, received, left and what is left is worth at the transit warehouse's average cost; `stock.on_hand` with `transit` true gives the levels. Planning (`stock.availability`, so also the suggestions) counts goods in transit as coming in at the destination (`in_transit`, part of `projected`), through `erpcraft_inventory::in_transit`, and leaves the transit warehouses' own stock out.
- Goods in a transit warehouse come and go only with transfers and adjustments: the stock ledger refuses any other movement there (`erpcraft_stock::post` by its context), and a transfer may not name a transit warehouse as its source or destination.
- A **transfer within one site** stays one step. One between two sites in one step asks the policy `stock_transfer.between_sites` (facts: the two sites' and warehouses' codes), which refuses by default; the general ledger then still moves the value between the sites' dimension values.
- The stock ledger does not check fiscal periods itself. A posting dated in a closed period is refused for every ledger by the general ledger's guard on postings; a stock-only posting dated where the company has no period at all is allowed.

**Units of measure** (stock migration 12, sales and purchasing migration 15, `crates/erpcraft-stock/src/units.rs`). An item is kept in one unit and bought and sold in others: steel kept in kilograms and bought by the tonne, bolts kept each and sold by the box of 100.

- **The stock unit** is the item's `uom`, as before, and fixed once anything was recorded in it. The stock ledger, lots, counts, reservations, planning and bills of materials know only the stock unit.
- **Other units** (`item_uom`, per item, shared by companies like items): a code, its `factor` (how many stock units one of it is: an exact decimal above zero, `1000` for a tonne of kilograms, `0.5` for a half), and whether it may be used to buy (`purchase`) and to sell (`sales`). A code is not the stock unit's, and is unique per item.
- **A line in any allowed unit.** A purchase or sales order line names its `uom` (omitted: the stock unit); a unit that is not the item's, or not allowed for the purpose, is refused. The line keeps the factor it was saved with (`factor`), so changing an item's unit later does not change what an order says. Its quantity and its `unit_price` are per that unit; its amounts are quantity times price as before.
- **What follows the order stays in the order's unit**: receipts, deliveries, returns, invoices and credit notes take quantities in the order line's unit, and what was received, delivered and invoiced is counted in it. Only the stock ledger converts: a movement is the line's quantity times its factor, which must come out at the stock ledger's six places exactly or the line is refused (never rounded). A receipt's cost is the line's quantity times its price, whatever the unit. The lots a line names are in the stock unit and add up to its converted quantity.
- **Planning and reservations** count open orders in the stock unit (`open_demand`, `open_supply`, drafts, reservations), and the last price paid that planning proposes is per stock unit (the line's price divided by its factor). Planning drafts purchase orders in the stock unit.
- **Prices per unit.** A line's price is per its own unit. Price lists keep prices, and quantity breaks, per stock unit: a line in another unit is looked up by its quantity in stock units and proposed the listed price times its factor (`Proposal::per`), which is what is kept for the price check at approval; the last price paid is divided by its line's factor first.
- **EDI.** A partner's unit code maps to one of ours (`edi_uom_xref`); when that is another unit of the item (`item_uom`), its factor is how many stock units one of the partner's is, where before only the stock unit itself (factor one) or an item number's own `units_per` matched. The order is still drafted in the stock unit.
- **Intercompany.** A mirrored purchase order is bought in the unit the order was sold in (items and their units are shared by companies), so a unit sold but not bought refuses the mirror.
- **Documents** print and e-invoices write each line's own unit.

**Physical inventory and cycle counts** (inventory migration 6, stock migration 11, `modules/inventory/src/count.rs`). The books say what should be on the shelf; a count says what is.

- **A count** (`stock_count`, `PC-`) is a document per warehouse, with the locations inside it, narrowed for a cycle count to an ABC class (`abc_class`) and to items (`item_ids`). `blind` hides the book quantity from the count sheet until it is posted, so counters write what they see.
- **Starting it freezes the book.** `stock_count.start` locks the levels it covers, takes the ledger's order number at that moment (`cut_off_seq`, the `seq` of stock entries) and writes a line per item, warehouse and lot (or serial number) on hand there, with its **book quantity at the cut-off**. Every book quantity is read from the ledger by `seq` (`erpcraft_stock::book_at`), so it is exact whatever moves later. A line may be added while counting for goods found that the book did not have (book quantity at the cut-off, zero or not).
- **Movements during the count: counted at the cut-off, adjusted by what moved since.** The count says what was on the shelf at the cut-off, and the difference is counted less book at the cut-off; what moved since is in the ledger already and stays there, so the adjustment lands on today's level. Each line shows `moved_since`. Whether goods may move at all while their level is being counted is the company's policy: the stock ledger asks `stock.count_movement` for every movement of a level under a count in progress (`stock_count_hold`, kept by the stock crate; facts `context`, `item_code`, `warehouse_code`, `count`), allowed by default. A company that freezes its warehouse during the count refuses it; one that keeps shipping counts at the cut-off. The count itself, and its adjustment, are not asked.
- **Counting, and recounting what is too far off.** Lines take `counted_qty`. `stock_count.review` asks the policy `stock_count.tolerance` for every counted line that differs from the book (facts `book_qty`, `counted_qty`, `difference`, `difference_percent`, `value_difference` at the level's average cost, `item_code`, `abc_class`; allowed by default): a line it refuses is marked `recount`, and takes a `recount_qty`, which then stands. Posting asks the same and refuses while a refused line has no recount; a line that was recounted is not asked again.
- **Posting the differences.** `stock_count.post` turns every difference into a stock adjustment (`stock_adjustment`, posted by `stock_adjustment.post`, linked to the count), one per offset account: the account rule `inventory_count_variance` (by item or warehouse, else the company's; required when anything differs). Goods found come in at the level's average cost, else its last cost, else nothing; goods missing go out at the average, as any issue. Lots counted that the book did not have are made. The count is then `posted`, its holds released; `stock_count.cancel` releases them without posting. A count's lines are never more than one per item, warehouse and lot.
- **ABC classification** (`stock.abc_classify`): per company, items ranked by the value on hand (`basis` `value`) or by the value issued over a period (`movement`), and classed A while the running share is within `a_share` (80 % by default), B within `b_share` (95 %), C after; items without value are C. The result is kept in `item_abc` (company, item, class, basis, when), which a count and the schedule read; running it again replaces it.
- **Cycle-count schedule.** `cycle_count_rule` (company, class, `every_days`) says how often each class is counted. `stock_count.propose` (company, warehouse, date) lists the items on hand in the warehouse that are due, never counted first, then by how long it is since their last posted count, with `limit`; with `draft` it drafts the count for them. Nothing is counted by itself.

**Lots and serial numbers** (stock migration 10, `crates/erpcraft-stock/src/lots.rs`). A manufacturer must say which batch of an ingredient went into which batch of a product, and which customers got it, when a recall comes.

- **Tracking is a property of the item** (`item.tracking`: `none`, the default, `lot` or `serial`). A serial number is a lot that is never more than one unit. It changes only while the item has no stock anywhere (an invariant), so the lots on hand always account for all of it.
- **A lot** (`stock_lot`, per company and item, code unique within them) has an optional `expiry_date` and `manufactured_date` and free `attributes` (JSON: a supplier's lot number, a grade, a certificate). Its code and item never change; its dates and attributes may be corrected. Lots are per company, like warehouses: the same supplier batch received by two companies is two lots with the same code. A lot is made when goods first come in under its code (a receipt, production output, an adjustment in); goods going out must name lots that exist.
- **The movement names its lots, the entry carries them.** A stock entry stays one per document line, valued as before; its lots are rows of `stock_entry_lot` (entry, lot, quantity), written by `erpcraft_stock::post` from `StockLine::lots`. Lots do not change costing: moving average stays per item and warehouse, every unit of an item in a warehouse is worth the same whatever its lot, and a lot has no value of its own. The ledger keeps **lot levels** (`stock_lot_level`: item, warehouse, lot, quantity), changed only by entry lots.
- **The invariants**, triggers like the rest of the ledger: an entry that moves a tracked item carries lots that add up to its quantity, every one the way the entry goes, of the entry's item and company; an entry of an untracked item, and a cost adjustment, carries none (checked at commit, so the entry and its lots are written in one transaction and never added to later); a lot level never goes below zero, so **a tracked item never goes below zero**, whatever the policy `stock.negative` allows; a serial number is on hand at most once in the company, one unit, in one warehouse, and moves one unit at a time; a reversal takes back exactly the lots of the entry it reverses, and an entry made before its item was tracked cannot be reversed once it is. Entry lots are never edited.
- **Documents name lots per line**: every stock line of a receipt, delivery, transfer and transfer receipt, adjustment, purchase and sales return has `lots`, a list of `{ lot, qty }` with, for goods coming in under a new lot, `expiry_date`, `manufactured_date` and `attributes`. They are kept in `stock_line_lot` (one table for every document type, guarded like the document's own lines) and checked when the document posts: a tracked item's line must name lots that add up to its quantity, an untracked one must name none, a serial is one unit, and goods going out name lots on hand. A document drafted from another carries its lots where they are known: a transfer receipt the lots still on their way, a return the lots its order line's deliveries or receipts moved and that have not come back; a sales return takes back only lots that went out on its order line. A production order is locked once released, so its lots are named when it is completed (`production_order.complete` with `components`, the lots consumed per component line, and `lots`, the lots made, with their dates); they are kept on the stock entries.
- **Which lot goes out is the company's choice, not the ledger's.** `stock.lot_proposal` proposes lots for a quantity of an item in a warehouse, first expiring first (FEFO, lots without an expiry date last) or first received first (FIFO); nothing is picked by itself. The policy `stock.lot_issue` is asked for each lot going out (facts: `context`, `item_code`, `lot`, `expired`, `days_to_expiry`, `first_expiring`, whether no lot on hand that has not expired expires sooner; allowed by default), so a company that ships nothing expired refuses `facts.expired`, and one that enforces FEFO refuses `!facts.first_expiring`.
- **Traceability** (`stock.trace`, report "Lot traceability"), read from the ledger with SQL: **forward** from a lot, every document that moved it (receipts, transfers, deliveries with their customers, returns), and through production, the lots of the products it went into, followed in turn; **backward** from a lot, where it came from (receipts with their vendors), and if it was made, the lots of the components consumed by the production order that made it, followed in turn. Production links components to products by order: every lot consumed under a production order went into every lot it made. Reversed movements are left out. `stock.lots` lists lot levels with their dates.
- **Outside the stock ledger**: printed documents show each line's lots (the delivery note in its own column, the generic template as `F-1 × 6, F-2 × 4`); the EDI 856 carries each item's lots from its delivery line: one lot in the LIN (`LT`) with its expiry date in a `DTM*036`, several as a `REF*LT` each, read back the same way. They are the delivery line's, not the carton's, since packing does not record which lot went into which carton.


### Company and currency

Every document, posting and entry belongs to exactly one company. Each company has one accounting currency. An entry stores the transaction currency and amount, the exchange rate captured at posting, and the resulting accounting amount. Amounts are exact decimals, sent as strings in JSON, rounded half away from zero to the currency's minor units; Rust and Postgres use the same rule.

**Buying and selling in other currencies.** A purchase or sales order has a `currency`, the accounting currency when none is given, fixed once the order is approved (its content is locked then). Its prices are in that currency, and so are the invoices and credit notes that follow it. A document in a foreign currency posts at its own rate: the rate it states (`fx_rate`), or else the rate on record for its date; once posted, `fx_rate` shows the rate it posted at. A stated rate is checked against the rate on record by the policy `fx.rate_differs` (by default any rate is accepted).

- **Stock is valued in the accounting currency.** A receipt converts the order price at the receipt's rate: that is what the goods come into stock for and what goods received not invoiced holds. Deliveries and returns move stock at its value and carry no rate.
- **An invoice posts at the invoice's rate.** Payables (receivables) and, for a sale, revenue are posted in the invoice's currency at that rate; tax is worked out in that currency, rounded to its decimals, line by line, and the tax account and the tax record hold its value in the accounting currency, so a return still equals the tax accounts. For a purchase, goods received not invoiced is cleared by what the goods were received for, and the difference from what they are invoiced at is purchase price variance, whether it comes from the price or from the rate: the goods cost what the invoice says in the accounting currency, and the variance is the correction of their cost, as it is for a price difference in the accounting currency. Separating the two would need the receipt's value in the order's currency kept per order line and gives no different total. Cost of goods sold stays what the stock ledger says.
- **A credit note posts at the rate of the invoice it credits**, so it takes back exactly what the invoice put in the books, tax included. An exchange difference arises only when money moves (or a credit is applied).
- **Open items keep both currencies.** An item holds what is owed in the document's currency (`currency`, `txn_amount`, `txn_settled`) beside its value in the accounting currency at the document's rate (`amount`, `settled`), which is what the control account holds. A payment settles items in their own currency; the ledger works out what each settlement takes off the item's value: its share at the item's own rate, and all that is left when it settles the last of the item, so a settled item leaves nothing in the control account (the database checks this). The payment relieves the control account by exactly those values and moves the bank account at the payment's rate; the difference is a **realized exchange gain or loss**, posted to the account the company names for `fx_gain` or `fx_loss` (or for both, `fx_difference`). Applying a credit to a debt in a foreign currency realizes the difference between their two rates the same way.
- **One currency per payment.** A payment settles items of one currency, and netting credits and debts of a party needs them in the same currency; mixed currencies are refused with a message that says to pay each currency apart. Converting between two foreign currencies in one payment is not built.
- **Bank accounts can hold a currency** (`account.currency`); a payment through such an account is in its currency, and one through an account without a currency is in the currency of what it pays. The ledger does not refuse an entry in another currency on an account that holds one; payments do.
- **Revaluation at a period end, reversed the next day.** An `fx_revaluation` document values, as of its date, every payable and receivable still open in a foreign currency at the rate on record for that day, and posts each item's difference from what it is carried at to its control account against unrealized exchange gain or loss (`fx_unrealized_gain`, `fx_unrealized_loss`, else `fx_gain` and `fx_loss`, else `fx_difference`). The open items ledger records the difference per item (`open_item_revaluation`), so an item's value on a day is its amount, less what was settled, plus the revaluations standing that day, and aging as of the period end equals the control accounts. `open_item.list` with `as_of` is that view of a past day: the items posted by then, what was open of each as the settlements dated by then left it (an item paid in part before and the rest after shows its balance that day, its parts too), and `carried` per item and `total_carried`, the open amount plus the revaluations standing that day, which is what the control accounts hold on that day. Without `as_of` it lists what is open now. The revaluation is reversed the day after its date: at once when that day's period is open, else with `fx_revaluation.reverse`. This is the usual revalue-and-reverse approach: once reversed the item is carried at its invoice's rate again and a payment realizes its whole difference against that, so the unrealized difference of the period end and the realized one of the payment never count the same movement twice. A payment dated after a revaluation that still stands is refused until it is reversed.
- Summaries show the document's currency. An invoice or credit note also shows `total_net_accounting`, `total_tax_accounting` and `total_gross_accounting`, what it posted in the accounting currency (null for a draft in another currency).

### Lines: discounts, charges, services and invoices without an order

A line of an order, invoice or credit note may carry a discount: a percent, an amount off the whole line, or both. Its net amount is its quantity times its price, rounded, less the percent discount (rounded) and the amount, each line on its own (`erpcraft_tax::line_net`), so that a document's total is the sum of its lines and the tax is worked out on each line's net amount. An invoice line takes its order line's discounts unless it gives its own, the amount in proportion to the quantity; a credit note line takes its invoice line's the same way. An invoice line records the net amount it posted, and credit notes are capped by it. Goods are received at the order line's net price.

A line is stock (an item and its warehouse), a **charge** (`charge`, shared by companies: freight, insurance, handling, a service, with the tax code its lines start with), or an **account** with a description. A line on an account may not be on an account another ledger keeps in step: a bank or cash account, payables, receivables, goods received not invoiced, a tax account or an inventory account (`erpcraft_gl::line_account_refusal`). On a sale a charge's revenue goes to the account rule `charge_revenue` for the charge, else the company's, else the sales revenue account; on a purchase to `charge_expense`. An order's line that is not stock counts as received or delivered in full: invoicing it completes it, and receipts, deliveries and returns refuse it. An invoice can carry charge and account lines of its own besides its order's lines.

An invoice without an order (rent, utilities, a service, a machine to capitalise) names its vendor or customer and currency and has only lines of its own. It opens an open item with payment terms like any invoice and can be credited line by line. A direct vendor invoice asks the policy `vendor_invoice.without_order` when it is posted (facts: total, currency, vendor code; allowed by default), since no approved order stands behind it. A machine bought this way is on its asset class's `asset_cost` account, and `asset.capitalise` takes the invoice line.

**Landed cost.** A charge marked `landed_cost` on a vendor invoice (freight on the goods, or a carrier's own invoice) is shared out over the goods of receipts: those the line names (`receipt_ids`), else every receipt of the invoice's order, by their value, their quantity or their weight (`allocate_by`; weight is the quantity times the item's `weight`, refused while an item has none), rounded per receipt line, the last taking what is left. Of what each item in each warehouse gets, the share of the goods still on hand raises their value through a **cost adjustment** in the stock ledger: an entry with no quantity, refused on a level with nothing on hand or one it would take below zero, reversed exactly with its posting. The inventory account is debited by the same amount, so it still equals stock value. The share of goods already gone (sold, used) is a cost of those goods: it goes to the account rule `landed_cost_variance` (by item, else the company's), or else to purchase price variance, where purchasing already puts every other difference in what goods cost; purchasing cannot tell whether the goods went to a customer or into production, so it does not post to a cost of goods sold account of its own. Under average costing the goods still on hand are taken to be the received ones as far as the level still holds that many.

### Payment terms, discounts and aging

Payment terms (`payment_terms`, shared by companies) say when an invoice is due: a number of days after its date, or after the end of its month, and optionally an early-payment discount (a percent, within a number of days counted the same way). A vendor or customer names its usual terms; an order takes them from its party and an invoice from its order, each able to name others. When an invoice posts, its open item gets its due date and, if the terms give one, the last day and the amount of its discount in the item's currency. A credit note is due on its own date, and money on account has no due date.

A payment allocation can keep back a `discount`, up to what the item offers, when the money pays the rest of the item; the item is then settled in full. `payment.draft` fills the discount in when the payment is dated by the discount date. After that date the policy `payment.late_discount` refuses it unless the company allows it. The discount is posted at the payment's rate: of each tax the invoice recorded, the same share is taken back to the tax account the invoice posted to and recorded in the tax ledger as a credit of the invoice's entry, in the payment's period, and the rest goes to the account for `discount_received` (payables) or `discount_given` (receivables). Where a cash discount does not change the tax (US sales tax), the company refuses the policy `payment.discount_tax` and the whole discount goes to the discount account.

**Write-offs.** An allocation can write off what is left (`write_off`, a magnitude that runs the way of its item): of the part it names, else of the whole item, the amount, the discount and the write-off together are the rest. It may be left of a debt (a customer short-paid) or of a credit (a customer overpaid by a few cents), and it needs no money: an allocation of amount 0 with a write-off settles a residue on its own, and a payment of nothing but write-offs moves no money and needs no bank account. Only the policy `payment.write_off` decides how much (facts: `kind`, `currency`, `amount`, `percent` of the item, `credit`); nothing else refuses it. What is written off goes to the account for `write_off`, debited for a debt and credited for a credit, at the payment's rate.

**What someone may be told.** How much is open on an item is the item's to tell: a refusal of a payment tells how much is open, or how much a part, a write-off or a discount would have to be, only to someone who may read open items (`open_item:read` in the company). Anyone else learns only that the allocation does not fit.

**Discount steps.** Terms may offer more than one early-payment discount: 2 % within 10 days, 1 % within 20, net 30. The terms' own discount is the first step and `payment_terms_step` rows add the others. An item keeps every step it offers in `open_item_discount`, and the step in force on the payment's date applies.

**Instalments.** Terms may make an invoice due in parts. Each `payment_terms_instalment` row is one part before the last: a percent due a number of days after the date, counted as the net days are. The last part is what is left, due at the net days. The parts are fewer days than the net days and leave something for the last; a trigger refuses anything else, including net days moved before a part. When an invoice posts, its open item keeps its parts in `open_item_instalment`, in the item's currency: each part's due date and amount, rounded, with the last taking what rounding leaves. A deferred trigger checks that they add up to the item. The item's own due date is its last part's. A payment allocation may name the part it pays (`instalment`, 1 for the first), and the ledger refuses more than is open of it, counting what unnamed payments took of it (the settlement trigger reads `open_item_instalments`, with the item locked). One payment may pay several parts of an item, each in an allocation of its own that names its part; an item appears in a payment once otherwise. A part paid short is written off with its payment, before the last part is paid. Payments read an item's parts only after they hold its lock, in a statement of their own, so a payment that waited for another reads the parts as the other left them. Adding a part to terms locks the terms first, so two parts added at once cannot take them to 100 %. An allocation that names none, a credit applied to the item, or a reversal calling it off pays the earliest part still open first. What is open of each part is worked out from the settlements, not stored (`open_item_instalments(item, as_of)`): first what was paid for it by name, then the unnamed payments in order of the parts. `open_item.list` shows each item's parts with what is open of them, and `open_item.aging` ages an item by its parts. What is open of the item in the accounting currency is shared over its open parts by what is open of each in the item's currency, each at its own due date, with the last part taking what rounding leaves. An early-payment discount is about the whole item: it is taken with the payment that settles all the rest of it.

`open_item.aging` puts what is open of payables or receivables as of a day into buckets by days past due (current, 1-30, 31-60, 61-90, over 90 unless other bounds are given), per party, in the accounting currency at the value each item is carried at, with what falls due in the next 7 and 30 days, and each control account's balance beside what its items add up to. As of a past day it counts only postings dated by then.

### Concurrency guarantees

| Situation | Guarantee | How |
|---|---|---|
| Two requests post the same draft | One posts; the other gets the same result | Row lock on the document |
| An idempotency key is reused with other input | Refused | Stored input hash |
| A period closes while a journal posts | They wait for each other; a closed period never receives an entry | Share lock taken by each entry, exclusive lock taken by the close |
| Two users edit the same draft | The stale edit is refused | Version number on the document |
| Two users edit the same plain record | The stale edit is refused, if the caller sends the `_version` it read | The row's `xmin`, which Postgres changes on every update |
| Two people take the last stock at once | One is refused; stock never goes negative unless the company's policy allows it, and then each sees what the other left | Row lock on the level of that item and warehouse, taken in a fixed order |
| Two payments settle the same invoice at once | Together never more than is owed | Row lock on the open item, taken in a fixed order |
| Two servers deliver the outbox | Each event is taken by one | Row lock, skipping locked rows |
| A number series under load | No gaps, no duplicates. Numbers follow the order in which commands finish, closely but not strictly | Counter row locked from the end of the command until commit: a document takes its number in its last step, the move to a locked state |
| A change triggers an integration | The event exists if and only if the change committed | Outbox row in the same transaction |

Each row has a test in `apps/server/tests/`.

### Identity and authorization

The two are separate. The kernel (`authz/`) holds the directory of users and decides what an actor may do. `erpcraft-auth` answers only "who is this?": it is an ordinary module that supplies the kernel's `Authenticator`, so an installation can replace it with its own.

Built:

- Users sign in with a password and receive an opaque token, stored hashed.
- Users sign in through an identity provider with **OpenID Connect** (Microsoft Entra ID, Google, Okta, Keycloak, Authentik; several at once) and receive the same kind of token. See [Single sign-on](#single-sign-on) below.
- **Users are administered** with `user.list` (search by name or email, filter by active, `ids` to show given users; each with the roles they hold and for which company), `user.get` (also the attributes), `user.update` (name; administrator rights, which only an administrator grants or takes away), `user.deactivate` and `user.activate`, `user.assign_role` (granting a role held already changes nothing) and `user.revoke_role`. Reading takes `user:read` for all companies, which also shows attributes: they are facts rules read, not secrets. No command returns a credential. The last active administrator can neither stop being one nor be switched off, and only an administrator switches an administrator off. A deactivated user's tokens stop working on the next request, since every request loads the user and checks `active`. Users are also the read-only entity `user`, so a field can link to one (a document's `created_by`) and generic reads find them. How a user signs in is the identity module's business: the UI reads `sso_identity.list` for a user's binding. Every change is recorded on the user, so `audit.history` with resource `user` shows it.
- **Nobody hands on more than they hold.** An administrator grants anything. Anyone else grants or revokes a role (`user.assign_role`, `user.revoke_role`) only for someone else, and only a role whose every allowing rule they hold themselves at least as far: for the company it is granted for or for all companies, for at least its fields, and with no condition or the very same one (a condition that reads `user.<attribute>` never counts as the same, since another user's attributes reach other records). A deny anywhere in their own roles that touches what the role allows means they do not hold all of it, and a token limited by scopes hands nothing on. Writing, changing or deleting a `role` record follows the same rule, for all companies, for the role as it was and as it would be. Attributes widen what rules reach, so `user.set_attributes` is handing on rights too: someone who is not an administrator sets them only for another user who is not an administrator and all of whose roles they could have granted.
- **The directory is read for all companies.** An entity can declare `read_needs_global`: then reading it, generic lists and reads included, takes the grant for all companies, not one for any company. `user`, `role` and `sso_provider` declare it. Other shared records (items, vendors, customers, tax codes) stay readable under any company's grant, because every company uses them.
- **An administrator acts as one only on a credential that could have signed one in.** Each token records how its user signed in (`password`, or `sso:` and the provider), and a token made with `auth.create_token` carries the origin of the one in use on. When a token authenticates, an administrator whose token came through a provider not trusted for administrators (or one renamed or deleted since) is refused, not quietly given fewer rights, so that they know to sign in again; the same is checked when a login code is exchanged. This covers a user made an administrator after signing in. `auth.create_token` makes tokens of at most 365 days (90 by default).
- A command input that refers to a record says so in its JSON Schema with `x-field-type`, in the form of a field type: `{"kind": "link", "entity": "user", "key": "id"}` on the `user_id` of `user.assign_role`, `user.revoke_role`, `user.set_attributes` and the `sso_identity` commands.
- A token can carry **scopes** that cap it below its user's rights. This is how an agent gets less than the person it works for.
- A **role** is a list of permission rules. A role is granted to a user for one company or for all companies. A user's rights are the sum of their grants.
- A rule allows or denies one `resource:action`, optionally only for records matching a condition, optionally only for some fields:

  ```json
  "account:read"
  { "allow": "stock_entry:read", "where": "record.warehouse in user.warehouses" }
  { "allow": "item:update", "fields": ["description", "bin"] }
  { "deny":  "item:read", "fields": ["cost"] }
  { "deny":  "journal_entry:post", "where": "record.created_by == user.id" }
  ```

- **Deny wins.** A record is denied if any deny rule applies, otherwise allowed if any allow rule applies, otherwise denied.
- **Row rules** become part of the database query, so lists, counts and paging only ever include what the caller may see. Records out of reach read as not found. Every write is checked too: a create against the new record, an update against the record before and after.
- **Field rules** remove withheld fields from every record that leaves and refuse writes to them. A withheld field cannot be used as a filter.
- **User attributes** are free-form facts on the user (`{"warehouses": ["W1"]}`) that rules read as `user.<name>`, so one role serves every warehouse.
- **Nothing undecidable helps the caller.** A rule that cannot be evaluated never allows and always denies. A null is undecidable like a missing value: a user attribute that is null is one the user does not have, and a field that is null can be asked `== null` or `!= null` and compared with nothing else. A record and a list filtered in the database are decided the same way. An action checked without a record, such as a total over a ledger, treats conditional rules the same way.
- Rules are checked when a role is saved: the syntax, the fields they name, and that they can be compiled to SQL.
- `/api/meta` describes, under `access`, what the caller could do: per entity whether they can read, create and update, and which fields are limited (`all`, `some`, `none`); per document type the actions open to them; and the commands they could run. An interface uses it to decide what to show. It is a courtesy: every command still checks for itself.

Limits of what is built:

- An administrator is not subject to rules.
- Rules on a document see its header (company, status, dates, creator) and its summary (`record.summary.<field>`), not its lines.
- Field rules apply to entities, not to documents.

Planned:

- Postgres row-level security as a second wall, which requires the server to connect as a non-owner role.
- SAML, and provisioning of users by the identity provider (SCIM).

#### Single sign-on

A provider is a record of `sso_provider`: a name for the sign-in page, a slug for the URLs, the issuer, the client id, the scopes, the email domains that may sign in, whether a first sign-in creates the user and with which role, whether the provider must state that the email address is verified, and whether administrators may sign in through it (`trusted_for_admins`). Providers are managed with the commands `sso_provider.create`, `.update`, `.set_secret` and `.delete`, and read with `sso_provider.list` (permission `sso_provider:read`). The client secret is in a table of its own that is not an entity: no read returns it, and the commands that take it are sensitive, so it reaches neither the audit log, the outbox nor the idempotency table.

**Whoever may configure providers can sign in as any user who is not an administrator.** A provider decides who its users are: point one at a server you run, name a domain, and that server's word is enough to sign in, by email address, every user of the domain who is not bound to another identity yet. So there is one permission for every change to providers and bindings, `sso_provider:manage`, held for all companies, and it must be held as closely as administrator rights. Besides it:

- A provider that grants a role to the users it creates (`default_role_id`) grants that role to whoever it lets in, so every change to who such a provider lets in (issuer, client id, domains, creating users, the role or its company, requiring a verified email, trust for administrators, switching it on) also takes `user:assign_role`, as does setting the role.
- Only an administrator can set `trusted_for_admins`, or change, give a secret to or delete a provider that has it, or change the binding of an administrator.
- The client secret belongs to one client at one issuer. Changing `issuer` or `client_id` discards the secret, the identities users are bound to at the provider and the sign-ins on their way, and makes the provider inactive. A provider cannot be active without a secret (enforced by the database too), so it signs nobody in until `sso_provider.set_secret` gives it the new secret and `sso_provider.update` switches it on. Without that, holding `update` was enough to send the real secret to a server of one's choosing.
- `allowed_domains` is required and cannot be empty: any domain is said with `["*"]`, never meant by omission. A provider saved before this has none, and signs nobody in until it is given some.
- Every change to a provider or a binding is kept in `auth_event` (kind `sso_provider` or `sso_identity`): who made it, which provider, and what changed. Never the secret.

**Users are bound to an identity.** The first sign-in of a user through a provider binds them (`sso_identity`) to that provider and the subject (`sub`) it states. From then on they are accepted only from that provider under that subject, whatever email address it states; another provider, or another subject with their address, is refused (`not_bound`). The first sign-in of an existing user who is not bound is allowed only from a provider that names the user's domain in `allowed_domains`; `["*"]` binds nobody by address and signs in only users bound to it with `sso_identity.set`. A user created at first sign-in is bound at once. An administrator signs in only through a provider marked `trusted_for_admins`, bound or not (`admin_not_allowed`). An administrator changes a binding explicitly with `sso_identity.set` (user, provider, subject; `auth.events` shows the subject of every sign-in, refused ones too) or `sso_identity.delete`, after which the next allowed sign-in binds the user again; `sso_identity.list` shows the bindings.

The flow is the authorization code flow with PKCE:

1. `GET /api/auth/sso` lists the active providers for the sign-in page. It needs no token.
2. `GET /api/auth/sso/{slug}/start?return_to=/path` notes a login attempt (state, nonce and PKCE verifier, good for ten minutes), gives the browser a cookie, and sends it to the provider. `return_to` must be a path on this server.
3. The provider sends the browser to `GET /api/auth/sso/{slug}/callback`. The state is checked and used up, the code is exchanged at the provider's token endpoint, and the ID token is checked: its signature against the provider's published keys, which are read again when a token names a key that is not known; the issuer; the audience; that it has not expired and was issued just now; and the nonce. Then the email address must be verified and of an allowed domain; the user is the one bound to the identity, or else the one with the address if the provider may bind them, or a new one if the provider creates users; and must be active.
4. The browser is sent to `return_to` with `sso_code`, a login code good once and for a minute. The page posts it to `POST /api/auth/sso/exchange` and receives what a password sign-in returns. The token is never in a URL. A refused sign-in goes to `/sign-in?sso_error=<word>` instead.

What keeps it safe:

- The redirect URI is built from `ERPCRAFT_PUBLIC_URL`, never from the headers of a request.
- The server calls only the issuer an administrator configured and the endpoints that issuer's discovery document names, all https, without following redirects, with a time limit and a size limit. `ERPCRAFT_SSO_ALLOW_INSECURE=1` allows plain http for an issuer on the same machine, for development and tests.
- Only algorithms with a public key are accepted for the ID token. The claims are checked by the JWT library and again by this crate on typed values.
- The state, the login code and the cookie are stored as hashes, and compared in constant time. The cookie ties a sign-in to the browser that started it, so that a link to somebody else's finished sign-in signs nobody in. Its name is `__Host-erpcraft_sso_` and an id of the sign-in, with `Secure`, `Path=/` and no `Domain`, so a sibling subdomain cannot plant it; only exactly that name is accepted for that sign-in. Over plain http, which the public URL may use only on the same machine, the prefix cannot be used and the name is `erpcraft_sso_` and the id. The PKCE verifier and the client secret must be sent to the provider, so they are stored as they are.
- A user's first sign-in matches them by email address, so an address the provider does not vouch for is refused. Microsoft Entra ID sends no `email_verified`: either add its optional claim `xms_edov`, which is accepted in its place, or set `require_verified_email` to false on that provider, which is right only for a single-tenant application, where the organization controls the addresses.
- A provider that creates users must name the email domains that may sign in (`["*"]` is refused there).

A user created at sign-in has no password, and `user.create` takes none for a user who is to sign in only through a provider, so an installation can do without passwords for everyone but its first administrator. Each token records how its user signed in (`password`, or `sso:` and the provider's slug). Sign-ins and refused sign-ins, by password or through a provider, are kept in `auth_event` and listed by `auth.events`, since the audit log holds only commands.

### Rules

A rule condition is one expression over `record` and `user`. The syntax is CEL. `erpcraft-rules` is the only crate that knows the engine; the kernel sees a `Rule` that can be checked, evaluated against a record, and compiled to a SQL condition with bound parameters. Only the part of CEL that maps to SQL is accepted: comparisons, `in`, `&&`, `||`, `!`, literals, record fields and user attributes. The same crate serves the `where` parameter of lists, and is meant to serve validations and workflow conditions later.

A rule or an expression is text that any signed-in user can send, and the engine walks it by recursion, so its size is limited before anything recursive sees it: at most 4,000 characters, parsed on a thread with a stack of its own (64 MB of address space), and refused if the parsed tree is more than 64 levels deep. Without that, 11 nested parentheses were enough to overflow the stack of a request in an unoptimized build, which aborts the server. The measurements are in `crates/erpcraft-rules/src/parse.rs`.

What parsing a source gave is remembered inside `erpcraft-rules`, by its exact text, so a rule is parsed once and not on every request: stored rules and policies (`parse_stored`) in a cache of 1,024 entries, conditions sent with requests (`parse`) in one of 256, and refusals in a third of 256, each also bounded by the bytes of source it holds and each dropping what was used longest ago. They are separate so that no stream of different `where` conditions or broken ones can push out the handful of stored rules every request needs. `ERPCRAFT_RULE_CACHE=off` turns it off.

A condition that is only ever evaluated in memory, such as a policy rule, is an `Expression` of the same crate and in the same syntax. It never becomes SQL, so it can say more: arithmetic (`+ - * / %`), comparisons between any two values, `condition ? a : b` and `has(user.x)`, besides `&&`, `||`, `!`, `in` and literals. Nothing of this widens what a rule that must filter accepts.

### Bank statements and reconciliation

A `bank_statement` (module `banking`) is a document per bank account (an `is_bank` account of the company) and period, in the account's currency: an opening balance, lines (booking and value date, a signed amount, counterparty name and account, reference, the bank's own transaction id) and a closing balance. Two things are invariants, refused when the statement is saved: opening plus lines is the closing balance; and a statement starts no earlier than the account's last statement ends and opens at its closing balance. A bank transaction id is unique per bank account.

`bank_statement.import` (`bank_account_id`, `format`, `content`) reads a file into a draft. Formats: **CSV**, read with a `bank_csv_mapping` saved per bank account (delimiter, header or not, date format, decimal comma, which column holds the booking and value date, a signed amount or a debit and a credit, counterparty, reference and transaction id; a row without a transaction id gets one made of what it says); **ISO 20022 camt.053** (any version from .001.02, namespaces ignored, one statement per file, read with `quick-xml`; a DTD or an unknown entity is refused, so nothing outside the file is read); **OFX** 1 (SGML) and 2 (XML), one statement per file, the opening balance worked out from the closing one, which the file must state (a file cut off before its balance, its last transaction or `</OFX>` is refused). The account a camt.053 or OFX file names must be the bank account's, as its `bank_account_number` records it (a file that names none is imported with a note saying so), and every amount must be in the statement's currency. Amounts are capped at what `numeric(20, 4)` holds; camt.053 amounts are unsigned with a point, `CdtDbtInd` exactly `CRDT` or `DBIT`; lines must be booked within the statement's period. Files are read on a blocking thread, in time linear in their size, with at most 500,000 elements nested at most 64 deep. Files are at most 5 MiB and 10,000 transactions; a malformed one is refused with the line (and for XML the element) it is about. A file whose transactions were all imported before returns that statement; one that repeats only some is refused.

`bank_statement.proposals` says what each line not matched yet probably is, best first: a posting that moved the bank account by exactly the line's amount within ten days, not reversed and not matched to another line; open items it pays, by a document number in the reference (grouped by party) or by amount, scored higher when the counterparty is the party (only for a caller who may read open items, and party names only where the caller may read the party); or an account, where an earlier line of the same counterparty or reference was posted to one, or the text reads like a fee or interest. `bank_statement.match` records the choice per line: `posting`; `open_items`, which runs `payment.draft` for them through the bank account, dated the booking date (the caller needs `payment:create`); `account`; or `clear`. A posting of another amount than the line is accepted only with an account for the difference and when the policy point `bank_statement.amount_difference` allows it (refused by default; facts `line_amount`, `posting_amount`, `difference`, `difference_abs`).

`bank_statement.post` reconciles and locks: every line must be matched; a payment drafted for a line must be posted, and what a line's posting moved through the bank account must be the line less its difference; lines and differences matched to an account are posted then, one posting per line, by the statement itself.

`bank.reconciliation` (`bank_account_id`, `as_of`) sets the ledger against the statements: the ledger balance of the account (in its currency), the closing balance of the last statement ending by then, the postings on no statement yet (outstanding), the statement lines or parts of lines the books do not hold yet (unmatched), and the opening balance of the first statement (money that was there before). Outstanding less unmatched less that opening balance is the difference, to the cent; `unexplained` reports anything else and is zero while the statements follow each other.

The module reads general ledger entries, postings, documents and open items with SQL, as a report does; it writes the ledger only through `erpcraft_gl::post` and payments only through `payment.draft`.

### Paying vendors in a run

The module `payment_runs` (`modules/payment_runs`) pays what is due to vendors in one batch, through the payments module's own commands, and writes the files a bank takes. It sends nothing to a bank: a file is generated and handed to whoever (or whatever) carries it there.

- **Bank details in one place: banking.** The company's bank accounts already have their numbers (`bank_account_number`: IBAN, BIC, account number, holder); banking migration 5 adds what US and Canadian banks need of them (`routing_number`, the ABA number; `ach_company_id`, the company identification a NACHA file carries; `ach_origin`, its immediate origin when the bank gives one), and **party bank accounts** (`party_bank_account`): a vendor's (or customer's) accounts, each with an IBAN and BIC, or a routing and account number and account type (`checking`, `savings`), a holder name and a currency, one of them the default. Party data does not hold them, as before: bank numbers are banking's. An IBAN is checked by its ISO 7064 check digits when it is saved or changed (banking migration 6, a trigger: an IBAN saved before the check existed stays as it is, and the rest of its row can still be changed), and a routing number by its ABA check digit whenever it is saved.
- **Holds.** `payment_hold` stops a vendor, or one open item, from being proposed, with a reason, until it is lifted (made inactive). A hold placed after a run was proposed still stops it: approving and posting refuse a run that would pay a held vendor or item, until the hold is lifted or the line is set to `hold`.
- **The run** (`payment_run`, `PR-`), per company and bank account: a pay date (the document's date), a `due_by` day, the run's currency (the bank account's, else the accounting currency), and whether to take discounts. `payment_run.propose` fills a draft with a line per vendor open item in that currency that is due by `due_by`, or that offers an early-payment discount still open on the pay date (taken when `take_discounts`), net of the vendor's credits in the same currency, leaving out held vendors and items, items already in another run that is not cancelled, and vendors whose items come to nothing or less. Each line has the vendor, the due and discount dates, the amount and discount proposed; a person changes amounts, removes lines or sets `hold` on a line before approving.
- **Approval.** `payment_run.approve` asks the policy `payment_run.approve` (facts: `total`, `count` of payments, `lines`, `currency`; allowed by default), so a company asks for approval over a limit with the approval machinery like any other point; the run is then locked.
- **Posting.** `payment_run.post` drafts one payment per vendor with the run's lines (outgoing, through the run's bank account, on the pay date, discounts as on the lines) and posts it with `payment.post`, in the same transaction, as the person posting the run: the payments module's checks, rights and policies (`payment.post`, `payment.late_discount`, ...) hold as for any payment. Each payment is linked to the run. All or nothing.
- **Bank files** (`payment_run.bank_file`, `format`), from a posted run, one credit per payment:
  - `sepa`: ISO 20022 **pain.001.001.09** customer credit transfer initiation, SEPA service level, in EUR only; debtor from the bank account's IBAN and BIC, creditor from the vendor's default party bank account (IBAN, BIC if known), the remittance information the invoices' vendor references (unstructured, 140 characters). The test checks the file against the official ISO 20022 schema `pain.001.001.09.xsd` (from iso20022.org) with `xmllint` when `PAIN001_XSD` names it; it passed when built (November 2026). The schema is not kept in the repository, as iso20022.org publishes it under its own terms of use rather than an open-source licence, so without it the test checks the structure only. The EPC's SEPA rulebook restrictions on top of the schema (the character set, `NOTPROVIDED` agents) are not checked.
  - `nacha`: a NACHA ACH file of credits, `CCD` (to businesses, the default) or `PPD`, in USD only: file header, one batch, an entry per payment (checking or savings credit to the vendor's routing and account number) with a CCD addenda record carrying the references, batch and file control with entry hash and totals, padded to blocks of ten records of 94 characters.
  - Canadian **CPA-005 is deferred**: it is a fixed-width standard whose originator fields and record layouts differ from bank to bank (each publishes its own variant), so a file one bank takes another refuses; Canadian banks increasingly take ISO 20022 pain.001 for EFT, which the SEPA writer is the start of. It will come with a bank's variant to test against.
- **Remittance advice.** `payment_run.send_remittances` sends each payment of a posted run to its vendor with `document.send` (mail module): the payment's PDF lists the invoices it pays. Vendors without an email address on record are listed, not sent. `document.parties` names a payment's party, so the address is the vendor's contact. Each message is `document.send`'s own: it takes the right `payment:send` of whoever sends the advice, and the company's `document.send` policy decides as for any document (a posted payment to the vendor's own address on record is allowed by default).
- An EDI 820 remittance can be built from a posted run later (EDI phase 7): run, payments, allocations and the invoices' vendor references are all readable.

### Collections: statements and dunning

The module `collections` (`modules/collections`, migration 1) is where a company chases what customers owe. It reads the open items ledger and posts only through the general ledger, the tax ledger and the open items ledger. Like a payment run, it does its work in documents that a person reviews, and it sends them with `document.send`.

**Customer statements.** A `customer_statement` (`CS-`) is a document about one customer and one currency (the accounting currency unless given). It covers a period: `from_date` to the statement's date.
- Saving a draft works the statement out from the ledgers, and `customer_statement.issue` works it out again and locks it, so an issued statement says what it said when it was sent.
- The statement holds:
  - the opening balance: what was open the day before `from_date`, from items dated before then less the settlements posted before then. A settlement counts from its posting's date or its item's date, whichever is later, so a payment dated before the invoice it pays shows with the invoice;
  - the activity in the period, each with its document's type and number: items opened (invoices and credits) and settlements (payments, credits applied, items called off by a reversal), with a running balance;
  - the closing balance, which equals the opening balance plus the activity;
  - the items still open on the statement's date, with the days each is past due;
  - the ageing of those items into current, 1-30, 31-60, 61-90 and over 90 days past due, by each item's due date (else its date; an item due in parts is aged by its last part).
- Amounts are in the statement's currency. Working one out takes `open_item:read` in the company.
- An issued statement prints through the printing module's generic template (or one of the company's for `customer_statement`). It is sent with `document.send` to the customer's address on record, which the default policy allows for a locked document. `customer_statement.issue_all` drafts and issues a statement for every customer with something open or some activity in a period, so a month's statements are one command; it returns each customer with its statement.

**Dunning levels** (`dunning_level`, per company):
- a `level` from 1, its `name`, and the `days_overdue` from which an item reaches it;
- a `fee` per letter, posted to `fee_account_id`. With `fee_taxable` the fee is taxed with the code the company's tax rules propose for the customer and its address: the customer's rule, its certificate, or the place's code (see [Tax by destination](#tax-by-destination)), else the default rule;
- an annual `interest_rate`, charged on what is overdue for each day since the item fell due (or since interest was last charged on it), on a 365-day year, to `interest_account_id`. Interest is not taxed;
- `pay_within_days`, the due date of what the letter charges;
- the letter: `subject`, `text` (printed on the letter and sent as the message), and `print_template_id`, a template for `dunning_letter`.

A fee or interest needs its account, which must be one a plain line may post to.

**Holds and payment plans.**
- `dunning_hold` stops a customer, or one open item, from being dunned, with a reason, until it is made inactive.
- `payment_plan` records that a customer pays what it owes by agreement from `starts_on` to `ends_on`: such a customer is skipped while its plan is active.
- A hold or a plan made after a run was proposed still stops it: posting refuses a run that would dun a held or planned customer or item, until the line or letter is skipped.

**A dunning run** (`dunning_run`, `DUN-`), per company, dated the day it duns.
- `dunning_run.propose` fills a draft with each overdue receivable item of a customer and the level it reaches:
  - the highest level whose `days_overdue` it has reached, if that is above the level the item last had;
  - so an item climbs as it gets older, and is not dunned again at a level it has had.
- A customer is left out when it is held, on a plan, or owes nothing or less once its credits are counted. An item is left out when it is held or on another run that is not posted or cancelled.
- The run has two collections:
  - `lines`, one per item: the level, `proposed_interest` and the `interest` to charge;
  - `letters`, one per customer: its level (the highest of its lines that are not skipped), `proposed_fee` and the `fee`.
- A person reviews it: lowers or clears a fee or an interest, or sets `skip` on a line or a letter. More than the level charges is refused, so a raised fee cannot hide waived interest; waiving is counted per line.
- **No interest on interest.** The item a letter opens for its fee and interest is dunned like any other and climbs the levels, but bears no interest.

**Posting a run** (`dunning_run.post`, the right `dunning_run:post`):
- **What is true now.** The items are read again under their locks. An item paid or credited since the run was proposed is left out (and a letter with nothing left is not made); an item that owes less is charged interest on what it owes now, at most what was approved; an item that another run dunned meanwhile, or whose level the levels no longer give, refuses the run, to be proposed again. The run keeps what it posted.
- **Waiving.** The policy `dunning.waive` is asked for each letter whose fee or interest is below what was proposed. Facts: `fee_waived`, `interest_waived`, `level`, `customer`. By default it refuses, so whoever may waive is configured, for example `allow when user.department == 'credit'`, or approval through the approval machinery.
- **Holds** and plans are checked again.
- **The letters.** Each customer letter that is not skipped becomes a `dunning_letter` (`DL-`, linked to the run), posted on the run's date:
  - the fee (and its tax) and the interest go to their accounts, against the receivable account of the company's sales settings;
  - they open one receivable item for the customer, due `pay_within_days` after the run;
  - the letter keeps the customer's parties first, so its tax entries know the place.
- **Level history.** Each dunned item gets a row in `dunning_history`: the item, the letter, the level, the date, and the interest with the days it covers, recorded even when the interest was waived, so those days are not charged later. An item's level and the day interest was last charged to are read from it; the generic list of `dunning_history` shows an item's history.
- **All or nothing.** A letter that charges nothing is a reminder with no posting.
- **Sending.** `dunning_run.send` sends each letter of a posted run with `document.send`, with the template, subject and text of its level, to the customer's email on record. A customer without one is listed as skipped. Each message takes `dunning_letter:send` of the sender and the company's `document.send` policy.

Limits:
- Fees and interest are in the accounting currency; interest is worked out on what an item is carried at in it.
- An item at the last level is not dunned again. A letter lists the items that reached a new level, not every overdue item of the customer.
- A posted letter is not reversed by this module: a fee or interest given back is a customer credit (`sales_credit`), applied to the letter's item.
- Statements of several currencies are one statement per currency.

### Price lists

The crate `erpcraft-pricing` (module `pricing`, migration 1) proposes the price and discount of an order line from price lists, and on purchases from the last price paid. The proposal is only a proposal: a person can change it before approving. The company's policy decides whether a change needs approval. Sales and purchasing call it the same way: the pricing module does not know what an order is.

**Groups.**
- `price_group` (shared) is a group of customers, of vendors or of items (`kind`), with a code and name.
- `price_group_member` puts a customer, vendor or item in at most one group of its kind.
- Neither the sales nor the stock module knows about groups: they are pricing's.

**Price lists** (`price_list`, per company):
- `code`, `name`, `side` (`sales` or `purchase`), `currency`, `valid_from` and `valid_to`, `active`;
- whom the list is for, `scope_type` and `scope_id`: a customer or customer group on the sales side, a vendor or vendor group on the purchase side, or nobody named (the list for everyone on that side).

A line (`price_list_line`) is:
- for an item, or for an item group;
- from a `min_qty` (a quantity break; 0 for any quantity);
- with a `unit_price`, a `discount_percent`, or both.

A line that gives only a discount discounts the price found elsewhere: the item group "fasteners" at 10 % off for a customer group, over the list for everyone's item prices.

**The proposal** (`erpcraft_pricing::propose`, for the company, side, party, item, quantity, currency and date). Lists that are active, of the side and currency, and valid on the order's date count. Their lines that match the item (itself, or its group) and whose `min_qty` the quantity reaches are ordered, most specific first:
1. the party's list, then its group's, then the list for everyone;
2. within that, the item before its group;
3. then the highest break.

The price is the first line's that gives one, and the discount, separately, the first line's that gives one. On a purchase without a listed price, the last price paid applies: the unit price and discount of the latest posted vendor invoice line of the vendor for the item, in the order's currency.

**On an order.**
- A sales or purchase order line of an item may leave out `unit_price`. Saving fills in the proposal: the price, and the discount when the line gives none. A line that gives its price keeps its price and its discount.
- A line left without a price and with nothing to propose is refused, naming the line.
- Each item line's proposal is kept beside the order (`price_proposal`: the line, the price and discount proposed, where from), and approving compares the line with it.
- When the order is approved, the policy `price.override` is asked for each line whose price or discount differs from what was proposed. Facts: `side`, `item`, `price`, `list_price`, `change_percent` (below zero: cheaper than proposed), `discount`, `list_discount`, `source` (`list` or `last_paid`). It allows by default; a company refuses, or asks for approval (`effect: approve`), for example when `facts.side == 'sales' && facts.change_percent < -5`.
- Lines with no proposal are not asked about.

Limits:
- No price in another currency is converted: a list is for one currency.
- No list price includes tax.
- Units of measure other than the item's are not priced.
- Invoices without an order take no proposal.
- Group membership is one group per kind.
- The order's date, not the delivery date, decides which list is valid.
- A proposal is worked out again each time a draft is saved, but a price the line already has is kept.

### Sales quotes

The module `quotes` (`modules/quotes`, migration 1) offers a customer prices before it orders.

**The quote** (`sales_quote`, `SQ-`):
- a customer, a currency and `valid_until`;
- lines like a sales order's: an item and its warehouse, a charge, or an account, with a quantity, price and discounts.

An item line may leave out its price and is proposed one by the price lists, as an order line is (see [Price lists](#price-lists)). What was proposed is kept, and issuing the quote asks the policy `price.override` for each line whose price differs from it, so a negotiated price is decided on before the customer sees it.

**States:** `draft` → `issued` (locked) → `won` or `lost`.
- `sales_quote.issue` locks a reviewed draft; it is then printed and sent with `document.send`.
- `sales_quote.accept` (optionally a `reason` and the order's date) drafts a sales order with the quote's lines, prices and discounts, linked to the quote, and marks it won. The order is an ordinary draft, approved as any other, so `price.override` is asked again then against the price lists. After `valid_until` a quote is refused unless the policy `sales_quote.expired` allows it (facts: `days_expired`, `total`, `currency`; refused by default).
- `sales_quote.lose` (`reason`, required) marks it lost. The reasons are kept on the quote (`won_reason`, `lost_reason`).
- A quote won or lost does not change again. Its summary shows `expired` once its date has passed.

### Recurring invoices

The module `recurring` (`modules/recurring`, migration 1) invoices a customer on a schedule: a rental, a subscription, a maintenance contract.

**A template** (`recurring_invoice`, per company) has:
- a `code`, the customer, its currency and payment terms;
- the lines (`recurring_invoice_line`): a charge or an account, a description, quantity, price and tax code, as on an invoice without an order;
- `frequency` (`weekly`, `monthly`, `quarterly`, `yearly`) times `interval` (every 2 months), and `next_date`, the date of the next invoice;
- `end_date` or `max_count` (whichever comes first ends it), and `count`, how many it has made;
- `post`: whether an invoice it makes is posted or left as a draft;
- `active`.

**The run.** `recurring_invoice.run` (`company_id`, `as_of`, by default today) makes, for every active template whose `next_date` is on or before `as_of`, the invoice of each date due up to `as_of`, so a missed run catches up:
- each invoice is an ordinary sales invoice without an order, dated its date, with the template's lines. Tax codes left out are proposed by the tax rules as for any invoice;
- each is drafted, and with `post` the policy `recurring_invoice.post` is asked (facts: `total`, `currency`, `customer`, `template`; allowed by default). Allowed, the invoice is posted with `sales_invoice.post` under the rights of whoever runs it; refused, it stays a draft for a person to post;
- the template's `next_date` moves on by its frequency (a monthly template started on the 31st falls on the last day of shorter months), its `count` goes up, and once it reaches `max_count` or passes `end_date` it is made inactive;
- each invoice is recorded against its template and date (`recurring_invoice_run`), once only, so a run repeated for the same day makes nothing twice.

The output lists each invoice made and whether it was posted. Nothing runs by itself: a scheduler outside calls the command, as for any other.

Limits:
- Invoices only, not orders or deliveries.
- No proration for part periods.
- Prices change by editing the template.
- A failed posting fails the whole run, so nothing is left half done.

### Fixed assets

The module `assets` keeps the fixed asset register: what the company owns and uses for years, what it cost, and its depreciation month by month. The general ledger holds the money; the register explains it, and `asset.register` shows whether the two agree.

- **Asset classes** (`asset_class`) are per company, because their accounts are: a method (`straight_line`, `declining_balance` with a yearly `declining_rate` in percent, or `none` for land) and a useful life in months. Their accounts are account rules with scope `asset_class` (or the company's default for the purpose): `asset_cost`, `accumulated_depreciation`, `depreciation_expense`, `asset_disposal_gain`, `asset_disposal_loss`. Where depreciation is written off the asset account directly, as SKR 03 does, `accumulated_depreciation` is the cost account itself.
- **An asset** (`asset`) is created planned, with its class's method and life unless it gives its own, and a salvage value. Its status (`planned`, `in_service`, `fully_depreciated`, `disposed`), cost and dates are written only by commands. Once it has been depreciated, its method, life, rate, salvage value and dates no longer change (a trigger); a capitalised asset is never deleted, and its class does not change.
- **Capitalising** (`asset.capitalise`) names a posted document line, such as a journal entry line, whose ledger entry debited the class's `asset_cost` account: the entry's amount is the cost, its posting date the acquisition date. Nothing is posted, as the ledger holds the cost already; an entry is capitalised once (a unique key). The policy point `asset.below_minimum` is asked (facts `cost`, `minimum`, `class_code`): by default an asset below the company's `asset_settings.minimum_cost` is refused, 0 meaning no minimum. `asset.put_in_service` starts the depreciation of an asset capitalised without an in-service date.
- **Taking over** (`asset.take_over`) records an asset from an older system with its cost and its depreciation up to the end of a month (`depreciated_through`), from an opening date (by default the day after). It posts nothing: the opening balances come in as a journal entry of their own, and until they do the register shows the difference. Depreciation continues over the life that is left.
- **The convention** (`asset_settings.convention`, per company): `full_month` (the default) depreciates the month an asset goes into service in full, `next_month` starts the month after. Once the company has depreciated anything it no longer changes (a trigger).

**Depreciation.** Every month of an asset's life has its amount, worked out the same way by a run, a disposal and the schedule, in the accounting currency's cents. Straight line spreads cost less salvage less depreciation taken over evenly over the months left, rounded per month; the last month takes what rounding left. Declining balance takes the yearly rate of the book value at the start of each calendar year, or of the asset's first year pro rata by months, as one block per year: a month is a twelfth of the year's amount and the year's last month takes the remainder. Each year it switches to straight line over the months left once that is more, as German and US practice allow. Depreciation never goes below the salvage value.

**A depreciation run** (`depreciation_run`, `DEP-`) is dated the last day of a month. `depreciation_run.post` depreciates every asset in service by then for the months since its last depreciation, so a missed month, or an asset capitalised late, is caught up, and posts one entry per asset (expense debit, accumulated depreciation credit), with the run's line for the asset as the source line. A draft shows what it would post. Runs go forward, enforced in the database: a month of an asset is depreciated once (a unique index over the months not reversed), and a run for a period already run, or before one, is refused (`depreciation_period` and its trigger). A run with nothing to depreciate posts nothing. `depreciation_run.reverse` reverses the company's latest run exactly, on its own date, so the register and the ledger agree at every date; not while an asset it depreciated is disposed of.

**A disposal** (`asset_disposal`, `ADS-`) sells or scraps an asset on its date: `asset_disposal.post` first depreciates the months that ended by then and were not yet, then removes the cost and the accumulated depreciation, books the proceeds to the account named (a bank, or a clearing account that a sales invoice to the buyer settles), and posts the difference to the book value as a gain or a loss. A disposal dated before a month already depreciated is refused. `asset_disposal.reverse` undoes it exactly, and the asset is depreciated again from where it was.

**Reports.** `asset.register` (report "Fixed asset register"): per asset in the books on the day, its cost, accumulated depreciation, book value and the depreciation since 1 January; beside it every account the classes' rules name for cost and accumulated depreciation, with what the register puts on it, its ledger balance and the difference, and `ties` when every difference is zero. `asset.schedule` (report "Depreciation schedule"): one asset month by month, posted (with the document) and planned.

`company.setup` creates the template's asset classes and their account rules (`asset_classes` in a template; `asset_disposal_gain` and `asset_disposal_loss` among its roles). `us_small_business` has furniture and equipment, computers, vehicles, machinery and land, with one accumulated depreciation account; `de_skr03` has Büroeinrichtung, EDV-Hardware, EDV-Software, Pkw, Lkw, Maschinen and Unbebaute Grundstücke on their SKR 03 accounts, written off directly, with the lives of the AfA-Tabelle (the template's sources say where each comes from).

### Electronic invoices (EN 16931)

The module `einvoice` writes and reads structured electronic invoices after the European standard EN 16931, the format German law requires between domestic businesses: received since 2025, issued from 2027 or 2028 by turnover (§ 27 Abs. 38 UStG). Its README names the sources it was built from, and lists exactly which rules it checks and which it does not.

- **Export.** `einvoice.export` (`doc_type` `sales_invoice` or `sales_credit_note`, `id`, `syntax` `ubl` or `cii`, `profile` `xrechnung` or `en16931`) writes a posted document as XRechnung 3.0 (or EN 16931 alone), in UBL 2.1 or CII.
  - The seller's and the buyer's particulars, addresses, tax identifiers, contacts and electronic addresses, and the buyer reference or Leitweg-ID, are party data (see [Party data](#party-data)), read with `erpcraft_party::load`. The VAT category of each line and its exemption reason are the tax code's (see **The VAT category of a code** under [Ledgers own their rules](#ledgers-own-their-rules)); the module keeps only the record of what it imported. The IBAN, BIC and holder of the account paid into are banking's `bank_account_number` (read with `erpcraft_banking::account_number`), the one place bank account numbers are kept.
  - Anything missing is refused at once, every item named with its business term and the record and field to set.
  - Line discounts are line allowances (reason code 95). A charge line such as freight is a line of its own.
  - The VAT breakdown carries the tax recorded per line, so the invoice says what was posted. The standard's rounding rule (BR-CO-17) allows that, within one currency unit.
  - A tax group (several taxes on a line) is refused: EN 16931 has one VAT rate per line.
  - **VAT categories.** A line is written in its code's category. `Z`, `E`, `AE`, `K`, `G` and `O` are at 0 % with no VAT, whatever rate the buyer accounts for; a line under such a code that was taxed is refused. `AE`, `K`, `G` and `O` get their VATEX code and text (VATEX-EU-AE, -IC, -G, -O) unless the code gives its own; an `E` code without a reason is refused. A code the buyer accounts for, or one at 0 %, that names no category is refused, with the categories to choose from.
  - **What the categories need.** A reverse charge (`AE`) needs the buyer's VAT identifier or legal registration (BR-AE-02). An intra-Community supply (`K`) needs the seller's and the buyer's VAT identifiers (a tax number is not enough, BR-IC-02), the delivery date (BR-IC-11, from the order's deliveries; a credit note takes its invoice's), and the country delivered to (BR-IC-12). An export (`G`) needs the seller's VAT identifier (BR-G-02). Each is refused, never written without, naming what is missing and where to set it (a `party_tax_id` of scheme `eu_vat`).
  - **Deliver to address (BG-15).** The shipping address the document kept, written with street, city, post code and country (XRechnung's BR-DE-10/11 want city and post code once there is one); for an intra-Community supply without one, the buyer's billing address, which is where such a delivery goes in this system.
- **Checks.** The XML is read back with the reader incoming invoices use, and checked: mandatory terms, line arithmetic, the VAT breakdown and the document totals (BR-CO-10 to 17), decimals, and XRechnung's German rules (BR-DE-*), with the tolerances of the official Schematron.
  - The category rules: BR-x-05, 08, 09 and 10 for each category, BR-S-10 and BR-Z-10 (no reason), BR-AE-02, BR-IC-02, 11 and 12, BR-G-02, BR-O-02 and 11, BR-57, BR-DE-10/11.
  - The official validator (KoSIT, Java and Schematron) is not run by the tests. The README says how to run it on the output; the output of the e-invoice tests (S, E, AE, K and G, UBL and CII, invoices and credit notes) was run through the official XSDs and the compiled EN 16931 and XRechnung 3.0.2 Schematron once, on 18 November 2026, without a fatal finding.
  - The reader and the checks pass every business case of the KoSIT XRechnung test suite (66 files, UBL and CII), with `EINVOICE_SAMPLES` pointing at them (`modules/einvoice/tests/samples.rs`).
- **Import.** `einvoice.read` reads an incoming invoice (XML, or the XML embedded in a ZUGFeRD / Factur-X PDF) and reports the rules it breaks, the vendor, the order and each line's order line and tax code. It creates nothing. `einvoice.import` drafts the vendor invoice.
  - The vendor is the one whose `party_tax_id` (scheme `eu_vat`) is the seller's VAT identifier, or the one confirmed with `vendor_id`; names only propose.
  - When the buyer's order reference is an open purchase order of that vendor, the invoice is drafted against it, line by line by line reference or item code. Other lines, and a direct invoice, go to `account_id`.
  - What the draft will come to is worked out as posting works it out and set against the invoice's VAT, total and amount due to the cent. A difference, an amount already paid, or a buyer the invoice does not identify is drafted only with `accept_differences`, and noted in the memo. A line charged VAT without a tax code stops the import until one is chosen (`line_tax_codes`).
  - What `einvoice.read` proposes (vendors, party records, the order) is read with the caller's rights.
  - Numbers beyond `numeric(20, 6)` are refused when read, and the arithmetic is checked, so no input can make it panic.
  - Refused: an invoice that breaks a checked rule, one addressed to another VAT identifier, a credit note, document level allowances and charges, and an invoice number of the vendor imported before (`einvoice_import`, with the file's SHA-256).
- **Hostile input.**
  - XML is read with `quick-xml`. A DTD, any entity but XML's own, more than 5 MiB, 200,000 elements or 64 levels is refused.
  - A PDF is parsed with `lopdf` on a thread of its own, waited for on the blocking pool with a time limit, and a panic is a refusal. Each stream lopdf inflates is limited to 4 MiB and what a load keeps to 200,000 objects and 64 MiB. It is never rendered and is refused if it holds JavaScript. The embedded file is inflated under the XML limit by the module itself.

**ZUGFeRD / Factur-X.** `einvoice.export_pdf` (`doc_type`, `id`, `profile`: `en16931`, the default, or `xrechnung`) writes the invoice as CII, checks it as `einvoice.export` does (refused if it does not hold), and makes our own printed PDF of the document (`printing::pdf_of`, PDF/A-3b) with the XML inside as `factur-x.xml` (`text/xml`, AFRelationship Alternative, listed in the catalogue's associated files) and the Factur-X XMP extension schema (`urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#`: DocumentFileName, DocumentType INVOICE, Version 1.0, ConformanceLevel `EN 16931` or `XRECHNUNG`), declared among the PDF/A extension schemas. krilla writes no custom XMP, so printing rewrites the packet in place (`printing::xmp`) and moves every offset after it. Checked by the tests: our own import reads the PDF back as the same invoice. Checked by hand on 18 November 2026: the embedded XML of both profiles against the CII D16B XSD and the EN 16931 and XRechnung Schematron (no finding), the PDF by Ghostscript and poppler (no repair). veraPDF needs Java and was not run.

### Electronic data interchange (EDI)

Decided 2026-11-18. **Built** (phases 1 and 2 of `modules/edi/PLAN.md`): the format layer (the tokenizer, X12 and EDIFACT envelopes, the 850 as a typed order, the 997, the 999 and the TA1, a sentence per segment), partners and cross-references, the interchange log, receiving (store, read, route, acknowledge), proposals and drafts of sales orders; the 855, 856 and 810 made from the approved order, the posted and packed delivery and the posted invoice or credit note, checked against the books; packing with SSCCs and labels; shipping in one transaction with the delivery's post; the partner's 997s matched; automation as the partner's run-as user; and the policy points `edi.auto_draft`, `edi.auto_approve`, `edi_order.duplicate`, `edi.send` and `edi_invoice.before_asn`. Everything else in this section is **planned**, in the order of the plan. The research behind it, with its sources and what could and could not be verified, is in [docs/research/2026-11-edi](docs/research/2026-11-edi/README.md).

**Why.** A manufacturer that sells to a retailer or supplies an OEM is told to trade by EDI: orders come as X12 850 or EDIFACT ORDERS, and the buyer wants an acknowledgement, a ship notice before the truck and an invoice back the same way. A small supplier cannot read these files, so it rents a value-added network (VAN) or an EDI service that carries and translates them, and pays per document or per kilocharacter, plus a fee to map each new partner. Nothing in this needs a middleman. The files are text, the transports are SFTP and HTTP, and what differs between partners is a document, their implementation guide. erpcraft reads and writes the files itself, connects to the partner directly, and keeps what differs per partner as data. A partner that accepts only a VAN is still reached: through that VAN's mailbox, in the partner's own format, so the VAN carries bytes and translates nothing.

**The standard is licensed, and that shapes the code.** X12 holds the copyright to its standard, its implementation guides and its code lists, and asks software that incorporates them for a licence; it does not say what that means for open source. Until that is settled this is a hard constraint: the repository holds a generic tokenizer and envelope reader; a segment is described in our own words, and only as far as the code acts on it; what a partner's messages look like is that partner's guide, entered by the company as data; no dictionary of the standard, no description of its code lists and no text of its guides is bundled; every fixture is written by us. EDIFACT's directories are published without charge.

**The module.** `modules/edi`, module `edi`, depends on `sales`, `stock` and `party`. It uses only the public module API: it reads records and documents through the kernel's reads with the caller's rights, and it writes business documents only by drafting them with `document::create`, as a person would. It posts nothing to any ledger and writes no table of another module. Inside, the format layer (`segment`, `x12`, `edifact`, `gs1`) depends on neither the database nor the kernel.

**One tokenizer, typed messages.** X12 and EDIFACT are the same shape: segments, elements, components, repetitions. They differ in which characters separate what and where a file says so, so the separators are data and the tokenizer is one. An X12 file states them in its ISA, the only fixed-width segment (106 characters: the element separator is the 4th, the component separator the 105th, the terminator the 106th, and from version 00402 ISA11 is the repetition separator); an EDIFACT file in its UNA, or else the defaults apply. EDIFACT has a release character and X12 none, which decides a rule of the writer below. Above the tokenizer every message is read into a typed structure (an order, an order response, a ship notice, an invoice) and written from one. Nothing maps segments to rows or documents to segments directly: the typed message is what a partner's guide is applied to, what a proposal shows, and the same for both syntaxes.

**Data model.** All tables are the module's own.

| Record | What |
|---|---|
| `edi_partner` | A trading partner of one company: the customer it is, the warehouse its orders ship from, the syntax and version, both sides' interchange identifiers and qualifiers, `test` or `production`, the separators to write with, which acknowledgement it expects and within how many hours, its guide, its transport, and the user automation acts as (`run_as_user_id`). An incoming interchange finds its partner by sender, receiver and usage; one that finds none is kept as `unroutable` and nothing else happens. |
| `edi_guide`, `edi_guide_message` | The partner's implementation guide as data, per message and direction (below). |
| `edi_item_xref` | The partner's number for an item, or a GTIN for every partner of the company (cross-references belong to one company, as partners do): kind (`gtin`, `buyer_item`, `seller_item`), value, the partner's unit and how many of the item's own unit one of it is (a case of 6). |
| `edi_uom_xref`, `edi_location_xref` | The partner's unit codes; the partner's store and warehouse numbers or GLNs as shipping addresses of the customer. |
| `edi_control` | The next control number per partner and level (interchange, group, set), in a locked row, taken as the last step before a message's bytes are fixed. |
| `edi_interchange` | The log of raw payloads, in and out: the bytes, their SHA-256, where they came from or went, and what became of them. Written in the transaction that reads the bytes; never changed, and deleted only by the purge of old files no partner sent (a trigger). |
| `edi_message` | One row per transaction set or message: its type, control numbers, state, the document it became or was made from, the message it answers, its findings, and the partner's acknowledgement of it. |
| `edi_document`, `edi_document_line` | What an order said that its sales order does not keep: the partner's order number and line identifiers, its item numbers, unit, quantity and price as sent, and the references to quote back. |
| `edi_shipment`, `edi_pack`, `edi_pack_line` | How a delivery was packed: carrier, bill of lading, pallets and cartons, each with its SSCC, and which delivery line's goods are in which carton. |
| `edi_transport`, `edi_transport_secret` | How files travel, and the password or private key, which is not an entity and which no read returns. |

**The guide as data.** Two partners read the same standard differently: which qualifier carries the buyer's item number, whether the ship-to is a store, which optional segments they demand, how the cartons of a ship notice nest. That is what a mapping fee pays for. Here a guide is a record with three closed parts: **options** (choices the standard leaves open, by name: the order in which item numbers are tried, which date is the ship date, the hierarchy of the ship notice); **constraints** (per segment and element: required, not used, lengths, allowed codes); and **extra segments** at named places of an outgoing message, whose values are constants or expressions of `erpcraft-rules` over a fixed set of facts. It is checked when saved, as a policy rule is. It is not a mapping language: there are no loops, no scripts and no templates, so a guide cannot do anything a reviewer cannot read. The built-in guides describe each message as the standard has it, and a partner's guide inherits one. `edi_guide.check` shows how a partner's sample file reads under a guide, so onboarding a partner is something an agent does over MCP from the partner's own documents, and the server checks the result. Guides export and import as one file, so companies that sell to the same buyer can share one. None for a named company is in this repository.

**Inbound.**
1. **Store.** `edi.receive`, the SFTP poller and the AS2 endpoint all hand bytes to one function. It reads them (step 2) and stores them in the same transaction, once it knows whose they are: an interchange for a partner is kept for that partner's company, after the caller's rights for it are checked; bytes nobody could read or route are kept for the caller who sent them. So a preview, a caller without the rights, or a failure keeps nothing, and nobody learns from a repeat what someone else sent. The same bytes again are a repeat: the first result is returned and nothing is done twice, because transports redeliver. Unreadable and unroutable files older than 30 days can be purged (`edi_interchange.purge`); nothing else in the log is ever deleted.
2. **Read.** On a blocking thread, under the limits below. Bytes that cannot be followed are kept as `unreadable` with the reason; there is nobody to answer.
3. **Route.** By the envelope's sender and receiver. A test interchange (`ISA15` `T`, or the UNB test indicator) is read and acknowledged and never becomes a document.
4. **Acknowledge.** Each functional group gets one 997 (or 999, or CONTRL, as the partner's profile says) that accepts or rejects each set by the standard's syntax alone, with the segment and element at fault. It is queued at once and does not wait for anyone: a 997 says "this could be read", not "this order is accepted". An interchange-level fault, or `ISA14` asking for it, gets a TA1.
5. **Propose.** `edi.proposal` is read-only, like `einvoice.read`: the typed order, the customer, the ship-to, and for each line the item, the quantity and the price in the item's own unit, each with how it was found; and the findings. A finding is `blocking` (an item or ship-to nobody knows, a price that does not divide into the unit, something the guide requires and the order lacks, the same order number received before) or a `note` (a segment with no field here, a count that does not agree). Everything is read with the caller's rights.
6. **Draft.** `edi.draft` creates the sales order as a draft through the normal command, under the caller's permissions and every policy, with the person's choices for whatever blocked (which can be remembered as cross-references). It is approved like any order.
7. **Answer.** The order response (855, ORDRSP) is an outbound message made from the approved order: what was accepted, changed or refused per line.

**Outbound.** A message is made from a document in a locked state, never from a draft: the 855 from an approved order, the 856 (DESADV) from a posted delivery and its packing, the 810 (INVOIC) from a posted invoice or credit note, the 846 from stock availability. A subscriber on the outbox makes them when the document's order came by EDI and the partner's guide has the message; `edi.generate` makes one by hand, and with `preview` shows it and stores nothing.
- **Generate** from the document, from what `edi_document` kept of the order, and the guide.
- **Validate**, three times over: the bytes are read back with the reader an incoming message meets and must say what was meant; the guide's constraints must hold; and the figures must be the books' (the quantities of an 856 are those of the posted delivery, the total of an 810 is the invoice's to the cent). A message that fails is kept as `invalid` with what is missing and where to set it, and raises an event, since nobody is waiting for the refusal.
- **Number and fix.** The control numbers are taken and the bytes stored; from here they never change.
- **Send** through the partner's transport, retried from 1 minute doubling to an hour for 24 hours, then `failed` with an event.
- **Track.** Two receipts are kept apart: the transport's (an AS2 MDN whose integrity check matches, an SFTP rename that succeeded) and the partner's 997, matched by group and set control number. `acknowledged`, `acknowledged_with_errors` and `rejected` come from the 997; a rejection is shown in words with the segment it names. Sent and not acknowledged within the partner's hours is shown as overdue and raises an event. Nothing is resent by itself: `edi_message.resend` sends the same bytes with the same numbers, so the partner's own duplicate check works, and a corrected message is a new one that supersedes the old.

**Ship notices and cartons.** The 856 is where suppliers lose money: buyers charge back, per shipment or as a share of the invoice, for a notice that is late, missing or does not match what the dock scans (the amounts are each buyer's own; the research has what secondary sources say). So the notice is not typed, it is derived. Packing is recorded per delivery (`edi_shipment.pack`, or `auto_pack` for goods that ship in their own cases); each pallet and carton gets an SSCC, eighteen digits from the company's GS1 prefix and a serial, with its check digit, never issued twice; the label is printed from the same record (`edi.label`). `edi_shipment.ship` checks that the cartons hold exactly what the delivery delivers, posts the delivery and makes the 856 in one transaction, so the notice exists the moment the goods are posted as gone and says what was posted. `edi.pending` lists deliveries posted with no notice sent.

**Which transport for which partner.** The largest retailers ask their suppliers for AS2 software that is on a certification list (Drummond's), and say so in their guides. That is a gate no code passes by being correct. So the order is: SFTP, to the partner or to a VAN's mailbox, and a certified gateway that carries bytes and translates nothing, for such partners; our own AS2 for OEMs and smaller partners, who ask for interoperability, not a certificate; and certifying it as a later, explicit decision with its own cost.

**Transport.** `manual` works from the first day: files are handed to `edi.receive` and fetched with `edi_interchange.content`, by a person or an agent. `sftp`: the host key is pinned, files are read under the size limit and deleted or renamed only after they are stored, and a file is written under a temporary name and renamed. `as2` (RFC 4130): signed and encrypted S/MIME over https, with a signed receipt (MDN), synchronous or asynchronous; an endpoint `POST /edi/as2` that is not a command. The identity of a sender is bound through every layer: the AS2 identifiers name one transport, the signature must verify against that partner's configured certificate, and the interchange inside must be from a partner of that transport, so no partner can send as another. Certificates are pinned per partner; nothing is fetched to validate one. SFTP hosts and AS2 addresses must be public addresses, by the allow-list webhooks use. Whoever may configure a transport decides where orders and invoices go and whose word is taken for an order, so there is one permission, `edi_transport:manage`, held for all companies, and its commands are sensitive.

**Hostile input.** A file is hostile until read, whoever sent it.
- The tokenizer works on bytes, in one pass, without recursion, in time and memory linear in the file. At most 4 MiB, 200,000 segments, 500,000 components, 512 components in a segment, 4,096 bytes in one, 100 interchanges in a file; one budget covers the whole file.
- Refused: separators that are letters, digits, spaces, not ASCII or the same as each other; an ISA whose elements are not at their fixed widths; a segment that is not terminated or a file that ends before its trailer (a file cut off in transit is never read as whole); a control character in data; a tag that is not two or three capital letters or digits; X12 binary segments; EDIFACT functional groups.
- Text is UTF-8 when the whole file is, else ISO 8859-1, decided once per file; separators are single ASCII bytes, so splitting is right in either.
- Numbers are digits, one decimal mark and an optional minus, at most 18 characters, read as exact decimals; sums are checked, so no input overflows.
- Counts and control numbers that do not agree are not refusals: the file is read and the errors go into the acknowledgement, in the standard's codes.
- AS2: the body is limited before it is read, inflating is limited, signatures use SHA-256 or better and encryption AES unless a partner's transport explicitly allows the older algorithms.
- A test replaces every byte of the fixtures in turn and cuts them at every length; reading may refuse and must return.

**What is an invariant.** These hold for every company, because without them the record of what was exchanged, or the books, would be wrong:
- raw payloads are stored with what was read from them and never change; every message leads back to its bytes;
- a control number is used once, and a resend is the same bytes;
- every routed functional group is acknowledged once, the same way if it comes again, and an acknowledgement is never acknowledged;
- nothing is sent that fails its syntax or its guide;
- EDI drafts through normal commands and never posts; test traffic never becomes a document;
- an outgoing message quotes the partner's order number, line identifiers, item numbers and units as they were received, not as the cross-references say today;
- the quantities of a ship notice and the amounts of an invoice message are those of the posted documents;
- an SSCC has its check digit and is never reused;
- the X12 writer never puts a separator inside data. X12 cannot escape one, so an identifier that contains one is refused; only free text (a description, a name) may have it replaced, by what the guide says;
- a sender is who its transport, its certificate and its envelope together say.

**What is a policy.** Judgements a careful company could make either way:

| Point | Default | Decides |
|---|---|---|
| `edi.auto_draft` | refuse | Whether an order with no blocking finding is drafted without a person, as the partner's `run_as_user_id`. Facts: `partner_code`, `message`, `notes`, `lines`, `total_net`. |
| `edi.auto_approve` | refuse | Whether such a draft is then approved, still subject to every policy of `sales_order.approve`. |
| `edi_order.duplicate` | refuse | An order number of this partner received before. |
| `edi.accept_with_errors` | refuse | Whether a set with syntax errors is still proposed (acknowledged `E`) or rejected (`R`). |
| `edi.send` | allow | Asked for every outgoing business message, so a company can have invoices to a partner approved first. Facts: `partner_code`, `message`, `total`, `test`. |
| `edi_invoice.before_asn` | allow | Sending an invoice whose ship notice is not acknowledged yet. |
| `edi_order.change`, `edi_remittance.deduction` | refuse | A change to an approved order; an amount a partner deducted from a payment. Both reach a person. |

Automation runs as a user, with that user's permissions, so it can do less than a person and never more; an administrator is subject to these policies like anyone.

**Commands.** Partners, guides and cross-references are entities, written with the generic commands. Besides: `edi.receive`, `edi.proposal`, `edi.draft`, `edi.dismiss`, `edi.explain` (any message segment by segment in words, for a person or an agent), `edi.generate`, `edi_message.resend`, `edi.pending` (the one report of what waits for somebody), `edi_interchange.content` and `.mark_sent`, `edi_shipment.pack`, `.auto_pack` and `.ship`, `edi.label`, `edi_guide.check`, `.derive`, `.export` and `.import`, `edi_transport.create`, `.update`, `.set_secret`, `.delete` and `.test`, `edi.poll` and `edi.send_pending`. Events for the outbox, and so for webhooks: `edi.unreadable`, `edi.invalid`, `edi.send_failed`, `edi.ack_overdue`, `edi.rejected`.

**Messages.** X12 004010 and 005010: 850, 855, 856, 810, 997 and 999, TA1, then 846, 860 and 820. EDIFACT D.96A, as EANCOM uses it: ORDERS, ORDRSP, DESADV, INVOIC, CONTRL, then INVRPT, ORDCHG and REMADV.

**Deliberately out of scope.**
- Being a VAN or a translator for others: the module exchanges the company's own documents with its own partners.
- A mapping language, scripts or templates in guides.
- Transaction sets of other industries (health care, transport, finance beyond the 820), X12 binary segments, EDIFACT functional groups, security segments and interactive EDI.
- AS1, AS3, AS4, OFTP2 and Peppol; proprietary VAN interfaces (a VAN is reached over SFTP or AS2).
- Web portals of buyers that offer no file exchange.
- Rendering a GS1-128 label as an image or PDF (the label's data and printer text are given).
- A certified AS2 product, for now (see above).
- Buying by EDI (850 out, 855, 856 and 810 in). The readers and writers exist both ways because each writer is checked by its reader; the proposals against purchase orders are not planned yet.

### Party data

What the company, a customer or a vendor is known by outside the books is kept by the crate `erpcraft-party` (module `party`), one schema for all three.

**The decision.** The records themselves stay with the modules that own them: the company with the kernel, customers with sales, vendors with purchasing. Their addresses, tax identifiers and contacts could have been added to each of the three tables by its owner. They are kept in one shared module instead, keyed by `party_type` (`company`, `customer`, `vendor`) and `party_id`, the way account rules are keyed by scope. The reasons:
- the three need the same data in the same shape;
- printing, e-invoices and tax reports read it the same way for whichever party a document names;
- one model and one reader keep it cohesive;
- none of the owning modules has to know about it.

A trigger checks that the party exists, and a row never moves to another party.

**Rights follow the owner.** The tables are not generic entities, so no permission of the party module's own can get around the owner's.
- `party.get` (`party_type`, `party_id`) reads all a party has on record, and `party.set` replaces the parts it is given (`profile`, `addresses`, `tax_ids`, `electronic_addresses`, `contacts`).
- Both first read the owning company, customer or vendor with the caller's rights, its row rules and the company row filter included; a record the caller cannot read is not found.
- `party.set` then requires the owner's own right to change that record: `customer:update` for all companies for a customer or vendor, which all companies share, and `company:update` for that company for the company. The change is in the owner's history.

**No orphans.** A trigger on `company`, `customer` and `vendor` deletes a party's rows with its record, so they never dangle. They never block a deletion either: they hold no foreign key to their owner. A record that something else refers to, such as a customer with orders, cannot be deleted, as before, and its rows stay with it. The account the company is paid into is set to nothing if that account is deleted.

| Record | What | One or many |
|---|---|---|
| `party_profile` | legal name, trading name, commercial register entry, further legal information; for a customer the `invoice_reference` its invoices quote (a Leitweg-ID for a German public buyer); for the company the bank account it is paid into (`payment_account_id`, a bank account of its own); for a customer how its invoices are sent (`einvoice_format`: `pdf`, `zugferd`, `xrechnung_ubl`, `xrechnung_cii`; when unset, a Leitweg-ID, as an electronic address of scheme 0204 or an invoice reference of its shape, or any electronic address other than an email means XRechnung in UBL, anything else a PDF) | one per party |
| `party_address` | `billing` or `shipping`, attention, street and second line, city, post code, region, country | many; at most one default of each kind |
| `party_tax_id` | `scheme` `eu_vat`, `tax_number` (such as the German Steuernummer), `us_ein`, `ca_bn` or `other`, the value, the issuing country | one per scheme |
| `party_electronic_address` | an EAS scheme (EM for email, 0204 Leitweg-ID, 9930 German VAT number, 0088 GLN, a Peppol participant identifier) and the address | many; at most one default |
| `party_contact` | name, role, telephone, email | many; at most one default |

**Reading.**
- `erpcraft_party::load` gives a party's particulars, its default billing address, its tax identifiers by scheme, and its default electronic address and contact.
- `load_readable` gives the same only to a caller who may read the party's record, and nothing to anyone else.
- `document.parties` (`doc_type`, `id`) gives the seller and the buyer of a document: the company and the customer of a sales document, the vendor and the company of a purchase document. A party's data shows only to someone who may read its record; the company is always named. Printing gives the result to every template as `parties`.
- Bank account numbers are not party data: they are banking's `bank_account_number`, the one place they are kept.

**Documents keep the address they were posted with.** A posted invoice prints, and is sent as an e-invoice, with the address it was posted with, even after the customer moves.
- The table `document_party` (party migration 2) holds, per document and `role` (`seller`, `buyer`, `ship_to`), the `party_type` and `party_id` and a copy of what the document shows: the name and particulars, the invoice reference, the account paid into, the address lines and country, the tax identifiers, the electronic address and the contact, and the id of the address it was copied from.
- `erpcraft_party::snapshot` writes one role; `snapshot_sale` (company sells, customer buys at its billing address, goods go to its shipping address) and `snapshot_purchase` (vendor sells, company buys) write a document's. The posting command calls them before it moves the document to a locked state, and the document child guard keeps the copy unchanged from then on: approving a sales or purchase order, posting a sales invoice or delivery, a vendor invoice or a receipt. A credit note keeps the parties of its invoice and a return those of its order (`copy_parties`); when that document kept none, the party's defaults now.
- A sales order may carry the customer's reference for it (`customer_reference`, its purchase order number, at most 100 characters, blank kept as none) and the day the customer asks for the goods (`requested_date`); both are in its summary, so a list can show and filter them. An order drafted from an EDI 850 takes the reference from BEG03 and the date from the requested delivery date (DTM 002), else the requested ship date (DTM 010); the memo keeps the partner, the release, the order's date and its other dates.
- A draft or an order may name one of its party's addresses: `billing_address_id` and `shipping_address_id` on a sales order and invoice, `shipping_address_id` on a delivery, `billing_address_id` (the vendor's) on a purchase order and vendor invoice. Saving refuses an address that is not that party's. An invoice or delivery that names none takes its order's; without one, the default of the kind is copied, and `ship_to` is kept only when the customer has a shipping address. The ids are plain columns, not foreign keys, so a party may still remove an address that a posted document copied; a draft whose address was removed is refused at posting, on the field that names it. The forms choose from `party.get`, which takes `address_kind` to list one kind.
- `party.set` keeps an address's id when it is given back with it (as document lines keep theirs); one left out is removed.
- `document.parties` and the e-invoice export read the snapshot when the document has one, and the party's current data otherwise; `document.parties` adds `ship_to` when the document kept one, and is otherwise as before. What a document kept is never replaced, but what it did not have when it was posted (no address yet, no VAT identifier, no contact) is filled in from the party's data now, so that a document posted before the data was entered can still be printed and sent. The rights are the same: a party shows only to someone who may read its record.
- Documents posted before this existed keep nothing, and show the party's current data.

E-invoicing kept this data in tables of its own (`einvoice_profile`, `einvoice_party`) until the party module existed; its migration 3 moved the rows across and dropped those tables. It added nothing where the party module had a record already.

### Tax by destination

Where a sale is taxed depends on where the goods go: US sales tax by the state, county, city and district shipped to; Canada's GST, HST, PST and QST by the province of supply; in the EU a sale to a consumer in another member state at that state's rate once the seller is past the distance-selling threshold. All three are the same mechanism, kept by the tax ledger (tax migration 12) and configured as data: rate tables, registrations and certificates are rows, not code. Nothing in it names a country.

**The decision.** One mechanism, not three country modules. The three differ only in data: which areas carry which taxes, where the company is registered, and whether only consumers are taxed at destination. A country module could still add its own on top (a return's boxes), but choosing the code by place is shared, because sales and purchasing ask for it the same way whatever the country.

| Record | What | Shared or per company |
|---|---|---|
| `tax_area` | a place and the code charged there: `country_code`, optionally `region` (the subdivision as ISO 3166-2 writes it without the country: `OH`, `BC`, `QC`), a post code range (`postcode_from`, `postcode_to`, compared on as many characters as `postcode_from` has, ignoring case and spaces) and a `city`; the `tax_code_id` (a group of every jurisdiction there, or one code); `valid_from`, `valid_to`; the `source` it was taken from | shared, like tax codes |
| `tax_registration` | where the company charges tax: `country_code`, `region` (none: the whole country), `scheme` (`local`, or `oss` for the EU One-Stop Shop, whose `country_code` is the member state of identification), `number`, `valid_from`, `valid_to`, `consumers_only` (destination tax only for buyers without a VAT identifier; always so for `oss`), and for `oss` the `threshold` | per company |
| `tax_exemption` | a customer's exemption certificate: `customer_id`, `country_code`, `region` (none: the whole country), `certificate_number`, `reason`, `valid_from`, `expires_on`, and the `tax_code_id` its lines take (a code marked `exemption_certificate`) | per company |
| `tax_union_member` | the member states of a union (`EU`), for the One-Stop Shop | shared, seeded |

A tax code gains the jurisdiction it belongs to: `country_code` and `region`, the registration a company must hold to charge it. HST is registered for with the GST, so `CA-HST-ON` is `CA` without a region; British Columbia PST is `CA`, `BC`; a US county's tax is the state's (`US`, `OH`), since nexus is per state. A code without a country is charged by anyone. `self_assessed_code_id` names what the buyer accounts for when the seller does not charge the code (British Columbia PST self-assessed on a purchase from outside the province, US use tax), and `exemption_certificate` marks a code a line may carry only under a customer's certificate.

**Which code a line starts with.** `erpcraft_tax::propose` replaces `proposed_code` for invoices (the credits without an invoice keep the old order) and takes the place as well as the party, item and charge. A line that names a code keeps it.
- On a sale: the customer's rule; else a valid certificate of the customer for the place (`country_code`, and its `region` or none) on the invoice date, whose code the line takes; else the item's rule; else the place's code; else the charge's code; else the company's default. The place is where the goods go: the invoice's `shipping_address_id`, else its order's, else the customer's default shipping address, else its billing address, the same address the posting keeps as `ship_to` or `buyer`.
- The place's code is the most specific `tax_area` valid on the date that matches (a city within a post code range, then a post code range, then a city, then a region, then the country). Of its components only those the company may charge are kept: a component with no country; one whose jurisdiction (country and region, exactly) the company has a `local` registration for on the date, unless that registration is `consumers_only` and the buyer has a VAT identifier (`eu_vat`); or one in another member state of the union of an `oss` registration's country, for a buyer without a VAT identifier, once the company is past the threshold. What is kept is the area's code when nothing was dropped, the single component when one is left, and otherwise the group of exactly those components, found or created (code `A+B`, named by its parts). Nothing kept: no destination tax, and the line falls through to the charge and the default. So a US company without nexus in a state charges nothing there by destination, and a Canadian company registered for GST/HST but not for British Columbia PST charges only the GST in British Columbia.
- On a purchase: the vendor's rule; else the item's; else the place's code, where the place is the company's own (its default shipping address, else its billing address); else the charge's; else the default. Registrations do not matter: the company owes the tax where it is. A component the vendor charges stays; the vendor charges a component when its billing address is within the component's jurisdiction (same country, and same region where the component has one). Otherwise the component's `self_assessed_code_id` takes its place, or it is dropped when it has none. A vendor without an address is taken to charge all of them. A vendor that charges more (an Ontario vendor registered for British Columbia PST) gets a vendor rule.
- **The threshold.** Article 59c of the VAT Directive taxes distance sales of goods to consumers in other member states in the seller's state until they pass EUR 10,000 in the calendar year or the one before. The `oss` registration's `threshold` (in the company's accounting currency; 0: taxed at destination from the first sale) is compared with what the tax ledger recorded: the bases of sales to consumers in other member states of the union, in the year of the invoice and the year before, each year on its own. The sale that crosses it is still taxed at home, since only what is posted counts.

**What is recorded.** Each tax entry keeps the place (`country_code`, `region` of the posting's `ship_to`, else its `buyer`), whether the buyer was a consumer (no VAT identifier on the document; none for a purchase), and the certificate it was exempted under (`exemption_id`). The sales invoice and the customer credit keep their parties before tax is recorded, so the entries read them. A reversal and a credit copy all of it from the entry they take back, so a credit in a later quarter is reported for the place and the certificate of the sale. A line with a code marked `exemption_certificate` is posted only if the customer has a valid certificate for the place on the posting date with that code: an expired certificate refuses the invoice, naming it.

**Reports.** `tax.report` takes `by_place`: then its rows are per code and place (a US state's return, Canada's provincial PST and QST), and they still add up to the tax accounts. `tax.oss_report` (`company_id`, `year`, `quarter`) is the One-Stop Shop return: per member state of consumption and rate, the base and the VAT of sales to consumers taxed there (a code of that member state on an entry for that place), and separately the corrections: credits and reversals posted in the quarter of sales of an earlier quarter, by member state and the quarter they correct. Its total is what the codes' accounts took in the quarter. `tax.exemptions` (`company_id`, `from`, `to`) lists the sales exempted under each certificate: customer, number, place, reason, base.

**Rate tables are imported.** `tax_area.import` (`csv`, the right `tax_area:import` for all companies) reads one row per jurisdiction of an area, with a header: `country`, `code`, `rate` required; `region`, `postcode_from`, `postcode_to`, `city`, `valid_from`, `valid_to`, `name`, `authority`, `registration` (`region`, the default, or `country`: registered for with the country, as HST is) and `source`. The rows of one place and start date, in order, are one area: a code per jurisdiction is created where it does not exist, and refused where it exists at another rate (a rate change is a new code, `US-OH-049-2027`, valid from its date); the area's group is found or created; an open area of the same place that started earlier ends the day before. Given `company_id` with `collected_account_id` and `paid_account_id`, each code the company has no accounts for gets those. Nothing is shipped that a vendor licenses. Free public sources: in the US, the Streamlined Sales Tax Governing Board's rate and boundary files for its member states, and the rate tables the states' revenue departments publish (California's CDTFA, the Texas Comptroller, Washington's Department of Revenue and others); in Canada, the Canada Revenue Agency's GST/HST rates and the provinces' finance ministries, which the Canadian templates cite; in the EU, the European Commission's Taxes in Europe Database and its list of VAT rates applied in the member states. Commercial ZIP code tables are licensed by their vendors and must not be committed.

**The templates.** The Canadian templates carry their areas (each province to its code: HST in Ontario and the Atlantic provinces, GST with PST in British Columbia, Saskatchewan and Manitoba, GST with QST in Quebec, GST in Alberta and the territories), the jurisdiction of each code, the self-assessed PST codes (`CA-PST-BC-SA`, `CA-PST-SK-SA`, `CA-RST-MB-SA`, on the PST payable account and the non-recoverable tax expense) as the counterparts of the provincial taxes, and register the company for GST/HST. A company registered for a provincial tax adds the registration. The US templates add `US-EXEMPT-CERT`, the code a certificate gives; US rates and nexus are the company's to import and set.

Limits: an item rule wins over the place, so taxability that differs by state or member state (food, clothing, reduced rates) needs codes chosen by hand or a rule per item; there are no product taxability categories. The place is read from the address, not geocoded: a post code that straddles a boundary takes the most specific area that matches. Only the sales invoice and vendor invoice look at the place; credits without an invoice, returns and orders do not. Origin-based states (where some intrastate sales are taxed where the seller is) are not modelled. The threshold is the company's own, not that of a group of companies, and is compared only with what was posted before. A vendor's registrations elsewhere are not recorded.

### Intercompany trading

Companies in one database can sell to each other. Each company keeps its own books: the seller's sales order and sales invoice, the buyer's purchase order and vendor invoice, each posted by its own people under its own rights and policies. The module `intercompany` (`modules/intercompany`) saves the typing on the buyer's side and shows where the two sides disagree. It reads and drafts documents only through the document handlers and the command executor, as any module would.

- **Who a party is.** Customers and vendors are shared by all companies. `intercompany_party` says that a customer or a vendor stands for one of the companies (`party_type`, `party_id`, `company_id`; a party stands for at most one). The company's own customer and vendor records stay where they are, so sales and purchasing know nothing of it.
- **A rule per direction.** `intercompany_rule` (per selling company): the customer that stands for the buying company, the vendor that stands for the selling company in the buyer's books, the user of the buying company the drafts are made as (`run_as_user_id`), what to mirror (`mirror_orders`, `mirror_invoices`), and the buyer's receiving warehouse for goods (`warehouse_id`) and account for lines on an account (`account_id`). The buyer's side must be the buyer's: the warehouse and account belong to it, the customer stands for the buyer and the vendor for the seller (checked when the rule is saved). Writing a rule takes the right to change rules in both companies, since it makes drafts in the other one.
- **Mirroring.** A subscriber of the outbox hears `sales_order.approve` and `sales_invoice.post` (after they commit) and, where an active rule covers the document's customer, runs `intercompany.mirror` as the rule's user, through the command executor: that user's rights and the buying company's policies apply, and the audit log shows the draft as theirs. The approved sales order becomes a draft purchase order of the rule's vendor, in the order's currency, each goods line to the rule's warehouse, charge lines with their charge, account lines to the rule's account, prices and discounts as sold. The posted sales invoice becomes a draft vendor invoice with the seller's invoice number as `vendor_reference`: against the mirrored purchase order where there is one (each line on the order line that mirrors its sales order line), otherwise direct, with charge and account lines; goods without a mirrored order cannot be invoiced directly and the mirror is refused. Tax codes are left to the buyer's tax rules. Nothing is posted: the buyer receives the goods and posts the invoice as for any vendor.
- **Once, and visibly.** `intercompany_document` keeps one row per source document: the mirror drafted, or why it was refused (the buyer's policy, a missing right, goods without an order), so a refusal is not retried every hour but shown, and `intercompany.mirror` can be run again by hand once it is fixed. Lines are matched in `intercompany_line`. The two documents are linked (kind `intercompany`): the kernel lets a link join two companies' documents only for that kind, and each reader sees the other side only if they may read it.
- **Balances.** `intercompany.balances` (report "Intercompany balances"), as of a day: for each rule and currency, what the seller has open on the buyer's customer and what the buyer has open on the seller's vendor, in that currency, with the difference, and each side's value in its own accounting currency; and the documents on one side whose mirror is not posted yet, which usually explain the difference. It takes the right to read open items in both companies, and leaves out a pair the reader cannot see whole.
- **Not built:** credit notes, returns, deliveries and receipts are not mirrored; a buying company that is the seller of another rule is fine, but chains (A to B to C) are mirrored one step at a time; consolidation and elimination (see Contracts for later).

### Budgets

The module `budgets` (`modules/budgets`, migration 1) keeps what a company plans to earn and spend, month by month, beside what the general ledger says it did.

**A budget** (`budget`, per company) has:
- a `code` and `name`;
- the year it covers, `starts_on` (the first of a month) to `ends_on` (the last day of a month), at most 24 months, usually the fiscal year;
- a `version`: `original`, `forecast`, or any other name, one of each per company and start;
- optionally the `dimension_id` it is kept by, such as a site or a cost center.

Its lines (`budget_line`) are an account, a month (the first day of it), a value of the budget's dimension or none, and an `amount`:
- the amount is in the account's natural direction, a cost as a positive expense and a sale as positive income, in the accounting currency;
- there is one line per account, month and value;
- an account may be of any type, though a budget is usually of income and expense accounts.

`locked` stops changes to the budget and its lines; an approved original stays as it was approved, and changes go into a forecast.

**Filling a budget.**
- `budget.import` (`id`, `csv`, `replace`) reads lines in either of two layouts:
  - long: `account`, `month` (`YYYY-MM`), `amount`, and optionally `dimension_value` (its code);
  - wide: `account`, optionally `dimension_value`, and a column per month headed `YYYY-MM`.
  Each account and value is named by its code. A month outside the budget, an unknown code, a group account or a value of another dimension is refused, naming the line. `replace` removes the budget's lines first; otherwise the lines given replace those of the same account, month and value.
- `budget.copy_actuals` (`id`, `percent`, optionally `account_types`, by default income and expense, and `from`, by default a year before the budget's start) fills the budget with what the ledger posted in the same months a year earlier, per account (and per value of the budget's dimension), changed by `percent` (+5 for five percent more) and rounded to the currency's cents. It replaces the lines of those accounts. The entries of a year-end close do not count.

**Budget against actual.** `budget.report` (`id`, optionally `from`, `to`, `by_month`, `dimension_value_id`) gives, per account (and per dimension value, and month with `by_month`):
- the budget, the actual (the ledger's entries in the range, in the account's natural direction, closing entries left out), the variance (actual minus budget) and the variance as a percent of the budget (none when the budget is 0);
- whether the variance is favourable: more income, or less cost, than planned;
- totals for income, expense and the result (income minus expense) per month and for the range.

The actual of a dimension value is what the entries carrying it posted, and entries without a value are their own row, as in the other reports. It takes `budget:read` and `gl_entry:read` in the company.

Limits:
- Budgets are in the accounting currency.
- There is no budget check on purchases: a budget reports, it does not stop anything.
- Lines are per month; a week or a quarter is entered as its months.

### Cash flow statement

`gl.cash_flow` (`company_id`, `from`, `to`, optionally `by_month` and `compare`) is the statement of cash flows by the indirect method, worked out from the general ledger.

**Which flow an account is part of.** An account's `cash_flow` (gl migration 12) is `cash`, `operating`, `investing` or `financing`. When it is not set:
- a bank or cash account is `cash`;
- the account of an `asset_cost` account rule (the cost of a class of fixed assets) is `investing`;
- other assets and liabilities are `operating`;
- equity is `financing`.

Income and expense accounts have none: they are the net income. The classification is the company's to correct, for example a loan as `financing`.

**The statement.** For each period:
- **operating:** the net income (income minus expense, closing entries left out), then for each operating account the change in its balance with the sign that cash moves (an increase in receivables lowers cash, an increase in payables or in accumulated depreciation raises it);
- **investing:** the change of each investing account, the same way;
- **financing:** the change of each financing account, the same way;
- the total of each section;
- the net change in cash;
- the cash at the start (the balance of the cash accounts the day before) and at the end.

Every posting balances. So the net income plus the changes of every account that is not cash is the change in cash, whatever the classification, and `reconciles` says that the start plus the net change is the end. The entries of a year-end close are left out throughout, since they only move the result into equity.

**Periods.**
- `by_month` gives a column per month of the range.
- `compare` adds the same range a year earlier, as columns of its own.
- Each row has an amount per column. Each column has its `from` and `to`, its totals, its cash at start and end, and `reconciles`.

Limits:
- The direct method (receipts and payments by kind) is not built.
- Cash equivalents are what is classified `cash`.
- Exchange differences on cash in foreign currency are part of operating changes, not shown on their own.

### Consolidation

`consolidation.report` (module `intercompany`, report "Consolidated financial statements") adds up the books of a group of companies of one database in one reporting currency and takes out what they owe each other and sold each other. It is a report: it posts nothing, and every figure can be traced to the companies' own ledgers.

- **The group.** A `consolidation_group` names a reporting currency; `consolidation_member` its companies (each wholly owned: no minority interests). Reading the report takes `gl_entry:read` in every member and the right to read the group.
- **Accounts.** Members' accounts are added up by account code, so companies set up from one template (or charts kept alike) line up; an account whose code only one member has stands alone. The account's type decides its section. A group chart that maps differing charts onto one is not built.
- **Translation** (the current rate method). Each member's balances are in its accounting currency, translated into the reporting currency:
  - assets and liabilities at the closing rate, the rate on record on `to`;
  - income and expenses of the period (`from` to `to`, closing entries left out, as the income statement does) at the average rate, the mean of the rate on record on each day of the period;
  - equity, and income and expenses before `from` not yet closed to equity, at the historical rate: each entry at the rate on record on its posting date.
  Rates are read with `erpcraft_gl::rate_on_record`, either way round; `rates` in the input overrides the closing and average rate of a currency. A member in the reporting currency is taken at 1. A rate missing is refused, naming the currency and the day.
- **Currency translation adjustment.** What translated assets less liabilities exceed translated equity and results by is the CTA, shown as its own line in equity (per member and in all), so the consolidated balance sheet balances.
- **Eliminations**, per intercompany rule between two members (see Intercompany trading):
  - *Balances.* What the seller has open on the customer that stands for the buyer, and what the buyer has open on the vendor that stands for the seller, as of `to`, each at its carried value translated at the closing rate, are taken off the receivables and payables accounts they are on. Where the two differ (an invoice the buyer has not posted, a payment in transit, a rate difference), the difference is shown, per rule, and carried in equity as "intercompany difference", so the balance sheet still balances.
  - *Trading.* The seller's revenue from invoices and credit notes to that customer in the period (the income entries of their postings), at the average rate, is taken off income, and the same amount off expenses ("intercompany cost eliminated"), so the group's result does not change. Beside it, the buyer's net of the vendor invoices mirrored from those sales invoices and posted in the period: where the two differ, the difference is shown per rule.
  Eliminations are shown each as a row with its two sides, what was eliminated and the difference.
- **Output.** Per account code: the members' balances in their currencies, translated, eliminated and consolidated; section totals (assets, liabilities, equity with CTA and intercompany difference, income, expenses), net income, total assets beside total liabilities and equity; the rates used per member; the eliminations.
- **Not built:** unrealised profit on intercompany goods still in the buyer's stock is not eliminated (the trading elimination takes the seller's revenue against cost as if the buyer had sold everything on); partly owned members, minority interests and equity accounting; a group chart of accounts; consolidation of dimension values; eliminations of intercompany loans, dividends or fixed asset transfers beyond open items; storing a consolidation or its adjustments.

### Setting up a company

`company.setup` turns a template into a company that can buy, sell, post tax and close its year: the company, its chart of accounts with groups and parents, its fiscal years, a warehouse, the purchasing, sales and tax settings, its tax codes, and the default account rules for `inventory` and `stock_variance`. Input: `template`, `code`, `name`, optionally `base_currency`, `first_year`, `start_month` (else the template's), `years` (1 to 5), `periods` (`monthly`, the default: a fiscal period a month, so a month can be closed; or `yearly`: one a year), and `bank_account_code` / `bank_account_name` to name the bank account. It writes through `entity::create`, so every validation and permission of each record applies and the audit log lists every record under the one command; it is one transaction, so a refusal at any point (a company code in use, a shared tax code that exists with another rate) leaves nothing. It needs `company:setup` for all companies and the right to create each kind of record. The output names, per role, the account created: every role the template has, `bank`, `retained_earnings` and the rest, which a payment or a year-end close then uses; the periods by name (`fiscal_periods`: `2026-01` to `2026-12`, or `FY2026`); and `fiscal_years`, each with its `first_period_id` and `last_period_id`, which a year-end close of the year names. A company whose years are one period each divides one into months with `fiscal_period.split_months` (`id`; right `fiscal_period:split`): the period must be open and no year-end close may refer to it; the months take its dates exactly, open, in the same transaction, and what is posted stays where it was, since postings are dated, not filed by period (the period guard lets that one delete through, by a transaction-local setting the command makes). `setup.templates` lists the templates, optionally for one `country`.

A `SetupTemplate` (`modules/setup`) is data: code, name, description, country, currency, start month, the accounts (`code`, `name`, `type`, `group`, `parent`), the account of each role (`bank`, `inventory`, `stock_variance`, `grni`, `payable`, `receivable`, `revenue`, `cogs`, `price_variance`, `retained_earnings`; optionally the account rules `fx_gain`, `fx_loss`, `discount_received`, `discount_given`, `asset_disposal_gain`, `asset_disposal_loss`, `inventory_in_transit`, `absorbed_cost`, `production_variance`, `write_off`, `fx_unrealized_gain`, `fx_unrealized_loss`, and `finished_goods`, an account with no rule of its own, which a company sets on the items or warehouses that hold what it makes), tax codes with the accounts for tax collected and paid and, optionally, their VAT category and exemption reason, whether the buyer accounts for them (`self_assessed`), their jurisdiction (`country_code`, `region`), the code self-assessed instead (`self_assessed_code`) and `exemption_certificate`; the areas each code is charged in (`tax_areas`, shared, kept where they exist) and the registrations of the company (`tax_registrations`); a warehouse, and the sources it was taken from. `SetupTemplate::check` refuses one whose roles or tax accounts are not postable accounts of its chart. Built in:

- `us_small_business`: a US chart in groups (1000 assets to 6000 operating expenses), USD, calendar year, and one flat `US-SALES-TAX` code at 0 %: US sales tax depends on the buyer's jurisdiction, whose rates a company imports (`tax_area.import`) with its nexus (see [Tax by destination](#tax-by-destination)); none are shipped. `US-EXEMPT-CERT` (0 %, category E, for exemption certificates) is the code a customer's certificate gives. `US-EXEMPT` (0 %, category E) is for a sale no sales tax is due on: a resale, an exempt buyer or exempt goods. An example group shows the shape of a combined rate: `US-EXAMPLE-STATE-COUNTY` of `US-EXAMPLE-STATE` (4 %, owed on 2100) and `US-EXAMPLE-COUNTY` (1.5 %, owed on 2110), labelled as examples, not real rates.
- `ca_small_business`: a Canadian chart in groups, CAD, calendar year, GST/HST payable on 2100 and input tax credits on 1350, and the codes `CA-GST` (5 %), `CA-HST-ON` (13 %), `CA-HST-NB`, `CA-HST-NL`, `CA-HST-PE` (15 %), `CA-HST-NS` (14 % since April 1, 2025), `CA-ZERO` (0 %, category Z) and `CA-EXEMPT` (0 %, category E), at the rates the Canada Revenue Agency publishes (cited in the template's `sources`). Where the provincial tax is not harmonized, a line carries a group: `CA-GST-PST-BC` (GST 5 % and PST 7 %), `CA-GST-PST-SK` (GST and PST 6 %), `CA-GST-RST-MB` (GST and RST 7 %) and `CA-GST-QST` (GST and QST 9.975 %, on the price without the GST), with each provincial tax owed on its own account (2110 to 2140). PST and RST paid are expensed on 6130; QST paid is an input tax refund on 1360. The provincial rates are cited from each province's finance ministry and Revenu Québec in the template's `sources`. Each code names its jurisdiction, each province and territory its code (`tax_areas`), the company is registered for GST/HST (`tax_registrations`), and `CA-PST-BC-SA`, `CA-PST-SK-SA` and `CA-RST-MB-SA` are what is self-assessed on a purchase from outside the province (see [Tax by destination](#tax-by-destination)).
- `de_skr03`: the accounts this ERP posts to, and common cost and revenue accounts, numbered as in the DATEV standard chart SKR 03 (verified against the DATEV SKR 03 chart for 2023; the template's `sources` say where), EUR, calendar year, and `DE-USt19` and `DE-USt7` (category S) with Umsatzsteuer 1776 / 1771 and abziehbare Vorsteuer 1576 / 1571. Tax-free sales: `DE-IGL`, an intra-Community supply (§ 4 Nr. 1b UStG, category K, VATEX-EU-IC), and `DE-AUSFUHR`, an export (§ 4 Nr. 1a UStG, category G, VATEX-EU-G), at 0 %, with their revenue accounts 8125 and 8120 in the chart (a tax code does not choose the revenue account). SKR 03 has no account for goods received not invoiced, so 1700 Sonstige Verbindlichkeiten is used. Cost of goods sold and price differences both go to 3200 Wareneingang. In DATEV, 1571/1576, 1771/1776, 3300/3400 and 8300/8400 are automatic VAT accounts; here tax is posted explicitly, so revenue goes net to 8400.
- `us_manufacturer`, `ca_manufacturer`, `de_skr03_manufacturer`: the three charts above with what a company that makes what it sells posts to: raw materials and purchased goods as the default inventory account apart from finished goods (`finished_goods`), goods in transit between sites, the labor and overhead a production order absorbs at standard and its variance against actual, payment differences written off, and unrealized exchange gains and losses apart from realized ones. US and CA: 1300 raw materials, 1310 finished goods, 1320 in transit, 5050 absorbed, 5060 variance, 6160 write-off, 4930 / 6170 unrealized, numbers this template chose. SKR 03: 3970 Roh-, Hilfs- und Betriebsstoffe, 7110 Fertige Erzeugnisse, 8980 Bestandsveränderungen fertige Erzeugnisse (absorbed), 2400 Forderungsverluste (write-off), as SKR 03 numbers them but not checked against the cited edition; 3985 in transit, 8985 variance and 2166 / 2666 unrealized are chosen in free ranges (the template's `sources` say which). No work-in-progress account: a production order books what it makes when it is completed.

**A country module adds a template** without touching `modules/setup`: it carries a JSON file and calls `erpcraft_setup::register(SetupTemplate::from_json(include_str!("fr_pcg.json"))?)` when it is constructed, before the server starts. A code can be registered once. Tax codes are shared by all companies, so a template's codes should carry the country (`DE-USt19`); one that exists with the same rate is reused.

Limits: one revenue account per company, so a German company's 7 % sales also land on 8400 unless the line is posted otherwise; no opening balances (post a journal entry); a company's chart can be extended afterwards but not re-applied from a newer template.

### Printing

A document is printed as an HTML page that the browser prints, and the server makes the same page into a PDF (`document.render_pdf`, below).

`document.render` (`doc_type`, `id`, optional `template_id`) returns `{html, template_id, title}`. The template is the one asked for (it must be active, for the document's type, and for the document's company or for all), else the active default of the document's company, else the active default for all companies, else the one built into `modules/printing`: purchase order, sales order, sales delivery and sales invoice have their own; every other type prints through a generic template that lays out its header fields, collections and summary from the type's description. `print_template.builtin` returns a built-in's source to start from, and `print_template.preview` (`doc_type`, `id`, `body`) renders a template that is not saved, as an editor shows it: the source gets exactly the checks of saving one and the same limits, nothing is stored, and it takes the right to create or change templates.

A print template is a record of `print_template`: `doc_type`, `name`, `company_id` (empty for every company), `body`, `is_default`, `active`. It is written through the generic entity API. Templates are shared records like policy rules: writing one needs `print_template:create` or `:update` for all companies. The database allows one default per document type and company, and one for all companies. When a template is saved, its document type must exist, and its body must compile and contain nothing active (below).

The template language is MiniJinja 3.1. It was chosen because it is maintained, has no dependencies worth naming, is built for templates written by people other than the developers, and in version 3 has fuel that charges for instructions, bytes produced and items visited, checked before an allocation is made, so it bounds both time and memory. A template is given:

- `doc`: the document exactly as `document.get` returns it to the caller (header, `summary`, `created_by_name`, `body`, `postings`, `links`). It is read through `document.get` itself, so the caller must be allowed to read the document.
- `meta`: the type's `label`, `fields`, `collections` and `summary`.
- `company`: `code`, `name`, `currency` and the currency's `decimals`, of the document's company.
- `refs`: for each id the document refers to (links to entities and documents, and lines of other documents, such as the order line of an invoice line), `{display, record}` as far as the caller may read it, read through the kernel's entity and document reads so that row and field rules apply. What the caller may not read is not there, and prints as nothing.
- `letterhead`: the company as it signs its documents: the legal name (else its name), its default billing address, VAT identifier, tax number, US EIN or Canadian BN, register entry and further legal information, the default contact's telephone and email, `bank` (IBAN, account number, BIC and holder of the account it is paid into: party data's `payment_account_id`, numbers from banking's `bank_account_number`) and `logo` (true when it has one). Only to someone who may read the company; anyone else gets its name.
- `title`.

**The letterhead and the logo.** The built-in head prints the letterhead and the foot its register entry, contact and bank. A company's logo is a PNG or JPEG of at most 512 KiB uploaded with `company_logo.set` (base64; the type is told by the bytes, not a name, and anything else, SVG included, is refused), read back with `company_logo.get`, removed with `company_logo.remove`; it is kept in `company_logo` and never fetched from a URL. A template prints it with `<img class="logo" src="#logo">`: the sanitizer keeps only that fragment link, and after sanitising the renderer puts in a `data:` URL of the checked bytes, in the `src` of `img` elements only (text such as a memo that reads `src="#logo"` stays text) and in at most four of them; the page with its logo is refused above 8 MiB. A logo must decode and be at most 4096 pixels across and down; `company_logo.set` is sensitive, so the image stays out of the audit log and the outbox, and it returns the image's size and SHA-256, not the image. An interface that shows the page under a Content-Security-Policy needs `img-src data:` for the logo to show.

**PDF on the server.** `document.render_pdf` (the same input as `document.render`) returns `{data (base64), content_type, filename, title, template_id}`: an A4 PDF/A-3b of the same sanitised page. Options compared, November 2026, with no headless browser and no system program allowed: Typst as a library (Apache-2.0, excellent typography, but it typesets its own markup, so every template would have to be written twice, and it is a large dependency); an HTML and CSS engine in Rust (none is mature enough to render arbitrary CSS faithfully); `printpdf` (MIT, low level, no PDF/A or attachments worth having); and `krilla` (MIT or Apache-2.0, the PDF writer under Typst: fonts subset and embedded, PDF/A-1 to A-4 validated as it writes, embedded files, no unsafe code). The choice is `krilla` 0.8 with a small layout of our own (`printing::pdf`) for the HTML the sanitizer lets through: blocks under one another, the head, parties and foot as columns, tables sized to their content with numbers to the right and the head repeated on each page, headings, grey and bold text, rules, the logo. Fonts are Liberation Sans regular and bold, embedded in the binary (about 800 KiB, SIL Open Font License, `modules/printing/fonts`); text is measured with `ttf-parser` and shaped by krilla. It reads no file and no URL and runs no code from the template: it lays out what the sanitizer kept. It follows elements 40 deep at most, stops and refuses at 500 pages, runs off the request's thread (`spawn_blocking`) and is refused after 20 seconds. Columns that would not fit go to the next page, columns taller than a page are laid out one under another, and a table row taller than a page goes on onto the next pages with the table's head; an image drawn more than once is in the PDF once. The cost of the choice is fidelity to custom templates: a template's own `style` attributes and any CSS beyond the built-in stylesheet show in the browser's page, not in the PDF; the built-in templates print the same in both. **PDF/A-3 is feasible, and is what the PDF is**: `printing::pdf_of` takes attachments, and an e-invoice module can carry its CII XML inside as `factur-x.xml` (association Alternative) to make a ZUGFeRD / Factur-X invoice; what remains for that is the Factur-X XMP extension schema, which krilla does not write yet.

Money and quantities are exact decimal strings. Filters format them without floats: `money` (the currency's places, or `money(n)`), `price` (a unit price: at least the currency's places, at most six), `decimal` (trailing zeros dropped, or `decimal(n)`), `mul` (an exact product, such as quantity times price), `date` (`15 Mar 2026` by default: day, month in letters, year, which reads the same in every country where `03/04/2026` does not; there is no locale on a company yet; or `date("%Y-%m-%d")`), `ref` (what tells a person which record an id is, such as `WIDGET Widget`; `ref("short")` gives only its first part, the code, for a narrow column), and `show(field)`, which formats a value as its field's description says (`show(field, "short")` for a reference by its code). The generic template prints the first reference of each line in full and the others by their code.

Every rendered page goes through a real HTML sanitizer, `ammonia` 4.2 on the `html5ever` parser, with an allow-list for printed documents: text, headings, tables, lists, `div`/`span`/`section`, `img` and `a`; the attributes `class`, `style` (only layout and type properties, none that can load a URL), `title`, `lang` and `dir`, cell spans, and `href`/`src` that are `http`, `https`, `mailto` or a `#fragment`. Scripts, event handlers, frames, objects, forms, `base`, `meta`, `link`, `style` elements, `svg` and `math` are removed, with the content of `script`, `style`, `title` and `textarea`. A template writes the page's body; the server wraps it in a fixed head with the title and the one built-in stylesheet, so a template styles with the stylesheet's classes and `style` attributes. When a template is saved, a scanner still refuses what will not work, with a message for whoever wrote it; safety rests on the sanitizer, not on that scanner.

What is guaranteed:

- A template reaches no data beyond what the caller may read: `document.get`, the entity and document reads under the caller's rights, and the code, name and currency of the document's company. It cannot read files (MiniJinja is built without its loader, and without `include`, `import`, `extends` and macros), reach the network, or call anything in the server but the formatting filters.
- Whatever it prints is escaped for HTML. The `safe` filter is removed and `{% autoescape %}` is refused, so a memo or a vendor name with markup is text.
- A render is bounded: fuel of 2,000,000 per render, recursion depth 50, and the page at most 4 MiB. A runaway template ends with an error, not a busy server.
- No active content: whatever a template or the data in it makes, the sanitizer keeps only the allow-list above, as a browser's own parser would read the page (raw-text elements, bogus comments, character references without a semicolon and the rest).
- A template asked for by id that cannot print this document (another company's, another type's, inactive, or none) gets one answer, which says nothing about it. References are resolved once per distinct record per render, at most 2,000 per render.

What it relies on: the interface shows the page in an iframe with `sandbox` and without `allow-scripts` (and without `allow-same-origin`), as a second wall in case the check above misses a construction a browser would run; and the people who may write templates are trusted not to make a page that misleads, since a template decides what the page says.

### Mail

`document.send` (`doc_type`, `id`, optional `to`, `cc`, `subject`, `message`, `template_id`, `format`) sends a document by email: a sales invoice or credit note in its customer's `einvoice_format` unless `format` says otherwise (a ZUGFeRD PDF from `einvoice.export_pdf`, or the XRechnung XML alone from `einvoice.export` in UBL or CII, profile XRechnung when the customer has a buyer reference, else EN 16931; refused if the e-invoice does not hold), any other document as the PDF `document.render_pdf` makes, to the contact email (else the email electronic address) its party has on record unless addresses are given, at most 20. It takes the right to read the document and the right `<doc_type>:send` (such as `sales_invoice:send`: reading a document is not sending it), and asks the company's policy `document.send` (facts: `doc_type`, `locked`, `recipients`, `to_party_only`, whether every address is the party's own on record). By default a draft is refused and so is any address the party does not have on record; a company allows more with an allow rule, for example with approval when `!facts.to_party_only`. The message is recorded on the document in `document_message`: addresses, subject, text, the PDF, who sent it, its Message-ID (`<id@erpcraft>`), and its status; `document.messages` lists them. It leaves after the command commits: the outbox's subscriber `mail` hands it to the company's server, and a failure leaves the event to be retried with the outbox's growing delay, up to 8 attempts, after which the message is `failed`. Each company names its server with `smtp_settings.set` (host, port, `starttls`, `tls` or `none`, user, from address and name, reply-to, a bcc for its own record) and reads it with `smtp_settings.get`. The server must resolve to public addresses only, checked when it is set and again before each message is sent, unless the installation sets `ERPCRAFT_MAIL_ALLOW_PRIVATE=1` (a relay on the same host, development). A password on record is cleared when the host, port, user or security changes and none is given with it, so nobody can send it somewhere else; it is kept as given, untrimmed. The server's answer to a failure shows in `document.messages` only to someone who may change the company; other readers see that it failed. A server has 10 seconds to answer; the password is `writeOnly`, kept in `smtp_secret`, which no generic read reaches, never returned, and the command is marked sensitive so its input stays out of the audit log and the outbox. Mail is sent with `lettre` (MIT) over rustls.

### Policies

Two kinds of refusal look alike and are not.

- An **invariant** is true for every company: a posting balances, an entry is never edited, a posting is reversed at most once, stock does not go below zero. Breaking one would make the books wrong. Invariants are compiled in, and where they concern a ledger they are the ledger's database triggers.
- A **policy** is a business judgement that a careful company could make either way: whether to accept a delivery of a few percent more than was ordered, or a vendor invoice above the order price. A policy is configured by the company, with expressions, and needs no rebuild.

The rule of thumb for a module author: if a careful company could reasonably want it otherwise, it is a policy point, with today's behaviour as its default. If breaking it would make the books wrong, it is an invariant and belongs in the ledger's triggers.

**A policy point** is declared in code by the module that makes the judgement (`Module::policies`): a name, a description for people and agents, the facts the module supplies with their types (a number, a text, true or false, or a list of texts that a condition tests with `in`), the decision when nothing is configured, and the words for a refusal.

```rust
PolicyPoint::new("purchase_receipt.over_receipt", "Asked for every line of a purchase receipt ...")
    .number("ordered", "Quantity ordered on the order line")
    .number("over_by", "By how much the line would be received beyond the quantity ordered ...")
    .number("over_percent", "over_by as a percentage of the quantity ordered")
    .refuse_when("facts.over_by > 0")
    .refusal("more would be received than was ordered")
```

The registry refuses a point declared twice, a fact declared twice, and a default that does not parse or reads a fact the point does not declare. Points are part of `meta.describe` (`policies`), so an interface or an agent can find what can be configured and which facts each condition may read.

**A policy rule** is a record of the entity `policy_rule`, managed like any other record:

```json
{ "company_id": "…", "point": "purchase_receipt.over_receipt", "effect": "allow",
  "condition": "facts.over_percent <= 5", "priority": 10 }
{ "company_id": null, "point": "purchase_receipt.over_receipt", "effect": "refuse", "condition": null,
  "message": "at most 5% more than ordered is accepted, not {over_percent}%", "priority": 20 }
```

`effect` is `allow` or `refuse`. `condition` is an expression over `facts` and `user` (the same `user` as in permission rules: the attributes, plus `id`, `email` and `name`); null means always. Without a `company_id` the rule applies to every company. `message` is what the user is told when the rule refuses, and `{fact}` in it shows a fact. A rule is checked when it is saved: the point exists, the condition parses, and it reads only facts that point declares. Because the condition is checked against the point, `point` and `condition` are sent together, on a change as well.

**Deciding.** The module asks at the moment of the judgement, inside its command: `ctx.decide(point, company_id, facts)`, or `ctx.policy(point, company_id)` once and `evaluate(facts)` for each line of a document. The active rules of the point that apply to the company are looked at in order of `priority`, lowest first; at the same priority a company's own rule comes before one for all companies. The first rule whose condition holds decides. If none does, the point's default decides. A refusal is a validation error with the rule's message, or else the module's own words.

- **Nothing undecidable loosens anything.** A rule whose condition cannot be worked out (a user attribute that is missing or null, a text compared with a number, a division by zero) does not match if it would allow, and does match if it would refuse. It is logged. This is the stance the permission rules take.
- **An administrator is subject to policies.** Permission rules say who may do what, and an administrator may do everything. A policy says how the company works, and that holds whoever asks.
- **Numbers in conditions are floating-point numbers**, including quantities and prices that are exact decimals everywhere else. That suits a threshold or a percentage. A condition decides whether something may happen; it never produces an amount.
- A module supplies exactly the facts its point declares. Anything else is an internal error, not a refusal: it is a mistake in the module.

By default only approving an order for an inactive party is refused; what was ordered before can still arrive, go out and be invoiced.
- `purchase_order.closed` and `sales_order.closed` are asked when a receipt, delivery or invoice is drafted or posted against a closed order; `complete` tells an order that closed by itself from one closed short by hand. A draft or cancelled order is never referred to: its lines can still change, or it never happened. Allowing it keeps the books and the order's progress right: the goods are counted on the order's lines like any others, valued at the order price, and owed for in goods received not invoiced. The order stays closed: posting against an order never reopens it (only a reversal that leaves it with goods not yet invoiced does, as before). By default an invoice is let through for what a closed order holds received and not invoiced, which before these points it never held, so that goods a company let in can always be invoiced.
- `posting.date` is declared by the kernel and asked by `document::create_posting` and `document::reverse_posting`, so every posting of every module is asked, reversals with `reversal` true. `days_from_today` is the posting date minus today in UTC. It does not replace the closed-period guard, which is an invariant.
- `production_order.inactive_bom` is asked when a production order is released; `tax_code.use` for every invoice line with a tax code when the invoice is posted (`erpcraft_tax::quote`). A draft shows tax with `erpcraft_tax::estimate`, which asks nothing.

Cancelling an order after goods were received or delivered against it stays refused, as an invariant: cancelled means the order never happened, yet the goods would remain in stock and in goods received not invoiced (or out of stock and in cost of sales) with no order left to invoice them against. Closing the order is the way to stop it; with `purchase_order.closed` a company decides what may still follow a closed order.

`stock.negative` is declared by the stock ledger and asked by `erpcraft_stock::post` for every issue that would take a level below zero. `context` says what is taking the stock out (`sales_delivery`, `production`, `adjustment`, `transfer`), so a company can let deliveries run ahead of receipts and still hold production to what is on hand. It is the one point whose decision a ledger checks again: the entry carries the rule that allowed it and the facts it was asked with, and the trigger refuses an entry that names no rule, one that is not such a rule, or facts that are not those of the movement. The trigger cannot evaluate the condition; it copies it onto the entry instead.

Where a company allows it, an order line can be received (or delivered) beyond its quantity. The goods come into stock at the order price like the rest, and what was received can be invoiced. An order line is **complete** when at least the quantity ordered has been received and everything received has been invoiced; so an over-received order stays open until the extra goods are invoiced too, and then closes by itself. The database no longer refuses a line received beyond its order: that was a judgement. It still refuses invoicing more than was received, and leaving value in goods received not invoiced: those keep the books right.

### Approvals

A policy rule has a third effect, `approve`: where it decides, the command does not run yet. It waits until enough other people have approved, and then runs as the person who asked, with exactly the input they gave. Because it is an outcome of the policy, every policy point has it, and no module does anything for it.

```json
{ "company_id": "…", "point": "purchase_order.approve", "effect": "approve",
  "condition": "facts.total_net > 10000", "approver_permission": "purchase_order:approve_large",
  "approvals_needed": 1, "approval_days": 14,
  "message": "an order of {total_net} {currency} needs a controller's approval" }
```

Who may approve is `approver_role_id` (holders of that role for the request's company or for all companies), `approver_permission` (whoever holds that permission for the company; any name, it need not belong to a command), or both, either sufficing; a rule with effect `approve` must name one, and only such a rule may. `approvals_needed` distinct people must approve (1 to 10, default 1); `approval_days` is how long the request waits (default 14). An administrator may approve any request; nobody, administrators included, may approve their own. An undecidable `approve` rule matches, like a refusal: nothing undecidable loosens anything.

**The pending response.** A command that needs approval answers HTTP 202 Accepted (over MCP: the tool result, `isError` false, with the same object as `structuredContent`):

```json
{ "status": "pending_approval", "preview": false,
  "approval_request": { "id": "…", "command": "purchase_order.approve", "point": "purchase_order.approve",
    "message": "an order of 20000.0000 USD needs a controller's approval",
    "facts": { "total_net": "20000.0000", "currency": "USD", "lines": "1" },
    "approvers": { "role_id": null, "permission": "purchase_order:approve_large", "approvals_needed": 1 },
    "expires_at": "2026-03-29T…Z" } }
```

`facts` are the facts as a person reads them, all text. `status` is the one key to look at: no command's own result has `status: "pending_approval"`. Asking again (the same person, command and input, or the same idempotency key) while the request is pending answers with the same request. A preview of such a command answers 200, `{"preview": true, "result": <the object above with "preview": true and "id": null>}`, and creates nothing.

**Recording.** The command's transaction is rolled back and the request is kept in `approval_request`: company, command, input, who asked and when, the idempotency key, the point, the rule, the facts it decided on, the rule's approvers, and `expires_at`. The audit log has the asking as a command with outcome `error` and code `pending_approval`, and the outbox has `approval.requested`.

**Deciding.** `approval.list` (scope `to_approve`, the default: pending requests the caller may approve; `mine`: the caller's own; `all`: with `approval:read` for all companies), `approval.get`, `approval.approve` (`id`, optional `reason`) and `approval.reject` (`id`, `reason` required). A person decides a request once (`approval_decision`); someone who may not approve it is refused, and one who cannot see it is told it does not exist. Each decision is an outbox event, `approval.approved` or `approval.rejected`. A rejected or expired request is final; the command can simply be asked again, which makes a new request.

**Running.** The approval that makes up the number needed runs the command, inside `approval.approve`'s transaction, behind a savepoint:

- as the requester, with the recorded input, after checking their permission for it again;
- with approval granted for that point and those facts: when the command asks the point again, a rule that would ask approval allows instead. If the facts are no longer the same (the order was edited, an amount changed) the approval does not apply, the run is refused and the request is marked `stale`;
- once: the request moves to `executed` with the command's result stored on it, or `failed` (with the error) when the command refused. The decision stands either way. A second approval of a request that is no longer pending is refused (409);
- audited as the requester's command, with the approval request among its subjects, next to the approver's `approval.approve`, so a record's history shows both; its outbox event (topic: the command) carries `approval_request_id` and `approved_by`.

**Delegation.** Someone away hands their approvals to someone else for a span of days: `approval.delegate` (`delegate_id`, `starts_on`, today by default, `ends_on`, `reason`), `approval.delegations` (what the caller gave and was given, not yet ended) and `approval.end_delegation` (by the person who gave it: it is kept and marked `ended_at`, and counts no more from then; one in force since before today keeps yesterday as its last day, one not yet begun never lasted). Days are UTC days, for its first and last day and for whether it is in force. While it is in force, the delegate may decide what the delegator could decide in their own right, and the decision is recorded as the delegate's with `on_behalf_of` the delegator. It counts as the delegator's: a unique index allows one decision per person whose right it is, so nobody is counted twice, in person and by proxy. What the delegate could decide in their own right they decide as themselves. A delegation is followed one step only, a requester's request is never decided on their behalf, a delegate signed in with a scoped token decides nothing by delegation, and a deactivated delegator's delegations stop counting. Delegating hands on the giver's whole standing as an approver, whatever their roles (an administrator's included), so it takes `approval:delegate` (in any company), a token limited to some permissions cannot do it (as it cannot hand on a role), and a delegation counts only while its giver still holds `approval:delegate`.

Statuses: `pending`, `executed`, `failed`, `stale`, `rejected`, and `expired`, which is a pending request past `expires_at` (shown so; the row stays `pending`).

**What cannot be approved.** A point declared `.not_approvable()` refuses a rule with effect `approve` when it is saved. `stock.negative` is one: its ledger checks the deciding rule again in a trigger, and an approval would not be a rule the trigger knows. Invariants are not policy points at all, so nothing a ledger forbids can be approved into the books.

The points that ask for approval in practice: `purchase_order.approve` (asked when an order is approved, after the vendor check; default allow), `payment.post` (asked when a payment is posted, `amount` being what it pays out or takes in, allocations plus on account; default allow), and any refusing point whose refusal a company would rather turn into a question, such as `vendor_credit_note.without_return`.

## Contracts for later

Recorded now so that later work does not break them.

**The module boundary.** Modules in this repository use only the public module API, as an outside module would. If the reference ERP needs something the API lacks, the API grows. Compiled modules are trusted server code: the module API is an architectural boundary, not a security sandbox.

**Module upgrades.** A module's name owns its migrations and must never change. Today the registry checks only that a module's dependencies are registered before it. Still to define: version compatibility between a module and the kernel API, and disabling a module while its historical documents stay readable.

**Configuration is not code.** New behavior is a Rust crate. A custom field, an approval threshold, a numbering series or a print template must not need a rebuild: these will live in the database and extend the registry at startup. Print templates and policy rules already do; see [Printing](#printing).

**Cross-module flows are the real test.** The purchasing flow is the first: purchase order → partial receipts → vendor invoices, across three documents, two ledgers and three modules, with each step reversible. It needed one addition to the kernel, document links. Still missing from it is the return of goods after they were invoiced.

**Agents at scale.** A full ERP will have hundreds of commands. `meta.describe` already takes a module name so an agent can load one module at a time, and the MCP tool list leaves out commands the caller can never run. Two discovery tools (`erpcraft_modules`, `erpcraft_tools`) let an agent load the tools of one module or for one resource instead of the whole list. What a module is for is still derived from what it holds; a module has no description of its own to show.

**Rules and scripts are separate decisions.** Rules use CEL, behind `erpcraft-rules`, so the engine can be replaced; stored rules would then need converting. The script engine is not chosen.

- A *rule* is one expression: a row permission, a list filter, a validation, an approval threshold, a computed value. Rules that filter lists must compile to a SQL `WHERE` clause, so the engine must expose its syntax tree and must not allow loops.
- A *script* is custom logic that runs without a Rust rebuild. It must be sandboxed.
- Whatever is chosen goes behind its own crate, so the kernel never depends on an engine directly.

Four engines were compared hands-on in November 2026 (CEL, Rhai, Cedar, Monty). The results and the test code are in [docs/research/2026-11-rule-engines](docs/research/2026-11-rule-engines/README.md).

**Several sites.** Decided 2026-11-18; built (see Dimensions under the general ledger's rules, and Sites and the location tree and Transfers in two steps under the stock ledger's). A company with several plants needs to know where things are and where money was made. These are two separate questions, answered by two structures. Both are modelled on what SAP Business One, ERPNext, Odoo and Business Central have in common.

- *Where money is: dimensions, not account segments.* A company defines its dimensions (site, cost center, project, ...) and their values. Every general ledger line points to an immutable **dimension set**, one row per distinct combination, so the same combination is stored once and reports group by set. The chart of accounts stays one chart: no account code carries a site, as `4000-OH-01` would. Nobody types dimension values in normal work. `dimension_for(scope)` fills them in beside `account_for`, from the most specific scope first: warehouse, then item, party, account, then the company default. Which combinations are required, allowed or blocked is the policy `gl.dimensions`, not code. A reversal copies the set exactly. Reports (trial balance, income statement, balance sheet, account ledger) filter and group by dimension. A posting is **not** balanced per site: there are no automatic due-to and due-from lines. So the income statement per site is exact, and a balance sheet per site is only as good as the postings that happen to stay within one site. This is deliberate. Most of the systems compared do the same, and balancing per site can be added later without changing the dimension set.
- *Where goods are: a location tree.* A **site** belongs to one company and carries its default site dimension value. A warehouse names its site and, optionally, a parent location, so a site holds warehouses and a warehouse holds locations or bins. Access rules read `user.sites` as they read `user.warehouses` today. Sites and the tree live in a module; the kernel knows nothing of them.
- *Goods between sites travel.* A transfer between sites is two steps. Shipping moves the goods into an in-transit location at the source's cost. Receiving moves them into the destination, in parts if they arrive in parts. Goods in transit are stock with their own inventory account (account rule `inventory_in_transit`), so the general ledger still equals stock value while the truck is on the road. Planning counts them as on their way to the destination. A transfer within one site stays one step.

**Trading between companies.** Decided 2026-11-18; built (see Intercompany trading). Companies of one database that sell to each other (Ohio Widgets Inc. to Ohio Widgets GmbH) trade through the ordinary documents: one company's sales order and invoice, the other's purchase order and vendor invoice. The module `intercompany` drafts the other side, never posts it, and reports where the two sides differ.

**Consolidation.** Decided 2026-11-18; built (see Consolidation). A report over a group of companies in one currency, translated and with intercompany balances and trading eliminated. It posts nothing: no company's books change, and there is no ledger of the group.

## Known gaps in what is built

- Manufacturing: the upgrade from separate materials and finished goods accounts gave each product of an existing bill of materials its own account rule. A bill created later posts its product to the company's default inventory account unless an account rule is added for that item; nothing remembers that the company kept finished goods apart.
- An outbox pass keeps one database connection for its whole length while each handler may use others, so a slow subscriber with a small pool can make requests wait.
- The guard on stock levels stops plain SQL from changing them, but not another database trigger.
- Webhooks: a webhook that keeps failing is retried without limit, at most hourly per event, until it is fixed, deactivated or deleted; nothing switches it off by itself. Events that pass while a webhook is inactive are not sent later, and there is no way to send an event again by hand. Secrets are not encrypted in the database. Delivery to a message broker is not built; it would be another subscriber. The refusal of an address does not say why, but how long it takes still can: a name that does not exist may answer at another speed than one that leads inward. The list of blocks that are not globally reachable is compiled in and follows the registries only with a new release; a Teredo address is refused even where what it carries is public.
- A refused stale edit does not say what the other person changed.
- A caller that sends no `_version` when updating or deleting a plain record is not checked for staleness.
- A plain record can be deleted only while nothing refers to it. There is no way yet to retire a record that is in use, such as an account that should take no new entries, except where its entity has a field for it.
- Payments: a payment settles items of one party; money on account is a credit of that party, applied to its invoices by hand (`payment.apply_credit`), nothing applies it by itself. A small difference left of an item is written off with the payment (`write_off` on an allocation, to the account for `write_off`), as far as the policy `payment.write_off` allows (nothing unless configured); it is written off gross, without taking back the tax on it. An early-payment discount is taken only with the payment that settles the rest of the item, up to what the item's terms offer; a credit note posted after a discount was taken credits the invoice line's tax as far as the discount left any, but its own amount is not reduced by the discount. Instalments: a part's discount is not built, so there is no discount per instalment. A credit note reduces the earliest parts first, like an unnamed payment, not the last. `payment.draft` proposes the whole item, not the part falling due. The e-invoice export states only the last due date and no terms per part (BT-20 text). An invoice's parts follow its terms; they cannot be set by hand on one invoice. Aging counts a payment on account, which has no due date, as due on its date.
- Tax: tax rules propose a line's code from its party, item or charge or the company's default, and on sales and vendor invoices from the place the goods go (see the limits under [Tax by destination](#tax-by-destination)); a line cannot say "no tax" where a rule proposes one (it takes a 0 % code instead). A rule for a record that was deleted stays and matches nothing. A rate change means a new code. Tax-inclusive prices are not there. Tax the buyer accounts for is a property of the code: the place chooses it only as the counterpart of a tax a vendor outside its jurisdiction does not charge (self-assessed PST, use tax); nothing chooses an EU reverse charge from the parties' VAT identifiers, and the tax report shows it under its code, in both directions, without boxes of its own (a country module maps codes to a return's boxes). An early-payment discount on an invoice with such tax does not reduce the tax the company assessed. The VAT category (S, Z, E, AE, K, G, ...) is a property of the code too, chosen with it: nothing checks that a K buyer is a business in another member state or a G buyer outside the EU, and no Zusammenfassende Meldung (EC sales list) is built for K sales. The tax representative (BG-11) is not supported, so K and G need the seller's own VAT identifier. Orders carry no tax, only invoices do.
- Sales: a customer credit (`sales_credit`) has no discounts of its own and is not sent as an e-invoice; its tax is taken back at the code's rate today, not at what any invoice charged. The same holds for a vendor credit (`vendor_credit`).
- Returns and credit notes: the facts of a credit without return are about one line, not the whole credit note or the party. A return of goods that are no longer on hand goes through the stock ledger like any issue, so the company's `stock.negative` policy decides (context `purchase_return`). `purchase_order.awaiting_credit` and `sales_order.awaiting_credit` list goods returned after they were invoiced and not yet credited, per order line, at the order line's price (before discounts and tax). Over-receipt is judged against what was received and kept, so replacements for returned goods are not over-receipts.
- Purchasing and sales share about 250 lines of near-identical order-progress code. It should move into a shared crate once a third order-like document shows what is really common.
- Purchasing: A credit note for a landed-cost charge credits price variance (or `landed_cost_variance`) and does not take the cost back out of the stock it raised. A landed-cost invoice cannot be reversed once the goods it raised have all left the warehouse. A receipt can be reversed only before its invoice (afterwards goods go back with a purchase return); goods are invoiced only after they were received: an invoice before receipt needs an account for goods invoiced not received and a way to clear it against the receipt, which is an accounting feature, not a policy switch. Accounts come from one settings record per company.
- Exchange rates: a posting uses the rate it states, or else the latest rate on record for that date, recorded either way round (`erpcraft_gl::rate_on_record`: a rate from the accounting currency to the document's is inverted, rounded to 10 decimals; of the two directions the later dated applies). Rates are entered by hand; cross rates through a third currency are not inferred. A rounding difference in a journal entry needs an explicit line.
- Foreign currency: open items are revalued at a period end (`fx_revaluation`, reversed the next day), but foreign bank balances and other monetary balances are not. The reversal is dated the day after the revaluation, which is the first day of the next period only when the revaluation is dated at a period end. A payment in one foreign currency for items in another, or a bank charge taken out of a foreign payment, is not built. Purchase price variance includes the exchange difference between receipt and invoice. Non-recoverable tax and freight are not added to the cost of goods. The stated rate on a receipt applies to all its lines; a receipt in parts at different rates averages the value in GRNI per order line.
- Payment runs: positive pay files (the list of checks issued, for the bank to match) and check printing are not built, so a run pays by bank transfer only. Canadian CPA-005 files are deferred (see Paying vendors in a run). A run pays in one currency through one bank account; vendors in other currencies need runs of their own. SEPA files are SEPA credit transfers only (no urgent or cross-border non-SEPA payments, no structured creditor reference), and the text is written as given, not reduced to the SEPA character set. A NACHA file holds one batch of credits (no debits, no IAT for payments abroad) and is not balanced by an offsetting entry; the bank's own requirements (immediate origin, destination name) beyond what `bank_account_number` holds are not configurable. A bank file is written again on request and nothing records that it was handed over. Remittance advice is the payment's PDF from the generic template, listing its allocations; a vendor without an email address is skipped and listed. A run's lines take the items' open amounts when proposed; an item paid elsewhere before the run posts makes the payment refuse it, and the whole run with it.
- Consolidation (`consolidation.report`): a report, never stored; members are wholly owned; accounts are added up by code, with no group chart to map differing charts; unrealised profit on intercompany goods still in stock, intercompany loans, dividends and asset transfers are not eliminated; the trading elimination takes the seller's revenue off income and the same amount off expenses, so a difference between the seller's revenue at its average rate and the buyer's cost at its own shows in the consolidated expenses and in the trading difference; the average rate is the plain mean of the daily rates on record, not weighted by activity; equity is translated at the rate of each entry's day, which for a year-end close is the year's last day, not the rates its results were earned at.
- Intercompany: companies trade through their own documents (see Intercompany trading); a posting never spans two companies, and there is no consolidation or elimination. Only approved sales orders and posted sales invoices are mirrored, once each: a sales order changed or an invoice reversed after its mirror was drafted does not change the draft, which the buyer then fixes or deletes by hand (once deleted, `intercompany.mirror` drafts it again). Credit notes, returns, deliveries and receipts are not mirrored. The buyer's vendor invoice takes its tax from the buyer's tax rules, so a difference in tax between the two sides shows only in `intercompany.balances`. The balances compare open items per currency; they do not set the seller's revenue against the buyer's cost. A refused mirror is not retried by itself. Writing a rule takes `intercompany_rule:update` in the buying company whatever was asked in the selling one.
- Sites and transfers in two steps: goods in one transit warehouse are valued at its moving average, so two shipments of the same item at different costs waiting in it at once arrive at their average, not each at its own cost (the general ledger still equals the stock ledger; one transit warehouse per pair of sites keeps it apart). A transfer receipt cannot add freight or other landed cost. Nothing dates the arrival: planning counts goods in transit as coming in, whenever. A transfer closed short is final. A warehouse's site and place are fixed while it holds stock. A stock level and a reservation carry no site of their own: rules by site apply to warehouses and stock entries.
- Dimensions: a posting is **not balanced per dimension**, deliberately: there are no automatic due-to and due-from lines between sites. A receipt, a delivery or a stock movement takes the warehouse's site on both of its sides and stays within one site; an invoice's receivables or payables line takes the line's warehouse when it has one, else the party's and the company's defaults; a payment's bank line takes the party's. So the income statement per site is exact, and a balance sheet per site is as good as the postings that happen to stay within one site. Balancing can be added later without changing the dimension set. Values are stated by hand only on journal entry lines; invoice, credit and charge lines take their defaults (a rule for the charge, the item, the party). The journal line's `dimension_value_ids` is a list of ids with no picker of its own in the generic forms yet. A foreign-currency revaluation posts per account, so its lines take only the account's and the company's defaults. Changing a dimension rule does not move value already posted: stock on hand keeps the values it came in with until it moves, so for a time the general ledger per value can differ from what the rules would now give the same stock. The policy sees one line, not the whole posting.
- Year-end close: a year kept as several periods (months) is closed in one step by naming its first period (`first_period_id`) beside its last: the income and expenses of every period from the first to the last are closed together, dated the last day of the last, and every period in between is closed with it. Reversing the close needs only the last period reopened; the earlier ones stay closed until someone reopens them. Two closes in effect never cover the same date: a close is refused while another that is not reversed covers any period of its range (its first period's start to its last period's end), and that close must be reversed first. The other design, letting a close take only what no close covers yet, was not chosen: a close reads balances up to its own last day, so it would have to find and leave out the entries of closes dated after it, and a month reopened inside a closed year would then be closed by two documents whose sum is the year. With the refusal one close in effect is the whole result of its dates, and changing a closed year means reversing its close, correcting, and closing it again. Nothing records which periods make up a fiscal year, so the person closing names them. The whole result goes to one equity account, per dimension set (see Dimensions); there is no split across several equity accounts. An income or expense account that has a balance and was made inactive must be reactivated first. Reports recognize closing entries by the command name on their posting (`year_end_close.`), and `gl.trial_balance` and `gl.account_ledger` show them like any other entry. Closing a later year does not check that the earlier ones are closed.
- Manufacturing: one step, one warehouse. Labor, machine time and overhead are absorbed at standard: an activity (`cost_activity`, shared) has a rate per company (`cost_activity_rate`), a bill says how much of each activity a run takes (`bom_activity`), a released order copies them scaled to the order at the rates then in force (`production_order_activity`), and completing it brings the product in at its components plus each activity's quantity times its rate, credited to the account for `absorbed_cost` (by activity, else the company's). That account must not carry stock: completing an order is refused when it is the product's or a component's inventory account or any account an `inventory` rule of the company names, since the product's account would take the credit back and stock would be worth more than the ledger says. Work centers and routings (module manufacturing, migration 4): a `work_center` belongs to a company (optionally a site, a plain id until sites land), charges its time at a cost activity's rate and can work `hours_per_day`. A bill's routing (`bom_operation`: step, work center by code, since bills are shared and work centers are not, setup hours per order and run hours per unit) is copied onto a released order (`production_order_operation`, the hours for its quantity at the rate then), which refuses a company without a work center of that code or one without a rate, and asks the policy `production_order.inactive_work_center` (facts: `work_center_code`, `active`; an inactive one refused by default) for each operation. Hours that cannot be counted (run time times quantity beyond 10^12) are refused. Completing the order absorbs the standard hours into the product like the bill's activities; actual hours are recorded with `production_order.record_time` while it is released (negative to correct), and for an operation whose net recorded time is not zero (time recorded and taken back again counts as none) the difference from standard, at its rate, is posted to the account for `production_variance` (by work center, then item, then the company's) against the absorbed cost account, outside the product's value. An operation with no time recorded counts as standard. Neither the absorbed cost account of a routing nor the production variance account may carry stock (an inventory account, the product's or a component's): completing the order is refused, as for the bill's activities. `work_center.load` gives each work center's capacity and the standard hours still to work, day by day; an order is planned on its date, with no lead times, finite scheduling or operation dates of its own. overhead as a percent of material is not built. An order whose component quantities do not come out to 6 decimals is refused at release. A completed order cannot be reversed once any of the product has been used.
- Reports that total a ledger (trial balance, balance sheet, income statement, stock on hand, tax report) are refused to a user whose right to read that ledger depends on a row condition, because a total cannot honour it.
- Single sign-on: nothing limits how often sign-in can be tried, by password or through a provider, and the record of sign-ins (`auth_event`) is never trimmed; both belong in front of a server on the open internet. Login attempts and login codes that nobody came back for are removed when the next sign-in starts, not by the clock. A user who has never signed in through a provider is matched to its identity by email address at the first sign-in, so whoever holds the address at a provider that names its domain at that moment gets the account; bindings made before this change do not exist, so every user who signed in before is bound by their next sign-in. Whoever holds `sso_provider:manage` can sign in as any user who is not an administrator (see above); there is no lesser permission for, say, renaming a provider. Signing out here does not sign out at the provider, and a user removed at the provider keeps the tokens already issued until they expire or the user is deactivated here. Password sign-in cannot be switched off for an installation, and a password once set cannot be removed. Client secrets are not encrypted in the database. A provider whose issuer differs per tenant (Microsoft's `common` and `organizations` endpoints) is not supported: use the tenant's own issuer. The failure page is fixed at `/sign-in`. Not built: SAML, SCIM, sign-in with a client assertion or a certificate in place of a client secret, and a command that tests a provider's settings before somebody tries to sign in.
- Canada: the provincial sales taxes are set up at their general rates only; reduced rates, exemptions and the rules for what is taxable in each province are the person's choice of code per line. PST that is not recoverable is expensed on 6130 when it is on goods for stock as well, rather than added to the goods' cost. Goods bought for resale are normally bought PST-free under the business's registration, which the template leaves to the person entering the invoice.
- Tax groups: the US example group is a shape, not a jurisdiction; nothing looks up the rates of a place. A component's rate change is a new code, and a group keeps its components as they are; changing a group's components changes what later invoices charge, not what was recorded. Groups are one level deep.
- Party data: a document keeps one billing and one shipping address; there is no delivery address per line, and a purchase document keeps no ship-to of the company's own (the receiving warehouse is not an address). A delivery keeps the customer's default billing address, not the one its order named. The e-invoice export writes the deliver to address (BG-15) only when the invoice kept a shipping address, or for an intra-Community supply; no deliver to party (BG-13) name or location identifier. Sales and purchasing call the party crate, so the party module must be installed with them. There is no generic list or search over party rows (party data is read per party). Setup templates create no party data.
- Electronic invoices: no XSD validation and only the rules the README lists (no code lists, no rules for the categories AE, K, G, L and M beyond rate and reason); the official validator is a separate step. ZUGFeRD / Factur-X is written in the EN 16931 and XRECHNUNG profiles only (not MINIMUM, BASIC WL, BASIC or EXTENDED), and the PDF/A-3 it is in was not checked by veraPDF, which needs Java (not on the machine it was built on): the PDF is checked by our own import, by Ghostscript and poppler, and its XML by the XSD and Schematron. Sending is by e-mail only; Peppol and public buyers' portals are not built. Sending an e-invoice by e-mail does not ask einvoice:export of the sender: `document.send`'s policy decides. Incoming credit notes, document level allowances and charges, attachments, invoicing periods and gross prices are not imported. A tax group cannot be written. Requests are limited by the server's request size (2 MB) before the module's own limits.
- EDI: only the format layer exists (`modules/edi`), and it is not registered in the server: no partner, log, proposal, outbound message or transport yet; `modules/edi/PLAN.md` has the order. The 850 reader knows the standard's segments, not any partner's guide, and has read no real partner's file. Whether an open-source implementation of X12 needs a licence from X12 is not settled (the research quotes X12's own statements); the code is kept to what needs none as far as we can tell.
- Fixed assets: a vendor invoice capitalises an asset through an account line on its class's cost account (see Lines); a machine bought on a purchase order of stock lines goes through inventory and needs a journal entry to the asset account first. An asset is capitalised from one ledger line, whole: neither several lines nor part of one. Amounts are in the accounting currency only. Declining balance works in calendar years, not the company's fiscal year; "this year's depreciation" in the register is from 1 January too. No impairment, revaluation, partial disposal, transfer between classes or companies, separate tax and book depreciation, or units-of-production method. A disposal books proceeds to an account; it does not draft the sales invoice, and posts no tax. Only the latest depreciation run can be reversed.
- Banking: one statement per file; no MT940, BAI2 or CODA; no automatic matching (every match is accepted by a person or an agent through `bank_statement.match`); a line pays open items through one payment drafted for them, never part of a payment or several payments; a posted statement cannot be reversed; statements are entered in order and only the latest can be edited; a file in a currency other than the account's is refused, not converted; no direct bank connection.
- Printing: the server's PDF follows the built-in stylesheet only (see Printing); a template's own `style` attributes show in the browser's page alone, and there is one typeface. The built-in templates are in English. An image may still be loaded from another site in the HTML page (`img` with an https source is allowed), and a template's own stylesheet is dropped: it styles with the built-in classes and `style` attributes. A template cannot be tried on a document before it is saved. Template records are shared: there is no right to manage only one company's templates. Mail: a message is sent as plain text with the PDF attached, in one language; there is no HTML body, no templates for the text, no bounce handling, no DKIM signing of our own (the company's server signs), and the SMTP server's address is not checked against private networks the way webhook addresses are, since a company's relay is often one; a password is refused with `security: none`. The SMTP password is kept as given, in plain text in `smtp_secret`, which no generic read reaches; it is not encrypted at rest. A name resolved when a message is sent can still resolve elsewhere by the time lettre connects. A message given up after 8 attempts is not tried again by itself.
- Stock: one stock unit per item, with other units for buying and selling by an exact factor (no catch weight, no unit that varies by lot, no units on production orders, bills of materials, transfers, adjustments or counts, which are in the stock unit; planning drafts in the stock unit). Lots are traced by production order, not by which component unit went into which product unit; lots carry no cost of their own (no lot costing, no specific identification); a lot is not split, merged or relabelled except by moving goods; no catch weight, no lot status (quarantine, released) beyond what a policy reads from its attributes, no expiry alerts. `stock.availability` (module `planning`) counts what open sales orders still have to deliver as committed, and what released production orders still need, against what is on hand, beside what open purchase orders and production will bring (`on_order`, `in_production`: open and released orders only), and apart from those what draft purchase orders and draft production orders would bring (`planned`, read by planning itself from the drafts), and how much of what is on hand is reserved (`reserved`, from `erpcraft_stock::reserved`; part of what is committed, not on top of it) and free of reservations (`free`); Reservations (`stock_reservation`, stock crate) set stock on hand aside for an order line: an approved sales order reserves for each stock line what it still has to deliver, a released production order its components, each as far as stock on hand not reserved for others covers it (`erpcraft_stock::reserve`, under the level lock). A sales order holds less as its goods leave and lets go when it is closed or cancelled; a production order lets go when it is completed or cancelled. What is reserved never exceeds what is on hand: when goods leave other than for the order that reserved them (another order's delivery, an adjustment, a transfer, a return, production) or a receipt is reversed, the stock ledger cuts the level's reservations back after its lock (`erpcraft_stock::cap_reservations`), keeping the earliest whole and cutting the latest first; a sales delivery and production settle their own order's reservation first and then cut the others back. Reservations are not made again by themselves when goods come in: `sales_order.reserve` does that for an open order. A delivery or a sales return locks the stock levels of every line of its order up front, in the stock ledger's one order, before it reads what others reserve, so two deliveries at once cannot both take what was free for one, and two orders sharing items cannot deadlock. `stock.reservations` lists them in pages (`limit`, `offset`, `total`), with the order and its number only for someone who may read that kind of order, and `erpcraft_stock::reserved` gives them per item and warehouse. A delivery line that takes goods other orders reserved asks the policy `sales_delivery.reserved_elsewhere` (facts: delivering, free, short, item code; allowed by default, so a company keeps reservations firm by refusing or asking approval). Stock issued otherwise (adjustments, transfers, production) does not ask it. Reorder rules (`reorder_rule`: minimum, fill-up quantity, multiple, `procure`, vendor, price) drive `planning.suggestions` (what to buy or make to stay at the minimum, or out of the negative without a rule, net of what is planned) `planning.draft_purchase_orders` (one draft per vendor, at the rule's price or the last price paid on an open or closed order, in the accounting currency; a suggestion with no price is returned, never drafted at 0) and `planning.draft_production_orders` (one draft per item to make, by its active bill; an item to make without one is returned). Whether an item is bought or made is the rule's `procure` (`buy`, `make`); left empty, it is bought when the rule names a vendor, made when the item has an active bill and the rule names no vendor, and bought otherwise. Drafts count as planned, so running a draft command again drafts nothing more, and the draft commands of one company run one at a time (an advisory lock held to the end of the transaction), so two runs at once do not draft the same need twice. A rule's vendor and price show in suggestions only to someone who may read reorder rules; the draft commands take that right, and drafting production orders takes the right to read bills of materials. Bills of materials are shared by all companies, so a bill made for one company makes the item "made" for every company whose rule does not say otherwise. Planning is not time-phased: dates are not looked at, and a made item's components are not exploded into requirements until its order is released (a draft production order plans its product, not its components). A receipt cannot be reversed once part of it has been issued; goods still on hand can be returned instead, and a revaluation document does not exist yet.
- Policies: a rule can allow, refuse or ask for approval. It cannot warn or set a value (a tolerance, a default). A decision is not recorded on its own: a refusal is in the audit log as a failed command, with its message; that a rule allowed something is not noted anywhere. A company's active rules are read from the database once per command, whatever points the command asks, and their conditions are parsed through the rule cache; nothing is kept between commands. A condition is checked for the facts it names when it is saved, but not for their types, so `facts.ordered == 'x'` is saved and then never decidable. Policy rules are shared records: whoever may write them may write them for every company; there is no right to manage only one company's policies. A rule has no validity dates. Approvals: approvers are not told by the system other than through the outbox (`approval.requested`); delegation is by person and span of days, not by company, point or amount, and an administrator cannot set one up for someone else; there is no escalation when a request waits, and a request does not say which other commands are waiting on the same record. The facts are scalars about one line; a condition cannot see the whole document, the vendor or the item. A party's inactivity, a closed order, a posting date, a retired bill or tax code and the price of an invoice are policy points; other refusals that are judgements may remain compiled in where nobody has asked for them yet (for example the line limits of a document, or a payment allocated in full). `posting.date` measures from today in UTC, not in the company's time zone, which is not recorded. The facts of `purchase_order.closed` and `sales_order.closed` add up quantities across lines, whatever their items. A document's form offers only open orders to refer to, even where the company allows a closed one.
- Stock below zero: the ledger checks that the rule an entry names is an active allowing rule of `stock.negative` for the company and that the facts on the entry are true, but not that the condition held for them; that is decided in `erpcraft_stock::post`. Raw SQL can still go below zero by naming such a rule with true facts. What it cannot do is hide it: the entry keeps the facts and the condition, so the condition can be asked again. The fact `context` is the caller's word, and user attributes a condition reads are not recorded; entries from before the facts were kept have none. A rule that an entry names can no longer be deleted, only made inactive. The estimate is the last receipt cost in the same warehouse; the cost of the item elsewhere is not looked at. A reversal that would leave quantity and value pointing different ways is refused (for example taking back an issue after the level went further below zero at another cost), as is taking back a receipt once its goods have moved on. The cost of sales of goods delivered before they arrived stays at the estimate; the difference shows as stock variance, not as cost of goods sold. Nothing reports levels below zero or how long they have been so, and there is no limit by value. A reversal is not asked the policy.
- Over-receipt and over-delivery: goods beyond the order are valued at the order price, and the order's own quantity is not changed. Nothing reports lines received beyond their order. Sales has no policy on the invoice price yet.
- The MCP endpoint answers each request with one JSON object: there are no server-sent streams, no `subscriptions/listen` and no change notifications, so a client learns of new tools when the `ttlMs` of its list runs out. Elicitation, sampling, logging, completion and tasks are not offered. It was tested by speaking the protocol directly, not with an official client.
- Posting cost per line: a journal entry of 100 lines posts in about 60 ms, 0.3 ms per line. It was 1.3 ms before ledger entries were written in one statement, and 0.5 ms while the ledger's rules were checked by a trigger per row; they are now checked once per statement. Of what remains, about 0.1 ms is the four foreign keys of an entry. The lines of purchasing, sales, inventory and manufacturing documents, the values a posting sets on them, order progress and stock entries are written one statement per document, not per line. Stock entries go in one `INSERT ... SELECT ... ORDER BY line_no`, so the ledger's trigger still values them one row at a time in the order given; the levels they find are read once under the lock and followed line by line, so a policy on stock below zero is asked with what each line will find, and the trigger checks it. What is left per line: the account rule asked for each line's inventory account.
